## Objetivo

Captura atribuição de anúncio (título, ad_id) em leads via Evolution API — hoje 0 de 371 conversas do tenant Monique têm dado de anúncio, o parser só lê o formato da Meta Cloud API

## Contexto

Pedido direto, com print real do painel mobile: um lead chegou com "¡Hola! Quiero más información" sem NENHUMA indicação de qual anúncio o originou, apesar do operador suspeitar que boa parte dos leads vêm de anúncio. Auditoria via Supabase confirmou: das 371 conversas do tenant Monique (`8a786c2a-aa8c-4c2a-bc12-d50058c598ce`), **zero têm `ad_headline`/`ctwa_clid`/`ad_source_id` gravado**.

Causa raiz: esse tenant usa a **Evolution API** (WhatsApp self-hosted via QR Code/Baileys), não a Meta Cloud API oficial (confirmado: `tenants.name = 'Monique - Evolution'`, com `tenant_evolution_credentials.instance_name` preenchido). `parseEvolutionWebhookPayload` (`webhookParsers.ts`) nunca extraía atribuição de anúncio — só `parseMetaWebhookPayload` lia `msg.referral` (campo específico do formato de payload da Meta Cloud API). O WhatsApp carrega a mesma informação de clique em anúncio "Clique para WhatsApp" pro protocolo Baileys/Evolution API num campo diferente: `contextInfo.externalAdReply` (mesmo mecanismo do WhatsApp, outro formato de payload).

## Mudança

- `server/services/webhookParsers.ts`: nova função `extractEvolutionAdReferral(message)` lê `contextInfo.externalAdReply` (checando `extendedTextMessage`, `imageMessage`, `videoMessage` e `audioMessage`, já que o clique em anúncio pode preceder qualquer tipo de primeira resposta) e mapeia `title→headline`, `sourceId→sourceId`, `ctwaClid→ctwaClid` (quando presente). Tudo opcional-chain — payload em formato inesperado nunca quebra o parsing, só deixa de capturar atribuição (mesmo comportamento de hoje). Resultado entra no mesmo campo `referral` já usado pelo formato Meta, reaproveitando todo o resto do pipeline sem mudança.
- `server/routes/webhooks.ts`: condição pra chamar `attachAdReferralIfMissing` relaxada de "só com `ctwaClid`" pra "com `ctwaClid` OU `sourceId` OU `headline`" — a Evolution API normalmente não vem com `ctwaClid` (campo específico da Meta), só título/sourceId.
- `server/services/conversationStore.ts`: `attachAdReferralIfMissing` — mesmo relaxamento na entrada, e a checagem de "já gravado antes" (idempotência, nunca sobrescreve) passou a considerar `ad_headline` além de `ctwa_clid`.
- **Não alterado, propositalmente**: `shouldBlockForAdsOnlyMode` continua exigindo um `ctwa_clid` real (não `adHeadline`) pra liberar automaticamente o modo "somente anúncios" — esse é um gate diferente (decide se a IA responde ou fica em silêncio), fora do escopo desta tarefa (que é só sobre o operador conseguir VER de qual anúncio veio, não sobre o comportamento do agente). Ficou como pendência abaixo.
- **CAPI (Meta Conversions API) inalterado**: `fireMetaConversionEvent` já só dispara com `ctwaClid` real presente — gravar `adHeadline`/`adSourceId` sem `ctwaClid` não muda esse comportamento nem risca de mandar atribuição incompleta pro CAPI.

Sem confirmação ainda contra um payload real de produção — não há como testar sem um lead de anúncio de verdade batendo no webhook da Evolution API. A extração foi implementada com o formato documentado do protocolo do WhatsApp (Baileys `ContextInfo.ExternalAdReplyInfo`), com todo acesso opcional-chain (nunca quebra a mensagem se o formato vier diferente).

**Pendente ou risco:**
- **Formato não confirmado contra produção real** — a extração assume que a Evolution API repassa `contextInfo.externalAdReply` sem alterar os nomes de campo do Baileys. Recomendo observar o próximo lead real de anúncio (ou pedir pra alguém clicar num anúncio ativo e mandar mensagem de teste) e conferir se `ad_headline` aparece na conversa — se não aparecer, o formato real pode ter nomes de campo diferentes, e vale adicionar um log temporário do payload cru pra ajustar.
- `shouldBlockForAdsOnlyMode` continua sem reconhecer atribuição só-por-headline (sem `ctwaClid` real) — se esse tenant algum dia ligar o modo "somente anúncios", leads de anúncio via Evolution sem `ctwaClid` continuarão precisando bater um gatilho de texto configurado (`ad_trigger_messages`) ou marcação manual do operador pra liberar a resposta automática. Fora de escopo desta tarefa; sinalizando caso vire prioridade depois.
