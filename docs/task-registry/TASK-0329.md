## Objetivo

Reforça regra do agente pra nunca inventar cidade/bairro ao mandar link de localização (achado real: disse 'Estamos en Asunción' sem esse dado no contexto, studio fica em Luque)

## Atualizações

Pedido direto do dono do produto, com print real de uma conversa: uma cliente ("Sady") pediu o endereço e o agente respondeu "Estamos en Asunción" seguido do link do Google Maps. O dono do produto avisou que o studio fica em Luque, não em Asunción.

**Investigação (Supabase, tenant real "Monique - Evolution", `8a786c2a-aa8c-4c2a-bc12-d50058c598ce`):** o documento publicado `business_profile` só tem `locationMapsUrl` (o link de coordenadas cru) — nenhum campo do KB (nem `companyName`, nem `businessModel`) menciona "Asunción" nem "Luque" em lugar nenhum. Ou seja, "Estamos en Asunción" foi 100% inventado pelo modelo — não veio de nenhum dado real da base de conhecimento. A regra 15 (`autoReply.ts`) já instruía a sempre mandar o link exatamente como está, mas não proibia explicitamente o modelo de ACRESCENTAR uma cidade/bairro chutados quando não há texto de endereço — a regra 5 (nunca invente dado específico) já cobria isso em tese, mas na prática o modelo violou mesmo assim quando o assunto era localização.

**Mudança:** nova regra 26 em `server/services/autoReply.ts` — proíbe explicitamente inventar cidade/bairro/descrição do lugar que não esteja escrita literalmente no contexto, mesmo que "pareça óbvio" a partir das coordenadas do link (deixa claro que o modelo não deve tentar decodificar lat/long de cabeça). Reforço aplicado à Camada 1 (universal, vale pra qualquer tenant) — não é específico deste tenant.

**Fora de escopo desta tarefa (decisão pendente do dono do produto):** corrigir o dado real do tenant "Monique - Evolution" — adicionar o texto do endereço (cidade Luque, e/ou endereço completo) no campo `businessModel` da Base de Conhecimento, pelo painel (Base de Conhecimento → Perfil do negócio), pra que o agente passe a ter a informação correta pra citar em vez de só ter o link cru. Perguntei ao dono do produto o texto exato que ele quer publicado ali, e também o que especificamente está errado nos horários mencionados na mesma conversa (as opções oferecidas vêm direto da disponibilidade real do Google Calendar via `checkFreeBusy` — não existe nenhuma fonte de "horário de funcionamento" configurável na Base de Conhecimento hoje, `opening_hours` é um tipo de documento propositalmente vazio/reservado pra uma evolução futura ainda não aprovada) — sem essa confirmação eu não sei se é um horário fora do expediente real (bloqueio de calendário incorreto) ou outra coisa.

**Arquivos:** `server/services/autoReply.ts`, `server/services/__tests__/autoReply.test.ts`.

**Validação:** `npm run lint` limpo; `npx vitest run` — 274 arquivos / 1511 testes (1 novo, confirma o texto da regra 26 no `systemInstruction`); `npm run build` limpo.
