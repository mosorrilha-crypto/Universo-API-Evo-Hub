## Objetivo

Abre figurinhas recebidas no WhatsApp como mídia de verdade (hoje viravam só texto placeholder)

## Atualizações

Pedido direto (print real, tela de Atendimento): "Ajusta para abrir figurinhas" — no print, uma figurinha recebida aparecia só como "🏷️ Figurinha recebida" (texto puro), sem a imagem, diferente de foto/áudio que já abrem/tocam de verdade no painel.

Investigação encontrou que sticker sempre foi tratado como um tipo `'other'` genérico (junto com vídeo/localização/reação/contato) — `friendlyLabelForOtherType` só troca `[sticker]` cru por um rótulo legível, mas a mídia em si nunca era baixada nem salva, só o texto (`server/routes/webhooks.ts`, ramo `else` final antes desta tarefa).

**Fix**: sticker virou um tipo de primeira classe no parser (`ParsedIncomingMessage.type` ganhou `'sticker'`, com `metaSticker`/`evolutionSticker` — mesmo formato de `metaImage`/`evolutionImage`), e um novo ramo em `webhooks.ts` grava a mensagem como `type: 'image'` (o `MessageType` do painel só tem `text|audio|image|file` — não existe bloco de UI próprio pra sticker, então reaproveita o MESMO player de foto já existente: `RealClientImage`/`GET /api/media/:messageId`) e baixa a mídia com as mesmas funções genéricas já usadas pra foto (`downloadMetaMedia`/`downloadEvolutionMedia` — nenhuma delas é específica de tipo de mídia, funcionam por `media_id`/message key igual pra webp de sticker). **Nenhuma mudança no frontend foi necessária** — o bloco `msg.type === 'image'` em `WhatsAppLeadsSim.tsx` já renderiza qualquer imagem salva sob o `messageId`.

**Decisão deliberada**: o novo ramo de sticker NÃO passa pela análise de "possível comprovante de pagamento" (Gemini analisando a imagem quando há agendamento aguardando pagamento) — esse fluxo é específico de foto sendo comprovante; uma figurinha nunca é.

**Arquivos/commits:** `server/services/webhookParsers.ts` (novo `type: 'sticker'`, `metaSticker`, `evolutionSticker`), `server/routes/webhooks.ts` (novo ramo `else if (msg.type === 'sticker')`), `server/services/__tests__/webhookParsersOtherTypes.test.ts` (teste existente atualizado — sticker não é mais `type:'other'`), `server/routes/__tests__/webhooksStickerMedia.test.ts` (novo, 2 casos: grava `type:'image'` sob o messageId real; nunca dispara escalonamento de pagamento).

**Validação:** `npm run lint`, `npx vitest run` (326 arquivos / 1866 testes) e `npm run build` — todos limpos. Confirmado manualmente (via `git stash` temporário dos arquivos de código) que o novo teste de webhook falha sem o fix (mensagem virava `type:'text'` com id gerado aleatório, não `type:'image'` sob o `messageId` real) e passa com ele. Sem validação visual em browser real (sandbox sem credenciais).

**Pendente ou risco:** sticker mandado DIRETO do celular conectado (fora do painel, eco `fromMe:true` via Evolution) continua sem registro — mesmo comportamento de antes pra qualquer tipo fora de texto/áudio/imagem nesse caminho específico (não fazia parte do pedido, que era sobre sticker recebido de cliente). Sem risco de regressão técnica identificado no restante do pipeline de imagem (funções de download/storage reaproveitadas sem alteração).
