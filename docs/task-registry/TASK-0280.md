# TASK-0280 — Paginação de mensagens ao abrir/rolar uma conversa (histórico sob demanda, igual ao WhatsApp real)

- **Iniciado em:** 2026-09-04T21:28:20.640Z
- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluída

## Objetivo

Paginação de mensagens ao abrir/rolar uma conversa (histórico sob demanda, igual ao WhatsApp real)

## Contexto

Continuação direta do achado de TASK-0279 (print do painel mobile mostrando "Carregando histórico completo desta conversa..." toda vez que abre): o dono do produto perguntou se era normal, e depois pediu explicitamente o comportamento do WhatsApp real: *"não precisa carregar tudo só as últimas msg no whatsapp as mensagens antiga vai sendo carregada conforma o usuário vai rolando as conversas"*.

Investigação confirmou a causa: `getConversation` (usado ao abrir o chat) sempre buscava a conversa INTEIRA — toda mensagem, do início ao fim — mesmo a lista já trazendo um preview leve (só a última mensagem, via `conversation_list_summaries`). Cada abertura de conversa não vista antes na sessão (ou depois de o navegador reiniciar a aba, comum em segundo plano no Android) pagava o custo do histórico completo de novo.

## Mudança

- **`server/services/conversationStore.ts`**: nova função `getConversationMessagesPage(tenantId, phone, { limit, beforeTimestamp, afterTimestamp })` — busca as mensagens da conversa (já filtradas por índice `tenant_id`+`conversation_id`) e pagina EM MEMÓRIA (não delega a `ORDER BY`/operador `>` do client Supabase — evita depender de um `order()`/`gt()` que o fake de teste não implementa, e o volume por conversa é baixo o bastante pra isso não pesar):
  - sem cursor → as `limit` mensagens mais recentes, em ordem cronológica, mais `hasMore` (se existe histórico anterior).
  - `beforeTimestamp` → página anterior a esse timestamp (rolagem pro topo).
  - `afterTimestamp` → só mensagens mais novas que o cursor, sem paginação de `hasMore` (usado pra anexar o que chegou com a conversa já aberta, sem reler tudo de novo).
  - `getConversation` (histórico completo) continua intocado e é quem os outros consumidores (prompt da IA, backup em planilha, retry de transcrição) continuam usando — nunca trocar esses pela versão paginada.
- **`server/routes/conversations.ts`**: nova rota `GET /api/conversations/:phone/messages?limit=&before=&after=`.
- **`src/components/WhatsAppLeadsSim.tsx`**:
  - `loadRealConversationHistory` (chamada na abertura da conversa) passou a buscar só a página mais recente (30 mensagens) via a rota nova, em vez do histórico inteiro.
  - Nova `loadOlderMessages`: dispara ao rolar a conversa pro topo (`handleMessagesScroll`, `scrollTop <= 120`), busca a página anterior e insere no início, restaurando a posição de leitura (compensa o `scrollTop` pelo crescimento do `scrollHeight`, via `requestAnimationFrame`) — sem isso o conteúdo "pularia" pra baixo a cada página carregada.
  - Nova `loadNewerMessages`: substitui a antiga recarga da conversa inteira a cada evento SSE (que agora DESCARTARIA as páginas antigas já carregadas pelo scroll) — busca só o que é mais novo que o já exibido e anexa, deduplicando por id.
  - Texto do placeholder de carga inicial trocado de "Carregando histórico completo desta conversa..." pra "Carregando mensagens recentes..." (reflete que agora é só a última página, rápido) + novo indicador discreto "Carregando mensagens anteriores..." só durante a rolagem pro topo.
- Testes novos: `conversationStoreMessagesPage.test.ts` (6 casos: conversa inexistente, página recente com `hasMore`, tudo cabe numa página, `beforeTimestamp` busca a página anterior corretamente, `afterTimestamp` só traz o que é mais novo, isolamento entre tenants/conversas).

## Encerramento

`npm run lint` limpo, `npx vitest run` — 264 arquivos / 1450 testes passando (6 novos), `npm run build` limpo.

**Arquivos:** `server/services/conversationStore.ts`, `server/routes/conversations.ts`, `server/services/__tests__/conversationStoreMessagesPage.test.ts` (novo), `src/components/WhatsAppLeadsSim.tsx`.

**Pendente ou risco:**
- Validado só por teste automatizado + typecheck/build — não testado manualmente num navegador/celular real (sandbox sem acesso à API em produção nem PWA instalada); vale o dono do produto confirmar a rolagem/posição de leitura funcionando bem num aparelho real antes de considerar 100% fechado.
- Achado colateral, fora do escopo desta tarefa: `isNewChatDateGroup`/`formatChatDateLabel` (`src/lib/chatDate.ts`) tratam qualquer timestamp já formatado como "HH:MM" (o que `loadRealConversationHistory`/`loadOlderMessages` sempre produzem pra exibição) como se fosse "hoje" — ou seja, o separador de data de mensagens antigas de dias anteriores sempre mostra "Hoje", nunca a data real. Isso já existia antes desta tarefa (afetava qualquer conversa de mais de um dia), mas fica mais visível agora que rolar pra cima abre acesso fácil a mensagens de dias/semanas atrás. Não corrigido aqui pra não expandir o escopo — precisaria manter o timestamp ISO cru separado do texto formatado (`HH:MM`) até o ponto de renderização, tocando vários pontos do arquivo que hoje assumem `msg.timestamp` já formatado.
