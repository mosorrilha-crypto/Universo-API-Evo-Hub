# TASK-0346 — Groq/Llama como provedor primário para resposta do especialista (fallback pro Gemini), mitigando incidente de créditos esgotados

## Objetivo

Groq/Llama como provedor primário para resposta do especialista (fallback pro Gemini), mitigando incidente de créditos esgotados

## Atualizações

**Contexto (incidente ativo):** créditos do Google AI Studio esgotados em
produção no momento deste pedido — todo o pipeline de resposta automática
(Gemini) fora do ar simultaneamente para todos os tenants. Pedido direto do
dono do produto: "sim vamos implementar versel sdk, e testar meta como
provedor principal para todo o processo se não funcionar depois voltamos
para gemini" → refinado para "sim caminho mais rápido primeiro visto que o
Gemini está sem créditos" após eu descobrir que o Groq (hospedando modelos
Meta Llama) já estava integrado em produção, mas só na etapa de
classificação do roteador (`classifyAgent`), usando `openai/gpt-oss-20b`
(não um modelo Llama).

**Escopo desta tarefa (caminho rápido):** estender a mesma infraestrutura
já provada (`server/services/groqClient.ts`) para também gerar o TEXTO da
resposta do especialista (FAQ/triagem/agendamento/reclamação), não só a
classificação — reaproveitando o padrão Groq-primeiro-Gemini-de-fallback
já usado no roteador e na decisão de mídia (`decideMidiaActionViaGroq`).
Migração completa pro Vercel AI SDK e extensão do Groq/Llama pro
function-calling real de agendamento (Google Calendar) ficam fora desta
rodada — Stage 2/3 de um plano maior, deliberadamente adiados.

**Implementado:**
- `server/services/groqClient.ts`: `callGroqJsonCompletion` ganhou
  parâmetros opcionais `model`/`temperature` (default preserva
  exatamente o comportamento do roteador). Novos exports
  `GROQ_SPECIALIST_MODEL = 'llama-3.3-70b-versatile'` (modelo Meta Llama
  ativo/produção confirmado na doc oficial da Groq em 08/09/2026 — usa a
  70B, não a 8B, pra melhor aderência às ~26 regras de negócio do prompt;
  evita repetir o incidente real já documentado no código onde
  `llama-3.1-8b-instant` foi descontinuado pela Groq em 16/08/2026 e
  causou fallback silencioso 100% do tempo) e
  `GROQ_SPECIALIST_TIMEOUT_MS = 12000` (maior que o do roteador, 6s — a
  resposta do especialista é texto de atendimento real, não um enum
  curto).
- `server/services/autoReply.ts`: `generateSpecialistReply` ganhou
  parâmetro final opcional `groqApiKey`. Quando presente, tenta primeiro
  o Groq (achatando o `systemInstruction` + contexto dinâmico num único
  prompt de texto, já que `callGroqJsonCompletion` foi construída pra
  esse formato — decisão deliberada de não montar um array de chat
  multi-turno novo pro Groq nesta rodada, pra minimizar risco durante um
  incidente ativo). Qualquer falha (rede, timeout, JSON malformado, ou —
  bug encontrado e corrigido durante a implementação — resposta sem
  `bubbles` válidas) cai pro caminho Gemini já existente, sem propagar
  erro. `recordGeminiUsage(..., 'groq')` chamado no sucesso, seguindo o
  padrão já usado no roteador/mídia.

**Bug encontrado e corrigido na própria implementação (antes de abrir
PR):** o branch Groq inicialmente aceitava qualquer JSON válido como
resposta do especialista, sem checar se realmente tinha `bubbles`. Nos
testes já existentes de fallback (que mockam só o formato do roteador,
`{agent, confidence, reasoning}`), isso fazia a chamada aceitar uma
resposta sem bolhas, cair no `if (!bubbles.length) return null`
pré-existente mais abaixo, e retornar `null` pro cliente em vez de cair
pro Gemini. Corrigido com uma validação explícita (mesmo padrão do
roteador, `ROUTER_VALID_AGENTS.includes`) que lança erro se `bubbles` vier
vazio/ausente, garantindo fallback real pro Gemini.

**Escopo importante a confirmar com o dono do produto:** esta mudança
aplica o Groq/Llama à geração do TEXTO de resposta para TODOS os tipos de
agente, incluindo `agendamento` — mas NÃO toca no function-calling real
contra o Google Calendar (`AGENDAMENTO_TOOLS`), que continua
exclusivamente no Gemini. Ou seja: o Llama pode passar a redigir a frase
que descreve um agendamento, mas quem efetivamente cria/reagenda/cancela
o evento continua sendo o Gemini via tool-calling — nenhuma mutação real
de calendário passa a depender do Groq nesta tarefa.

**Validação:** `npm run lint` (`tsc --noEmit`), `npx vitest run` (277
arquivos / 1519 testes, suíte completa) e `npm run build` — todos limpos.
Sem chamada real à API Groq nesta sessão (sem chave de API disponível) —
validação é por teste automatizado com mocks (incluindo os cenários de
fallback já existentes, `autoReplyGroqRouterFallback.test.ts` e
`autoReplyGroqMidiaFallback.test.ts`) e por leitura cuidadosa do fluxo,
não por teste manual em produção.

**Pendente ou risco:**
- Não testado contra a API Groq real com `llama-3.3-70b-versatile` — a
  qualidade real da resposta (aderência às ~26 regras de estilo do prompt,
  tom, tamanho de bolha) só será confirmada em produção; recomendo
  acompanhar de perto os primeiros atendimentos reais depois do deploy.
- `GROQ_API_KEY` precisa estar configurada em produção (Render) para este
  caminho ativar — se ausente, o comportamento é idêntico ao anterior
  (Gemini direto), sem risco de regressão, mas também sem mitigar o
  incidente atual até a chave existir/ter crédito Groq.
- Confirmar com o dono do produto se o escopo (reply-text para todos os
  agentes, mas sem tocar no tool-calling de agendamento) é o esperado
  como primeiro passo do "testar meta como provedor principal para todo o
  processo" — ou se o passo seguinte (Stage 2, estender pro tool-calling
  de agendamento) deve ser priorizado em seguida.
- Migração completa pro Vercel AI SDK permanece como trabalho futuro
  separado, não iniciada nesta tarefa.
