# TASK-0118 — foto de exemplo do catalogo falha ao enviar via evolution api por data uri nao limpa

## Objetivo

foto de exemplo do catalogo falha ao enviar via evolution api por data uri nao limpa

## Atualizações

Continuação da auditoria pedida pelo usuário ("pode revisar de novo e ver se conseguimos
resolver mais algum gap") sobre o caso real da cliente Arami (595991938552, tenant Monique). Ao
revisar os logs do Render em volta das 3 escalações de "IA não conseguiu gerar resposta
automática (falhou mesmo com retry)" que se acumularam pra essa cliente, encontrei em paralelo
(não é a causa raiz dessas, mas um bug real e recorrente na mesma janela de tempo):

```
⚠️ [runMidiaTool] enviar_foto_exemplo: falha ao enviar foto de "Pestañas" (...):
Falha ao enviar mídia via Evolution API: HTTP 400 —
{"status":400,"error":"Bad Request","response":{"message":["Owned media must be a url or base64"]}}
```

Causa raiz confirmada consultando a `knowledge_base` real no Supabase: `exampleImageBase64` é
salvo como data URI completa (`data:image/png;base64,...`, direto do upload no navegador — ex.:
o produto "Pestañas" tem uma imagem de ~3MB nesse formato). `runMidiaTool`
(`server/services/autoReply.ts:1721`) manda esse valor pra `sendEvolutionMediaMessage`
(`server/services/evolutionSend.ts`) sem tirar o prefixo — diferente do caminho da Meta Cloud API
na mesma função (linha 1732), que já faz `.replace(/^data:[^;]+;base64,/, '')` antes de subir a
mídia. A Evolution API rejeita a data URI inteira como valor de `media`, então **toda tentativa
da IA de mandar uma foto de exemplo pra um tenant configurado via Evolution API falhava
silenciosamente** (capturado por try/catch, vira só um aviso pro especialista — não crasha nada,
mas o cliente nunca recebe a foto).

Vídeo não tem esse problema — vem de um Buffer bruto do Storage (`video.buffer.toString('base64')`),
nunca de uma data URI.

Correção em `server/services/evolutionSend.ts`: `sendEvolutionMediaMessage` agora limpa o prefixo
`data:...;base64,` internamente, antes de montar o payload — protege esse E qualquer chamador
futuro, em vez de depender de cada call site lembrar de limpar (3 dos 6 chamadores já faziam essa
limpeza manualmente antes de chamar; os 2 de `autoReply.ts` — foto e vídeo — não precisavam pro
vídeo, mas a foto sim e não fazia).

Teste novo em `server/services/__tests__/evolutionSend.test.ts` (mesmo padrão já usado pra
`sendEvolutionVoiceMessage`): confirma que uma data URI completa chega limpa no campo `media` do
payload enviado à Evolution API.
