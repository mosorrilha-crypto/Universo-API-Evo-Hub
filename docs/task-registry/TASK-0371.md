## Objetivo

Libera conexao WhatsApp via QR Evolution (self-service) para admin de tenant sem instancia provisionada ainda

## Contexto

Pedido direto, print real do painel SaaS Admin: tenant "Dr. Daniel" (segmento generic) aparecia como "Sem conexão", e o botão "WhatsApp QR" pra conectar só existe dentro de `SaaSAdminDashboard.tsx` — visível só pra `saas_admin` (`App.tsx`: `activeTab === 'saas' && canSeeSaasMaster`). Pergunta do dono do produto: "esse botão está disponível pra admins?" Resposta, confirmada no código: não.

Investigação mostrou que o backend JÁ liberava isso pra `admin` comum desde 15/08/2026 (incidente Clic Piscinas, TASK anterior): as rotas `POST/GET .../evolution-instance*` usam `requireRole('admin')` + `resolveEvolutionTenantId` (ignora `:id` da URL pra quem não é saas_admin, sempre resolve pelo tenantId do JWT). Existe até um componente self-service pronto (`ReconectarWhatsAppQrCode.tsx`, TASK-0167) já plugado na Base de Conhecimento do tenant. O gap real era só de **visibilidade no frontend**: esse botão só aparece quando `GET /api/status/available` responde `true`, e esse endpoint só responde `true` quando o tenant JÁ TEM uma linha em `tenant_evolution_credentials` — ou seja, servia pra RE-conectar, nunca pra fazer a PRIMEIRA conexão de um tenant novo como o Dr. Daniel. Só saas_admin conseguia iniciar a primeira conexão, apesar do endpoint que o botão chama (`POST .../evolution-instance`) já ser idempotente e já suportar provisionar do zero.

## Mudança

- `server/routes/admin.ts`: novo endpoint `GET /api/admin/tenants/:id/evolution-instance/available` (`requireRole('admin')`, mesmo escopo por tenant de `resolveEvolutionTenantId`). Responde `{ available: true, alreadyConnected: true }` se o tenant já usa Evolution; `{ available: true, alreadyConnected: false }` se o tenant não tem NENHUMA credencial própria (nem Meta nem Evolution) e o servidor tem `EVOLUTION_API_URL`/`EVOLUTION_API_KEY` configurados (senão o POST de criação falharia com 503); `{ available: false, alreadyConnected: false }` se o tenant já tem credencial Meta própria configurada (`phone_number_id` preenchido) — nunca oferece Evolution pra quem foi deliberadamente configurado com Meta Cloud API. Endpoint separado de `/api/status/available` de propósito: aquele outro alimenta a feature de Status/Stories (só faz sentido `true` pra quem já está conectado de verdade).
- `src/components/AgentKnowledgeBase.tsx`: troca a chamada de `/api/status/available` por `/api/admin/tenants/:id/evolution-instance/available`; novo estado `whatsAppAlreadyConnected` repassado como prop pro componente.
- `src/components/ReconectarWhatsAppQrCode.tsx`: nova prop opcional `alreadyConnected` — ajusta só o texto/título do botão e do modal ("Conectar WhatsApp" vs "Reconectar WhatsApp"); a lógica de `handleGenerateQr` já criava a instância do zero quando necessário, sem mudança nenhuma aqui.

Sem mudança nenhuma nas rotas de criação/reconexão em si (`POST .../evolution-instance`, `GET .../qrcode`, `GET .../status`, `POST .../recreate`) — já estavam corretas desde 15/08/2026.
