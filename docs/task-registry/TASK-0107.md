## Objetivo

Correção do contador de pendências humanas incluindo escalonamentos arquivados + limpeza de dados de teste em produção

## Atualizações

**Achado real (relatado pelo dono do produto via print do painel):** o card "Resumo da operação" mostrava **24 pendências humanas** para a tenant "Monique — Pestañas por Monique" (`8a786c2a-aa8c-4c2a-bc12-d50058c598ce`), mas na prática só existia 1 pendência real (`awaiting_customer`).

**Causa raiz:** `src/App.tsx` sempre busca `/api/escalations?includeArchived=true` (linha 659) e guarda tudo no mesmo estado `escalations`. O contador (`pendingCount`, usado por `AtendimentoWorkspaceFrame`) filtrava só por `!e.resolved` — mas um escalonamento arquivado (`deleteEscalation` em `escalationStore.ts`) nunca marca `resolved=true`, só troca `status` para `'archived'`. Resultado: todo escalonamento arquivado com `resolved=false` (a maioria, já que arquivar é a ação normal do dia a dia, não um "resolver") continuava contando como pendência.

**Fix de código:** `pendingCount={escalations.filter((e) => !e.resolved && e.status !== 'archived').length}` — exclui explicitamente arquivados, não só não-resolvidos.

**Limpeza de dados (autorizada explicitamente pelo dono do produto):** a tenant real tinha 40 escalonamentos com `status='archived'` acumulados (dados de teste da fase de desenvolvimento, confirmados pelo dono do produto como descartáveis). Executado `DELETE` direto via Supabase MCP (`execute_sql`), escopado por `tenant_id`, com verificação antes/depois:
- Antes: 24 arquivados `resolved=false` + 16 arquivados `resolved=true` + 1 `awaiting_customer` + 1 `resolved`.
- Apagados: 39 linhas (todas com `status='archived'`).
- Depois: só restaram os 2 registros reais (`awaiting_customer` e `resolved`).

Nenhuma outra tenant foi tocada (a query filtrou só pelo `tenant_id` da Monique real, confirmado antes de rodar o DELETE, já que existem 2 outras tenants com "Monique"/"Clic Piscinas" no nome no mesmo banco).
