# TASK-0249 — Achado sistêmico: dados sensíveis (token de auth, token Meta CAPI, CRM/financeiro/base de conhecimento) em localStorage sem criptografia no painel

- **Iniciado em:** 2026-09-03T18:46:40.139Z
- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** achado registrado, sem correção ainda — aguardando decisão do dono do produto sobre prioridade/abordagem

## Objetivo

Documentar um achado real de segurança encontrado durante a TASK-0243 (ao investigar 2 alertas CodeQL "Clear text storage of sensitive information" que bloqueavam o PR #625): o padrão de gravar dados sensíveis em `localStorage` sem nenhuma criptografia é **sistêmico** neste app, não isolado aos 2 pontos já corrigidos na TASK-0243.

## Atualizações

Investigação (agente Explore, `grep -rn "localStorage.setItem" src/` + leitura do que cada chamada grava) encontrou, além do cache de `leads` já corrigido (`saas_whatsapp_leads_${tenantId}`, TASK-0243):

**Dados sensíveis em texto puro em `localStorage`, hoje:**
- `saas_auth_token` (`src/lib/apiClient.ts:17`) — **o JWT de sessão do operador**. Em texto puro. Isso é mais sério que PII: um XSS ou extensão maliciosa lendo essa chave rouba a sessão inteira, não só dados de exibição. Provavelmente o item de maior prioridade da lista.
- `meta_capi_config` (`src/components/AdAttributionCAPI.tsx:169`, lido na linha 85) — guarda `{ pixelId, accessToken, testEventCode, ... }` da Conversions API da Meta. **`accessToken` é um segredo de API de terceiro de verdade**, gravado em texto puro a partir de um formulário.
- `meta_capi_events_log` (`AdAttributionCAPI.tsx:220`, lido na linha 112) — log de eventos disparados, inclui `leadName`, `userHash` (telefone com hash) e `responsePayload` (resposta crua da API da Meta) — exposição de PII moderada.
- `saas_crm_leads_${tenantId}` (`App.tsx:656`) — `LeadInfo[]` do CRM: nome, telefone, e-mail, notas livres do operador sobre o cliente (`crmNotes`), valor do negócio (`dealValue`).
- `saas_transactions_${tenantId}` (`App.tsx:672`) — `FinancialTransaction[]`: nome/telefone do lead, valor, `pixQrCode`, `paymentLinkUrl` — dado financeiro real.
- `saas_agent_kb_${tenantId}` (`App.tsx:692`) — base de conhecimento/catálogo; um comentário já existente no código (`App.tsx:478-481`) confirma um bug real anterior em que esse fallback vazou "dado bancário real" de um tenant — mostra que esse cache específico já teve consequência real, não é só risco teórico.
- `saas_current_user` (`App.tsx:895`) — perfil do operador logado (nome, e-mail, papel) — sensibilidade menor (é o próprio operador, não dado de cliente), mas ainda PII.

**Não existe nenhum helper de criptografia/ofuscação em `src/lib/`** — `localStorage.setItem(key, JSON.stringify(value))` (às vezes envolto em `safeSetLocalStorage`, `App.tsx:66-72`, que só trata `QuotaExceededError`, não é medida de segurança) é o único padrão de persistência client-side usado no app inteiro, pra dado sensível e não-sensível igual.

**Decisão explícita tomada na TASK-0243 (não expandir escopo aqui):** o cache de `leads` (`WhatsAppLeadsSim.tsx`) foi corrigido removendo a gravação inteira, porque uma investigação confirmou que ele só existia por performance (pintura instantânea antes do fetch real) e nenhum comportamento real dependia dele. **Os pontos listados acima são diferentes**: `saas_auth_token` sustenta a sessão logada entre reloads (removê-lo sem substituto quebraria "continuar logado"), o CRM/financeiro/KB provavelmente têm o mesmo papel de cache-pra-performance do `leads` (mas isso não foi confirmado caso a caso), e a Meta CAPI guarda configuração que o operador digitou (não um cache de fetch, então "parar de persistir" mudaria comportamento de verdade, não só performance). Ou seja: **cada item pode precisar de uma abordagem diferente** (mover token de sessão pra um lugar mais seguro que localStorage puro — ex. cookie httpOnly exigiria mudança de arquitetura de auth; reduzir/parar de cachear CRM/financeiro/KB seguindo o mesmo raciocínio do `leads`, se a mesma investigação confirmar que são só cache-pra-performance; criptografar especificamente a config da Meta CAPI, já que ali sim existe motivo real pra persistir o valor entre sessões).

## Encerramento

**Não fechada** — é um achado documentado, não uma correção. Fica pro dono do produto decidir prioridade (recomendação: `saas_auth_token` primeiro, é o único que expõe a sessão inteira, não só dados de exibição) e abordagem por item antes de qualquer sessão futura tocar nisso. Ao decidir, abrir uma TASK nova por item (ou por lote) e resolver com o mesmo rigor de investigação usado aqui — confirmar se cada chave é só cache-pra-performance (nesse caso, seguir o padrão já validado na TASK-0243: eliminar a gravação) ou se sustenta comportamento real (nesse caso, a solução é outra, caso a caso).
