## Objetivo

Fix jobs de fundo quebrados pelo RLS: getDb() sem contexto de tenant em jobs globais (agentPausedAlertJob, evolutionConnectionAlertJob, reminderJob, paymentPendingAlertJob, pendingFollowUpJob, preReservationFollowUpJob, heldAppointmentExpiryJob, messageBuffer)

## Atualizações

Contexto: TASK-0081 (outra sessão) endureceu o RLS — `getDb()` agora exige um
`TenantDbContext` (AsyncLocalStorage) e rejeita sem ele quando
`config.rlsEnforced` está ligado. O commit `2aea569` foi mesclado a `main`
sem as env vars necessárias (`SUPABASE_PUBLISHABLE_KEY`,
`SUPABASE_JWT_SECRET`), derrubando o boot do servidor em produção (loop de
`update_failed` no Render, confirmado via `mcp__Render__list_deploys` +
`mcp__Render__list_logs`) — corrigido primeiro, fora desta tarefa, ao
configurar as duas variáveis no serviço Render e disparar um novo deploy
(ficou live com sucesso).

Com o boot corrigido, os logs de produção revelaram uma SEGUNDA regressão,
esta sim o objeto desta tarefa: jobs periódicos (`setInterval`/
`startPeriodicJob`) nunca rodam dentro de uma requisição HTTP, então nunca
têm `TenantDbContext` — `getDb()` chamado por eles (direto ou via uma
função de store) sempre lançava `Acesso ao banco sem contexto de tenant`,
quebrando silenciosamente 8 jobs de fundo reais: alerta de agente pausado,
alerta de conexão WhatsApp, lembretes de agendamento, alerta de pagamento
pendente, acompanhamento de funil, follow-up de pré-reserva, expiração de
reserva retida e o sweeper de recuperação de buffer de mensagens.

`tenantDbContext.ts` já previa esse caso (`source: 'job'` no tipo
`TenantDbContext`), mas nenhum job de fato usava
`runWithTenantDbContext()` — rollout do RLS ficou incompleto nessa parte.

Correção aplicada em dois níveis:
1. Funções de listagem cross-tenant nos stores (`listTenantIdsWith...`,
   `listConnectedCalendarTenants`, a query de instâncias Evolution em
   `evolutionConnectionAlertJob.ts`, a query de buffers vencidos em
   `messageBuffer.ts`) passaram de `getDb()` para `getPlatformDb()` — são
   inerentemente cross-tenant, nunca deveriam depender de contexto de um
   tenant específico.
2. O processamento por-tenant dentro do loop de cada job passou a rodar
   dentro de `runWithTenantDbContext({ tenantId, source: 'job' }, ...)`,
   preservando o RLS por tenant (em vez de usar a chave de plataforma
   também aqui, o que abriria mão do isolamento dentro do próprio job).

Entregue: `server/services/preReservationStore.ts`,
`pendingFollowUpStore.ts`, `appointmentStore.ts`, `googleCalendar.ts`,
`agentPausedAlertJob.ts`, `evolutionConnectionAlertJob.ts`,
`reminderJob.ts`, `paymentPendingAlertJob.ts`, `pendingFollowUpJob.ts`,
`preReservationFollowUpJob.ts`, `heldAppointmentExpiryJob.ts`,
`messageBuffer.ts`, `server/services/__tests__/tenantDbRls.test.ts`
(novo teste de regressão cobrindo o padrão `source: 'job'`).
