## Objetivo

Registra gaps de segurança (2FA, rotação de senha, UI de auditoria de impersonação) para implementação futura

## Atualizações

**Contexto:** conversa com o dono do produto explicando o processo atual de
controle de acesso e credenciais (RBAC, hash de senha, cookie httpOnly,
gestão de operadores, e a impersonação auditada recém-implementada,
TASK-0363) levantou 3 gaps de segurança reais que não existem hoje no
sistema. Resposta do dono do produto: "registra este gaps para
implementação futura já carreguei os créditos do gemini verifica se a
operação está corrente e os agentes funcionando corretamente" — ou seja,
só registrar (sem implementar agora), prioridade atual é fechar o produto.

**Implementado:** item 8 novo em "Gaps conhecidos que valem engenharia"
(`docs/GUIA-DO-PROJETO.md`) — 3 gaps: sem 2FA (login só e-mail+senha ou
Google, qualquer role incluindo saas_admin), sem expiração/rotação forçada
de senha (só troca voluntária ou reset manual por admin), e sem UI de
auditoria de impersonação (`operator_impersonation_events` grava certinho
mas só é consultável via SQL/Supabase direto, sem tela no painel).
Explicitamente marcado como decisão do dono do produto — nenhum bloqueia
o lançamento hoje.

**Verificação de operação (mesma conversa, pedido paralelo):** conferido
via Render MCP (logs) + Supabase MCP (queries diretas) que os créditos do
Gemini recarregados estão funcionando de verdade em produção:
- Logs confirmam `RESOURCE_EXHAUSTED` (429, "prepayment credits
  depleted") recorrente até ~20:59 UTC (09/09/2026), e chamadas reais
  bem-sucedidas ao Gemini a partir de ~21:14 UTC (transcrição de áudio,
  roteador, especialista, base de conhecimento — todas `outcome=success`)
  pro tenant real (Monique, `8a786c2a-...`) — recarregamento levou efeito
  entre 21:00 e 21:13 UTC.
- Achado adicional (não é regressão nova): Groq também bateu no teto
  diário de tokens (TPD 200.000/dia) nas mesmas horas — o fallback pro
  Gemini funcionou exatamente como projetado (TASK-0346/0350) nesses
  casos.
- `system_incidents` ainda tem 2 linhas `critical`/`open` de "Cota/crédito
  pré-pago do Gemini esgotado" (`last_seen_at` 19:34 e 20:47 UTC) — não se
  resolvem sozinhas, precisam ser marcadas como revisadas/resolvidas
  manualmente em Logs do Sistema agora que o problema passou. Reportado ao
  dono do produto como pendência de ação manual.

**Validação:** mudança é só documentação (`docs/GUIA-DO-PROJETO.md`) — sem
código de produto alterado. `npm run lint`/`npx vitest run`/`npm run
build` rodados mesmo assim (padrão da sessão), todos limpos, sem impacto
esperado.

**Pendente ou risco:**
- Os 2 incidentes `system_incidents` de esgotamento do Gemini continuam
  `open` no banco — ação manual do dono do produto (marcar como
  revisado/resolvido no painel) ainda pendente, não fiz isso
  automaticamente por ser um julgamento humano (confirmar que o problema
  de fato não vai recorrer antes de fechar o registro).
- Os 3 gaps de segurança registrados (2FA, rotação de senha, UI de
