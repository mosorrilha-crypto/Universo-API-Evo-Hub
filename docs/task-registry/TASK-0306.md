## Objetivo

Horários de atendimento não refletem na tela: fetch de business-hours corre antes do login/token estarem prontos e nunca tenta de novo

## Atualizações

Print real do usuário: modal "Horários de atendimento" (Base de Conhecimento) com todos os 7 dias desmarcados/"sem atendimento", relatando "já fizemos várias tentativas mas os horários ainda não persistem".

**Investigação (não confiei no relato à primeira vista — reconstruí o que realmente aconteceu):**
1. Consultei o Supabase direto (`tenants.business_hours`) pro tenant "Monique - Evolution" (`8a786c2a-...`): **o valor JÁ ESTAVA salvo corretamente** — seg-sáb 09:00-18:00. Ou seja, a gravação nunca foi o problema — o `setTenantBusinessHours` já usa `getPlatformDb()` (bypass de RLS), fix de um incidente anterior (TASK-0187) documentado no próprio código.
2. Chequei os logs do Render (`srv-d9p5t5e7bikc738hlen0`) — tráfego real do tenant certo rodando ao vivo (webhooks, router Gemini/Groq) no mesmo intervalo, confirmando que os logs funcionam; nenhuma linha de log específica da rota `/api/business-hours` (rota não tem log próprio, então isso não prova nada por si só, mas descartou "serviço fora do ar").
3. Confirmei que só existe 1 operador pro tenant, `saas_admin`, com `tenant_id` já batendo com o tenant certo — descartei troca de tenant/role insuficiente como causa.
4. **Causa raiz encontrada no código**: o `useEffect` em `App.tsx` que busca `/api/business-hours` tinha `useEffect(..., [])` — sem checar `currentUser`, dispara uma ÚNICA vez no mount, usando o token/`X-Tenant-Id` que existir NAQUELE instante. Se rodar antes da sessão terminar de resolver (ou antes do `activeTenant` corrigir pra o tenant real — `setTenantOverride` também depende de `activeTenant`/`currentUser`), a resposta vem vazia/errada e **nunca tenta de novo pelo resto da sessão**, mesmo depois do login terminar. Confirmei que essa é a MESMA classe de bug já encontrada e corrigida 3 vezes nesse mesmo arquivo (efeitos de `activeTab`/`tenantCapabilities`/`activeTenant` nas linhas ~246-334) — todos guardam com `if (!currentUser) return;` e reagem a `currentUser`/`activeTenant.id` nas deps. A busca de `business-hours` era a única que ainda faltava esse tratamento.

**Fix** (`src/App.tsx`): guarda `if (!currentUser) return;` + deps `[currentUser?.id, activeTenant.id]` (re-busca no login e na troca de tenant, cobrindo também o saas_admin usando o seletor de empresa). Também passou a resetar pra `{}` quando o backend não devolve nada (antes só atualizava se viesse algo — uma troca pra um tenant sem horário configurado continuava mostrando o horário do tenant anterior).

**Validação:** `npm run lint` limpo; `npx vitest run` — 270/270 arquivos, 1490/1490 testes; `npm run build` limpo. Sem teste automatizado dedicado a esse efeito (nenhum existia antes).

**Pendente:** confirmação do usuário — recarregar a página (F5) deve mostrar o horário já salvo (seg-sáb 09:00-18:00), sem precisar salvar de novo, já que o valor real já está no banco.
