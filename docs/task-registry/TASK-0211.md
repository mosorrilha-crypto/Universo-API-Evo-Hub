## Objetivo

criptografia em repouso do refresh token do Google Calendar (AES-256-GCM), item 2 da auditoria de segurança (fase 1 de 2)

## Atualizações

Continuação da auditoria de segurança (comparação com o DeskcommCRM,
TASK-0210). Item 2: credenciais de terceiros ficam em colunas `text`
comuns, protegidas só pelo RLS — confirmado via `information_schema` que
`tenant_calendar_tokens.refresh_token`, `tenant_evolution_credentials.api_key`,
`tenant_instagram_credentials.access_token` e 4 colunas de
`tenant_meta_credentials` (`access_token`, `capi_access_token`,
`meta_ads_access_token`, `meta_ads_management_access_token`) são texto
puro. Diferente do DeskcommCRM (uma tabela só, um ponto de leitura/escrita),
o Universo tem esses tokens espalhados em 5 tabelas e 21+ pontos de leitura
inline pelo código (`tenantResolver.ts` sozinho tem 8+), vários no caminho
quente de envio de mensagem — risco real de quebrar o WhatsApp da tenant
paga em produção se algum ponto de leitura for esquecido.

Sequência escolhida com o dono do produto pra reduzir o risco: começar pela
tabela mais isolada (`tenant_calendar_tokens.refresh_token`, só 2 funções
em `googleCalendar.ts`, nenhum ponto de leitura espalhado, e uma falha só
quebra a reconexão do Calendar — recuperável reconectando, nunca o envio de
mensagem) antes de atacar Evolution/Meta/Instagram (21+ pontos, caminho
quente).

**`server/services/tokenCrypto.ts` (novo)** — AES-256-GCM (autenticado,
GCM detecta adulteração do ciphertext, não só confidencialidade). Formato
autodescritivo `v1:<iv base64>:<tag base64>:<ciphertext base64>`, cabe nas
colunas `text` já existentes sem migration de schema.

- `encryptSecret`/`decryptSecret` usam `TOKEN_ENCRYPTION_KEY` (32 bytes
  base64, `openssl rand -base64 32`).
- **Rollout sem quebra, de propósito**: `TOKEN_ENCRYPTION_KEY` é OPCIONAL.
  Sem ela, `encryptSecret` devolve o valor original sem cifrar (aviso no
  log, uma vez) — nenhum ambiente sem a chave (dev, teste, ou produção
  antes da chave ser gerada) quebra ao gravar. `decryptSecret` reconhece o
  prefixo `v1:` — um valor sem ele é texto puro legado, devolvido como
  está, nunca lança. Nenhum backfill é obrigatório pro código continuar
  funcionando.

**`server/services/googleCalendar.ts`** — `saveRefreshToken` cifra antes
de gravar; `loadRefreshToken` decifra ao ler (compatível com token
legado em texto puro, sem quebrar tenants já conectados).

**`scripts/encrypt-calendar-tokens.ts` (novo, `npm run
encrypt:calendar-tokens`)** — backfill idempotente (pula linha já cifrada,
prefixo `v1:`) pra cifrar o token que já está em produção sem esperar o
tenant reconectar sozinho. Não é obrigatório rodar — só acelera a proteção.

Arquivos: `server/services/tokenCrypto.ts` (novo),
`server/services/googleCalendar.ts`, `scripts/encrypt-calendar-tokens.ts`
(novo), `package.json` (novo script `encrypt:calendar-tokens`).

- Validado com `npm run lint` (limpo), `npx vitest run` (243 arquivos,
  1314 testes, todos verdes — inclui `tokenCrypto.test.ts` novo: cifra/
  decifra roundtrip, IV aleatório produz ciphertexts diferentes pro mesmo
  valor, compatibilidade com texto puro legado, rejeição de ciphertext
  adulterado — GCM —, rejeição de chave com tamanho errado, e o
  comportamento de rollout sem a chave configurada; os testes existentes
  de rotação de token do Calendar continuam passando SEM
  `TOKEN_ENCRYPTION_KEY` no ambiente de teste, confirmando o rollout
  seguro na prática), `npm run build` (limpo).

## Encerramento

**Pendente ou risco:** esta é a FASE 1 de 2 — só o Google Calendar
(isolado, baixo risco). Evolution API, Meta (Cloud API + Ads + CAPI) e
Instagram seguem pendentes, numa tarefa separada, dado o volume de pontos
de leitura no caminho quente de mensagens. `TOKEN_ENCRYPTION_KEY` ainda
precisa ser gerada e configurada em produção (Render) pra a criptografia
entrar em vigor de verdade — sem ela, o código roda normalmente mas
continua gravando em texto puro (rollout intencionalmente não-quebrante).
Recomendo gerar a chave (`openssl rand -base64 32`), configurar no Render,
e rodar `npm run encrypt:calendar-tokens` uma vez pra cifrar o token já
existente.
