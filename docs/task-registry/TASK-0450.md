## Objetivo

Memoiza a lista de conversas do Atendimento (filtro/ordenação + linhas) pra parar de travar ao digitar/receber eventos em tempo real

## Atualizações

Pedido direto ("o aplicativo está um pouco lento e travando, o que pode estar causando isso?"). Investigação encontrou um problema real e concreto: `WhatsAppLeadsSim.tsx` é um componente único enorme (7 mil+ linhas) onde a lista de conversas e o campo de digitar mensagem (`inputMessage`) vivem no MESMO escopo de estado. `archivedLeads`/`filteredLeads` (filtro + ordenação, com busca por texto percorrendo as mensagens de TODOS os leads) eram recalculados sem `useMemo` — ou seja, a CADA renderização do componente, mesmo quando nada relevante mudou. Como digitar no composer (`setInputMessage`) renderiza o componente inteiro, cada letra digitada recalculava a lista inteira (até ~560 conversas em produção) e reconstruía todas as linhas (`renderLeadRow`/`LeadListRow`) do zero.

**Fix (fase 1, baixo risco)**: `useMemo` em 4 pontos — `archivedLeads` (dep: `leads`), `filteredLeads` (deps: `leads`, `searchQuery`, `labelFilter`, `activeTabFilter`) e os dois arrays de linhas JÁ RENDERIZADAS (`archivedLeadRows`/`filteredLeadRows`, deps: a lista filtrada + `activeLeadId`/`flashLeadIds`/`openMenuForLeadId` — as únicas coisas que `renderLeadRow` lê fora do próprio `lead`). Memoizar o resultado MAPEADO (não só o array de entrada) é o que garante que o React nem tente reconciliar as ~560 linhas numa renderização não relacionada à lista (ex: digitar no composer) — React pula a árvore inteira quando recebe a mesma referência de array de elementos.

**Decisão de escopo — por que não `React.memo` por linha também**: avaliei memoizar `LeadListRow` com `React.memo`, mas os handlers passados pra cada linha (`onSelect`, `onTogglePinned` etc.) são funções inline recriadas a cada `renderLeadRow`, e os handlers de origem (`handleSelectLead`, `handleUpdateConversationState` etc.) usam `leads.find(...)` internamente — ou seja, mesmo "corrigindo" com `useCallback`, a identidade mudaria quase tão frequentemente quanto hoje (a cada atualização real de `leads`, que é legítima e frequente — SSE/poll). O ganho adicional seria pequeno frente ao risco de introduzir uma closure obsoleta nesse fluxo central (seleção de conversa), então fiquei só com a memoização em nível de lista/array, que já resolve o problema relatado (digitar trava) sem tocar em nenhum handler.

**Teste de regressão**: `WhatsAppLeadsSim.listMemoization.test.tsx` — mocka `LeadListRow` pra contar quantas vezes é renderizado, seleciona uma conversa entre 30 e digita 5 caracteres no composer; confirma que o contador de renderizações das linhas NÃO aumenta. Confirmado manualmente (via `git stash` temporário do arquivo corrigido) que o teste falha sem o fix (120 → 270 renderizações, 30 leads × 5 teclas) e passa com ele.

**Arquivos/commits:** `src/components/WhatsAppLeadsSim.tsx`, `src/components/__tests__/WhatsAppLeadsSim.listMemoization.test.tsx` (novo).

**Validação:** `npm run lint`, `npx vitest run` (327 arquivos / 1867 testes) e `npm run build` — todos limpos. Sem validação visual/perf real em browser (sandbox sem credenciais) — recomendo o dono do produto confirmar que o campo de resposta não trava mais com a lista de 560 conversas carregada.

**Pendente ou risco:** esta é só a fase 1. A causa estrutural maior continua: a lista renderiza todas as ~560 conversas no DOM de uma vez (sem virtualização tipo `react-window`) — essa memoização evita recálculo/reconciliação em renderizações NÃO relacionadas à lista, mas não reduz o custo real de ter 560 nós no DOM simultaneamente (primeira renderização, scroll, etc.). Virtualização é a fase 2, sinalizada como mudança estrutural maior na tela mais usada do sistema — fica para confirmação explícita do dono do produto antes de implementar (risco de quebrar scroll/seleção/swipe sem validação visual real neste sandbox).
