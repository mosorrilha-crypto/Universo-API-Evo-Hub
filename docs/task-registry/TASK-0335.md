## Objetivo

Fallback de leitura pro Supabase Storage legado (mídia de conversa pré-R2)

## Atualizações

Achado real, pós-merge da TASK-0332 (PR #708, mergeado e já em produção nesta mesma sessão): a migração pro Cloudflare R2 trocou o CORPO das funções `get*` dos 4 arquivos de storage pra só consultar o R2, sem nenhum fallback pro Supabase Storage antigo. Fotos de catálogo da Base de Conhecimento o dono do produto reenvia manualmente (decisão explícita da TASK-0332) — mas mídia de CONVERSA já trocada com clientes (fotos, comprovantes de pagamento) **não dá pra "reenviar"**, já aconteceu. Sem fallback, esse conteúdo ficaria permanentemente inacessível no painel assim que o deploy da TASK-0332 subisse (o que já tinha acontecido antes desta correção).

**Mudança:** novo módulo `server/services/legacySupabaseStorage.ts` com `getLegacySupabaseStorageObject(supabaseUrl, supabaseKey, path)` — reimplementa a chamada REST crua ao Supabase Storage (bucket `app-data`) que existia antes da TASK-0332, com a mesma validação de URL (só http/https) e melhor esforço (nunca lança, qualquer falha vira `null`). `getMediaImage` (mediaImageStore.ts), `getKnowledgeBaseImage` (knowledgeBaseImageStore.ts), `getKnowledgeBaseVideo` (knowledgeBaseVideoStore.ts) e `getKnowledgeBaseDocument` (knowledgeBaseDocumentStore.ts) agora tentam o R2 primeiro e, só se não encontrarem lá, caem pro Supabase Storage legado — os parâmetros `supabaseUrl`/`supabaseKey` (que a TASK-0332 tinha deixado só como `_supabaseUrl`/`_supabaseKey` ignorados, mas todo chamador já passava os valores reais) voltam a ser usados só nesse caminho de fallback. Upload (`putObject`) e delete continuam indo só pro R2 — sem escrita nova no Supabase Storage, sem duplicar dado.

**Arquivos:** `server/services/legacySupabaseStorage.ts` (novo), `server/services/mediaImageStore.ts`, `server/services/knowledgeBaseImageStore.ts`, `server/services/knowledgeBaseVideoStore.ts`, `server/services/knowledgeBaseDocumentStore.ts`, `server/services/__tests__/legacySupabaseStorage.test.ts` (novo), `server/services/__tests__/mediaImageStore.test.ts` (novo).

**Validação:** `npm run lint` limpo; `npx vitest run` — 275 arquivos / 1509 testes (11 novos: 5 cobrindo `getLegacySupabaseStorageObject` — config ausente, URL inválida, sucesso, HTTP não-ok, erro de rede — e 5 cobrindo o encadeamento R2→legado em `getMediaImage`); `npm run build` limpo.

**Pendente ou risco:**
1. Nenhuma env var nova — reaproveita `SUPABASE_URL`/`SUPABASE_KEY` já configuradas em produção.
2. Área crítica (mensageria/mídia de produção) — aguardando revisão explícita antes do merge, sem self-merge.
3. Este fallback é uma ponte de transição: enquanto o conteúdo antigo não for migrado/apagado do Supabase Storage (decisão adiada, ver TASK-0332), a leitura depende de 2 backends. Pode ser removido no futuro quando o bucket `app-data` for descontinuado de vez.
