## Objetivo

Pedido direto do dono do produto: "Configurar o GitHub Actions para realizar a compilação (build) do código e empacotar a aplicação gratuitamente (...). Envie apenas o artefato pronto para o Render, ou faça o deploy utilizando uma imagem Docker pré-construída."

## Investigação

O serviço Render hoje (`universo-api-evo-hub`, confirmado via `mcp__Render__get_service`) é `env: "node"` — builda a partir do código-fonte na própria infra do Render (`npm install && npm run build`), sem suporte nativo a "receber só o artefato pronto" pra um serviço Node (isso é um recurso tipo Heroku slot/slug que o Render não replica pra buildpacks). O caminho real e suportado é o segundo que o pedido já cita: Docker. Confirmado meu próprio tooling (Render MCP `create_web_service`) explicita que não cobre serviços Docker/registro — a troca do serviço existente pra "imagem existente de um registro" é uma ação exclusiva do dashboard do Render, fora do alcance de qualquer ferramenta disponível nesta sessão.

Repositório já é público (decisão anterior, ver `ci.yml`) — GitHub Actions já tem minutos ilimitados de graça pra esse caso (não só os 2.000/mês de repositório privado), e GHCR (GitHub Container Registry) também é gratuito pra imagens públicas.

## O que foi feito

- `Dockerfile` (novo, multi-estágio): estágio `build` com todas as devDependencies pra rodar `npm run build` (Vite + esbuild); estágio `runtime` só com dependências de produção (`npm ci --omit=dev`) + `dist/` copiado do estágio anterior — imagem final bem menor. Base `node:24-bookworm-slim` (glibc, não alpine — `ffmpeg-static` usado por `audioTranscode.ts` baixa um binário estático pré-compilado no postinstall, mais seguro em glibc; versão 24 pra bater com o Node real hoje em produção, confirmado via log na TASK-0317).
- `.dockerignore` (novo).
- `.github/workflows/docker-publish.yml` (novo): dispara via `workflow_run` depois que o workflow `CI` (lint/test/build/dependency review) passar de verdade no mesmo commit de `main` — nunca publica uma imagem sem essa validação. Builda e publica em `ghcr.io/<repo>:latest` + `:<sha>`. Achado real corrigido antes de finalizar: `github.repository` preserva a caixa original do nome do repo (`Universo-API-Evo-Hub`), e GHCR exige minúsculas — adicionado um passo que converte antes de montar as tags, ou o push quebraria.

## Validação

**Não consegui validar com um build real nesta sessão** — o Docker (cliente + daemon) está disponível no sandbox, mas a política de rede do ambiente bloqueia `production.cloudfront.docker.com` (confirmado via `/root/.ccr/__agentproxy/status`, `connect_rejected`/403), que é de onde o Docker Hub serve os blobs da imagem base `node:24-bookworm-slim` — `docker pull` falha por esse motivo, não por erro no Dockerfile. O workflow do GitHub Actions roda em runners com rede irrestrita, então deve baixar a base normalmente lá; recomendo acompanhar a primeira execução real em `main` antes de confiar cegamente.

`npm run lint`/`vitest`/`build` não se aplicam a este PR (sem mudança de código da aplicação, só infraestrutura de build/deploy).

## Pendente ou risco

**Passo manual fora do meu alcance, no dashboard do Render** (nenhuma ferramenta Render disponível cobre isso): pra Render de fato passar a rodar a imagem do GHCR em vez de buildar do código-fonte, alguém precisa, no dashboard, trocar o serviço existente (ou criar um novo) pro tipo "Existing Image" apontando pra `ghcr.io/mosorrilha-crypto/universo-api-evo-hub:latest` — e, como o pacote fica privado por padrão no GHCR mesmo em repositório público, também autorizar o Render a puxar a imagem (token de leitura do GHCR nas credenciais de registro do Render, ou tornar o pacote público depois do primeiro push). **Nada neste PR muda o deploy atual** — o Render continua buildando do jeito de sempre até essa troca manual acontecer; o pipeline novo só fica pronto, esperando.
