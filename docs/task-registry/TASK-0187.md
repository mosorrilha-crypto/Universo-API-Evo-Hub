# TASK-0187 — Callback OAuth do Google Calendar falhava sempre com erro de contexto de tenant ausente, bloqueando reconexao em producao

- **Iniciado em:** 2026-09-01T13:33:29.459Z
- **Agente/plataforma:** Claude
- **Issue central:** [#290](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/290)
- **Status:** concluída

## Objetivo

Callback OAuth do Google Calendar falhava sempre com erro de contexto de tenant ausente, bloqueando reconexao em producao

## Atualizações

**Bug real relatado ao vivo pelo dono do produto** (print do painel mobile, 01/09/2026): ao tentar reconectar o Google Calendar (pedido explícito da TASK-0185, pro escopo de Sheets), a reconexão falhava sempre com "Falha ao conectar / Não foi possível concluir a conexão" na tela do navegador.

**Investigação:** `mcp__Render__list_logs` confirmou a causa real: `❌ [Google Calendar] Falha no callback OAuth: Acesso ao banco sem contexto de tenant — recusado para preservar RLS.` `GET /api/google-calendar/oauth-callback` (`server/routes/googleCalendar.ts`) é uma rota pública (sem `authenticateToken`, porque o Google redireciona o navegador direto pra ela) — nunca passava pelo `TenantDbContext` do `AsyncLocalStorage`. `handleGoogleOAuthCallback` chama `getDb()` (via `saveRefreshToken`) e sempre rejeitava.

**Confirmado que é bug PRÉ-EXISTENTE, não causado pela TASK-0185**: mesma classe de bug dos 8 jobs de fundo corrigidos na TASK-0083 (rollout de RLS, 26/08/2026) — `setInterval`/rotas fora do fluxo autenticado normal nunca ganham `TenantDbContext` sozinhas. Esta rota específica ficou de fora daquela correção porque ninguém tentou conectar/reconectar o Google Calendar desde o rollout de RLS até hoje — o bug ficou latente, sem ninguém perceber, exatamente até a TASK-0185 pedir pro usuário reconectar.

**Fix:** `handleGoogleOAuthCallback` agora roda dentro de `runWithTenantDbContext({ tenantId, source: 'webhook' }, ...)` — o `tenantId` já vem verificado do state assinado (`verifyOAuthState`) antes de chegar aqui, mesmo padrão de confiança dos webhooks do WhatsApp em `tenantResolver.ts`.

## Atualização (parte 2 — "Horários de atendimento" não persistindo, mesmo dia)

Investigado a pedido direto do usuário. **Achado mais sério do que parecia**: não é bug de frontend nem da mesma classe do callback OAuth — é uma lacuna de RLS que afeta QUALQUER update autenticado normal na tabela `tenants`.

Consultei `pg_policies` direto no Supabase de produção: a tabela `tenants` só tem **uma** policy, `tenant_jwt_self`, `cmd = SELECT`, pro papel `authenticated`. **Nenhuma policy de UPDATE existe.** Isso significa: quando uma rota autenticada normal (com `TenantDbContext` via middleware, tudo certo) chama `getDb().from('tenants').update(...)`, o Postgres/PostgREST não retorna erro nenhum — RLS sem policy que autorize simplesmente filtra pra **zero linhas afetadas**, silenciosamente. O código só verifica `if (error) throw error`, e não há erro — então a rota responde sucesso, o frontend mostra o toast de "salvo", e nada realmente mudou no banco.

Varri todos os `.update()`/`.insert()`/`.delete()` em `tenants` via `getDb()` (tenant-scoped) no projeto e achei **3 pontos afetados**, todos corrigidos pra `getPlatformDb()` (seguro aqui porque o `tenantId`/`tenantOf(req)` já vem verificado do JWT autenticado antes de chegar em cada função, nunca de input do cliente — mesmo raciocínio já usado pros jobs de fundo da TASK-0083):

1. **`tenantProfileStore.setTenantBusinessHours`** — o bug relatado (horários de atendimento).
2. **`googleSheetsSync.saveSheetInfo`** — achado colateral, na MINHA PRÓPRIA task (TASK-0185, já mesclada): `backup_sheet_id`/`backup_sheet_url` nunca persistiam de verdade, então cada sincronização recriaria uma planilha nova do zero achando que nenhuma existia ainda.
3. **`PUT /api/public-catalog-settings`** (`conversations.ts`) — Catálogo Público (endereço, contato, mensagens do WhatsApp) também nunca persistia salvamentos feitos depois do rollout de RLS (26/08/2026).

**Outro problema relatado na mesma mensagem, ainda não investigado:** push notifications não ativando no dispositivo ("Registration failed - push service error") — esse texto de erro é gerado pelo próprio `PushManager.subscribe()` do navegador, não pelo nosso código (nosso wrapper só adiciona um prefixo em português). Revisei manifest.json, sw.js e as rotas de push (`pushSubscriptions.ts`) e não encontrei nada de errado no código — esse erro específico é um sintoma bem documentado de falha no serviço de push do próprio Google (FCM) no nível do navegador/Android (rede bloqueando `fcm.googleapis.com`, Play Services desatualizado/com problema, etc.), não uma classe de bug de código nossa. Não abri task pra isso — recomendo tentar em outra rede/reiniciar o Chrome antes de investigar mais fundo.

**Arquivos/commits:** `server/routes/googleCalendar.ts`, `server/services/tenantProfileStore.ts`, `server/services/googleSheetsSync.ts`, `server/routes/conversations.ts`, `server/services/__tests__/tenantDbRls.test.ts` (2 novos testes de regressão).

**Validação:** `npm run lint`, `npx vitest run` (237 arquivos, 1275 testes, 100% verde) e `npm run build` limpos. Causa raiz confirmada via consulta direta a `pg_policies` no Supabase de produção, não só suspeita.

**Pendente ou risco:** nenhuma migration nova necessária (fix é só trocar o cliente usado, não a policy) — mas recomendo fortemente que uma sessão futura faça uma varredura sistemática por TODAS as tabelas tenant-scoped comparando as policies RLS reais (`pg_policies`) contra os métodos (`select`/`update`/`insert`/`delete`) que cada rota autenticada realmente usa via `getDb()`, já que esta classe de bug (RLS sem policy = sucesso silencioso, não erro) pode estar escondida em qualquer tabela que só ganhou policy de SELECT no rollout original.
