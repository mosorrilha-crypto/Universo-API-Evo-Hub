## Objetivo

Migrar imagens inline Base64 da Base de Conhecimento para mídia referenciada (Storage)

## Atualizações

**Etapa 1 (fundação, este commit) — tipos e Storage, sem mudar comportamento nenhum ainda:**

Pedido detalhado do dono do produto (prompt de implementação completo, com objetivo, escopo, princípios obrigatórios, modelo de dados, API esperada, frontend, runtime do agente, script de migração, observabilidade, testes e critérios de aceitação). Antes de editar, li `GUIA-DO-PROJETO.md`, `CLAUDE.md`, e fiz auditoria real do código (não só da doc) — inclusive delegando o mapeamento detalhado de todos os pontos de leitura/escrita dos 4 campos-alvo a um agente de pesquisa, com verificação própria das rotas centrais (`GET/POST /api/knowledge-base`, `POST/GET /api/knowledge-base/videos`) antes de desenhar a solução.

**Achado que definiu o desenho:** o padrão já existente pra vídeo (`knowledgeBaseVideoStore.ts`, usado desde antes desta task) NÃO usa uma tabela de metadados separada como o prompt sugeria — usa Storage puro (bucket `app-data`, prefixo `kb-video/{tenantId}/{videoId}`, upload/get/delete via `fetch` cru na REST API do Storage) com os metadados (`mimeType`/`fileName`/`sizeBytes`) inline no próprio JSON da Base de Conhecimento, ao lado do id. Segui esse padrão exato pra imagem, em vez de introduzir uma tabela SQL nova — mais simples, já provado em produção, e é exatamente o que o prompt pediu ("escolha o modelo que melhor se encaixa no schema existente... não copie [a tabela sugerida] cegamente").

**Também confirmado na auditoria:** `service_catalog`/`media_assets` (documentos tipados, o sistema de publicação REAL que o painel usa hoje, "Operação visual única") reaproveitam as MESMAS interfaces `AgentProduct`/`FirstContactBlock` do blob legado — uma mudança de tipo cobre os dois caminhos de uma vez, sem migração duplicada.

Mudanças feitas nesta etapa:
- `server/services/knowledgeBaseStore.ts`: `AgentProduct`, `ProductVariant`, `BeforeAfterPair`, `FirstContactBlock` ganham `exampleImageId`/`beforeImageId`/`afterImageId`/`imageId` (+ `MimeType`/`FileName`/`SizeBytes`), mantendo os campos `*Base64` como opcionais (antes obrigatórios em `BeforeAfterPair`) e marcados `@deprecated` — só lidos como fallback de registro legado, nunca mais produzidos por upload novo. Nova função `collectReferencedImageIds()`, espelhando `collectReferencedVideoIds()` já existente — cobre também `beforeAfter` (2 ids por par, before/after), caso que vídeo não tem.
- `server/services/knowledgeBaseImageStore.ts` (novo): `uploadKnowledgeBaseImage`/`getKnowledgeBaseImage`/`deleteKnowledgeBaseImage`, cópia estrutural de `knowledgeBaseVideoStore.ts` (bucket `app-data`, prefixo `kb-image/{tenantId}/{imageId}`), com `ALLOWED_IMAGE_MIME_TYPES` (JPEG/PNG/WebP — os 3 que a Meta aceita direto, sem transcodificação, diferente de vídeo) e `MAX_IMAGE_BYTES` (5MB, limite real da Meta Cloud API pra imagem).

**Próximas etapas (ainda não implementadas, mesma task):** rotas `POST/GET /api/knowledge-base/images/:imageId` (modelo: `POST/GET /api/knowledge-base/videos`), limpeza de órfão no save (modelo: `POST /api/knowledge-base` + `collectReferencedVideoIds`, mas também precisa ser estendida pro caminho de documentos tipados que hoje NÃO tem limpeza de órfão nenhuma — achado da auditoria, gap pré-existente independente de imagem), runtime do agente (`autoReply.ts` `runMidiaTool`, `firstContactMessage.ts`, `conversations.ts` `send-example-photo`) lendo do Storage com fallback pro Base64 legado, catálogo público (`publicCatalogStore.ts`/`catalogImageThumbnail.ts`) buscando do Storage antes de comprimir, frontend (`AgentKnowledgeBase.tsx` — replicar o fluxo de upload real que vídeo já tem, hoje foto ainda é só `FileReader`+`formData` local), `catalogPdf.ts` (hoje assume a foto já em memória, precisa buscar via fetch), script `scripts/migrate-knowledge-base-images.ts` (dry-run, idempotente, por hash SHA-256), testes de isolamento/segurança/upload/compatibilidade/migração/frontend.

**Achados colaterais da auditoria, fora do escopo direto mas relevantes:**
- `App.tsx` (linha ~674) remove `exampleImageBase64` do cache do `localStorage` só do produto pai — nunca de variantes/before-after/1º-contato. A migração resolve isso de raiz (ids são curtos, sem risco de estourar cota).
- Limpeza de mídia órfã no save (Issue #261) só existe hoje no caminho legado (`POST /api/knowledge-base`), nunca no caminho de documentos tipados (`PUT .../draft`) que é o realmente usado pelo editor visual atual — gap pré-existente pra vídeo também, não só imagem.

**Etapa 2 — rotas de upload/servir imagem + limpeza de órfão no save (commit `16ca591`):**
- `server/routes/conversations.ts`: novas rotas `POST /api/knowledge-base/images` (upload — valida MIME/tamanho, sobe pro Storage, devolve `{imageId, mimeType, fileName, sizeBytes}`) e `GET /api/knowledge-base/images/:imageId` (download autenticado, `Cache-Control: private, max-age=3600`), cópia estrutural das rotas de vídeo equivalentes.
- `POST /api/knowledge-base` (save real): estendida a limpeza de órfão (Issue #261) já existente pra vídeo — compara `collectReferencedImageIds()` antes/depois do save e apaga do Storage só o que deixou de ser referenciado. Cobre explicitamente o caso de `beforeAfter` ter 2 ids por par.
- **Decisão de desenho registrada:** a limpeza de órfão NÃO foi estendida ao caminho de documentos tipados (`PUT .../draft`) nesta task — esse sistema preserva histórico via status `archived`, e um diff ingênuo "antes vs depois do draft" arriscaria apagar mídia ainda referenciada por uma versão histórica/publicada, violando diretamente o princípio de segurança do próprio pedido ("nunca apagar mídia referenciada por qualquer versão ativa, publicada OU HISTÓRICA"). Fica para a operação de "Limpeza" separada (script de migração), que pode auditar todas as versões históricas antes de decidir que algo é órfão de verdade.
- Testes novos: `conversationsKnowledgeBaseImage.test.ts` (10 testes — upload/download) e `conversationsKnowledgeBaseSaveOrphanImage.test.ts` (6 testes — limpeza no save, incluindo o caso before/after).

**Etapa 3 — runtime do agente lê do Storage com fallback pro Base64 legado (este commit):**

Contrato de compatibilidade implementado em `resolveKnowledgeBaseImageBinary()` (`knowledgeBaseImageStore.ts`): se existir `imageId`, busca no Storage; senão, se existir Base64 legado, usa e registra observabilidade (`logStructured`, `detail: 'source=legacy_base64_fallback'`); senão, considera a imagem ausente. `imageId` presente mas não encontrado no Storage é tratado como ausente (nunca cai pro Base64 legado).

Os 3 pontos que efetivamente mandam a foto real por WhatsApp foram migrados pra usar esse resolver único, em vez de ler `exampleImageBase64`/`imageBase64` direto:
- `server/services/autoReply.ts` (`runMidiaTool`, ferramenta `enviar_foto_exemplo`): guarda de match e filtro `productsWithPhoto` aceitam `exampleImageId` OU `exampleImageBase64`; resolve o binário via `resolveKnowledgeBaseImageBinary`; se vier `null` (imageId cadastrado mas arquivo sumiu do Storage), devolve `actionsSummary` explicando sem travar o fluxo — mesmo padrão já usado pelo bloco de vídeo vizinho.
- `server/services/firstContactMessage.ts` (bloco `image` da sequência de 1º contato): mesma troca; `blockHasContent()` passa a aceitar `imageId` também. **Achado colateral corrigido de brinde:** o bloco de imagem nunca salvava o binário via `saveMediaImage` sob o id da mensagem (diferente do bloco de vídeo, que já fazia isso desde o achado real de 15/08/2026, Clic Piscinas) — o painel mostraria "Imagem indisponível" pra sempre pra esse bloco específico. Corrigido junto, replicando o padrão do vídeo.
- `server/routes/conversations.ts` (`POST /:phone/send-example-photo`, envio manual pelo operador): mesma troca, espelhando como o `send-example-video` irmão já buscava do Storage.

Testes novos/estendidos (todos cobrindo o caminho novo via Storage E o caso "não encontrado", além dos testes pré-existentes do caminho legado continuarem passando sem alteração):
- `server/services/__tests__/autoReply.test.ts`: +2 testes (`envia a foto real via Storage...` / `avisa que a foto não foi encontrada no Storage...`).

- `server/services/catalogImageThumbnail.ts`: `buildCatalogThumbnail()` passa a receber um `Buffer` já resolvido em vez de uma string Base64 — quem chama busca o binário (Storage ou fallback legado) antes de comprimir, evitando um round-trip buffer→base64→buffer desnecessário (achado da auditoria original).
- `server/services/publicCatalogStore.ts`: novo `CatalogImageContext` ({supabaseUrl, supabaseKey, tenantId}) passado por `toPublicCatalog`/`toPublicCatalogProduct`/`publicVariant`/`publicBeforeAfterPair(s)`; cada foto (produto, variante, antes/depois) é resolvida via `resolveKnowledgeBaseImageBinary` antes de virar miniatura. `toPublicCatalog`/`getPublicCatalogBySlug` agora recebem `{supabaseUrl, supabaseKey}` explicitamente — threading desde `server.ts`/`createPublicCatalogRouter` (mesmo padrão de injeção de config já usado pelos outros routers), já que o catálogo público não tem JWT de operador pra resolver essas credenciais de outro jeito.
- `src/types.ts`: `AgentProduct`/`ProductVariant`/`BeforeAfterPair`/`FirstContactBlock` ganham os campos espelhados (`exampleImageId`/`beforeImageId`/`afterImageId`/`imageId` + `FileName`/`SizeBytes`) já existentes no backend desde a Etapa 1 — o frontend não os tinha ainda. `BeforeAfterPair.beforeImageBase64`/`afterImageBase64` viram opcionais (`@deprecated`), igual ao backend.
- `src/lib/catalogPdf.ts`: `compressProductImageDataUri` (via novo `resolveProductImageSrc`) busca a foto via `GET /api/knowledge-base/images/:imageId` (autenticado, `apiFetch`) quando o produto já tem `exampleImageId`, com fallback pro `exampleImageBase64` legado — antes assumia a foto sempre já em memória, premissa que deixa de valer pra produtos migrados.
