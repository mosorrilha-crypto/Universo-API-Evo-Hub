# TASK-0389 — Fecha o ciclo atendimento-agendamento-pagamento: comprovante vincula a agendamento já resolvido e permite registrar agendamento na hora

- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluído

## Objetivo

Pedido direto do dono do produto, com print: "quando eu marco este comprovante não consigo lincar com um agendamento realizado fechando o ciclo — vc pode rever este fluxo entre atendimento, agendamento e pagamento".

## Investigação

O checkbox "Vincular a este agendamento" (`TransactionDialog.tsx`, usado a partir de "Marcar como comprovante" no chat) já existia, mas só aparecia quando o agendamento rastreado do contato ainda estava aguardando aprovação (`payment_status` `awaiting_payment`/`pending_verification` — o ciclo curto da IA: pré-reserva → comprovante → aprovação, via `POST .../verify-payment`).

Confirmei o achado direto em produção (Supabase, tenant Monique, telefone 595981749001 do print): **zero linhas** em `appointments` e **zero eventos** em `appointment_journey_events` pra esse contato — o comprovante marcado virou uma receita 100% avulsa (já registrada, `sourceRef: chat-image:...`). Causa raiz é estrutural: `appointments` guarda só 1 linha "atual" por telefone (upsert), sem histórico — um agendamento já concluído (ou nunca tracked pela IA) não deixa rastro nenhum pra linkar depois.

## O que mudou

**Parte 1 — vínculo deixa de exigir status "aguardando":** `linkableAppointment` (WhatsAppLeadsSim.tsx) agora oferece o checkbox pra QUALQUER agendamento atualmente rastreado, não só os 2 status originais. `savePaymentProofTransaction` decide o caminho pelo estado real (nunca pelo operador): se ainda aguardando aprovação, comportamento intocado (`verify-payment`, cria evento real quando falta); se já resolvido (verificado/confirmado/manual), NÃO reexecuta `verify-payment` — evitaria sobrescrever o valor de uma cobrança já fechada com o valor deste comprovante novo (pode ser serviço adicional/outra visita) — em vez disso, anexa um SNAPSHOT do agendamento (resumo/data/eventId) ao lançamento avulso.

Snapshot novo, não uma FK (3 colunas nullable em `financial_transactions`, migration `0086` aplicada em produção): `linked_appointment_event_id`/`_summary`/`_start_iso`. Deliberadamente separado de `source_ref` (que tem índice único por tenant, migration 0037, usado pra deduplicar `apt:<eventId>` do verify-payment) — nunca compete por esse valor.

**Parte 2 — registrar na hora quando não existe nenhum agendamento:** `TransactionDialog.tsx` ganhou um atalho opcional "Registrar agora" (só aparece com `lockedLead` + sem `linkableAppointment` + callback fornecido) que reaproveita 100% o `ManualAppointmentModal`/`POST .../manual-appointment` já existentes (issue #182) — nenhum formulário novo. Ao clicar, o `TransactionDialog` se esconde temporariamente (`paymentProofDraft` nunca é tocado) e o `ManualAppointmentModal` abre; ao criar o agendamento com sucesso, `paymentAppointment` já é atualizado pelo handler existente e o `TransactionDialog` reaparece com o vínculo disponível (Parte 1).

**Arquivos:** `supabase/migrations/0086_financial_transaction_appointment_link.sql`, `server/services/financialStore.ts`, `server/routes/financial.ts`, `src/types.ts`, `src/App.tsx`, `src/components/financial/TransactionDialog.tsx`, `src/components/WhatsAppLeadsSim.tsx` + testes novos (`financial.test.ts`, `TransactionDialog.appointmentLink.test.tsx`).
