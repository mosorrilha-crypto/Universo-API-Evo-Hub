## Objetivo

Migra mídia (Base de Conhecimento + mensagens de WhatsApp) do Supabase Storage pro Cloudflare R2 pra eliminar o estouro de egress

## Atualizações

Pedido direto do dono do produto, continuação da investigação do estouro de egress do Supabase (ciclo de faturamento 07/08-07/09/2026, "Saída" em 276% do limite do plano Free). Auditoria via logs (`mcp__Supabase__query_logs`) confirmou que Storage respondeu por ~91% do egress em 24h (6,13 MB de 6,75 MB, com só 27 requisições — mídia de WhatsApp e fotos de exemplo do catálogo, não a API REST). Dono do produto confirmou: sem necessidade de migrar o conteúdo já existente (reenvia manualmente as fotos), autorizado apagar o antigo se precisar.

**Causa raiz:** o bucket privado `app-data` do Supabase Storage guarda tanto mídia recebida/enviada por WhatsApp (`mediaImageStore.ts`) quanto fotos de exemplo/vídeos/documentos da Base de Conhecimento (`knowledgeBaseImageStore.ts`/`knowledgeBaseVideoStore.ts`/`knowledgeBaseDocumentStore.ts`) — mesma classe de incidente já documentada em TASK-0074/0075/0218 (na época o problema era Base64 inline no JSON; a correção de lá moveu pro Storage, que agora sozinho estourou a cota de egress).

**Mudança:** Cloudflare R2 (S3-compatível, sem cobrança de egress) substitui o Supabase Storage nesses 4 arquivos. Novo módulo `server/services/objectStorage.ts` com 3 operações primitivas (`putObject`/`getObject`/`deleteObject`) via `@aws-sdk/client-s3` (SDK oficial da AWS, compatível com R2 apontando `endpoint: https://<account_id>.r2.cloudflarestorage.com`, `region: 'auto'`), credenciais lidas de 4 variáveis de ambiente novas (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`).

Os 4 arquivos que já falavam com o Supabase Storage (upload/get/delete via `fetch` cru na REST API) tiveram só o CORPO das funções trocado pro novo módulo — a assinatura exportada ficou EXATAMENTE igual (inclusive os parâmetros `supabaseUrl`/`supabaseKey`, agora ignorados) pra não precisar tocar nos ~45 pontos de chamada espalhados pelo projeto (autoReply.ts, conversations.ts, firstContactMessage.ts, rotas admin, etc.) nem nos testes existentes — confirmado que nenhum deles quebrou.

**Arquivos:** `server/services/objectStorage.ts` (novo), `server/services/knowledgeBaseImageStore.ts`, `server/services/knowledgeBaseVideoStore.ts`, `server/services/mediaImageStore.ts`, `server/services/knowledgeBaseDocumentStore.ts`, `server/services/__tests__/objectStorage.test.ts` (novo), `package.json`/`package-lock.json` (`@aws-sdk/client-s3`).

**Validação:**
- `npm run lint` limpo; `npx vitest run` — 273 arquivos / 1499 testes (7 novos, cobrindo config ausente/completa, upload, download, "objeto não encontrado" vs erro real propagado, delete); `npm run build` limpo.
- Validação end-to-end contra o R2 real não foi possível nesta sessão — preciso das credenciais reais do bucket (ver pendências).

**Pendente ou risco:**
1. **Preciso que o dono do produto crie o bucket + token de API no painel do Cloudflare** e me passe: Account ID, Access Key ID, Secret Access Key, nome do bucket (privado — nunca marcar como público, mesma política de acesso via rota autenticada já usada pro Supabase).
2. **As 4 variáveis de ambiente precisam ser configuradas em produção** (Render) antes do deploy — sem elas, upload lança erro explícito ("Storage não configurado") e download/delete retornam vazio (fail-safe, nunca mascara indisponibilidade como dado ausente de verdade — mesmo padrão de antes).
3. **Conteúdo já existente no Supabase Storage não foi migrado nem apagado** — decisão explícita do dono do produto (reenvio manual). O bucket `app-data` do Supabase pode ficar órfão/ser limpo depois, sem pressa.
4. Reforço: este PR é área crítica (mensageria/mídia de produção) — aguardando revisão explícita antes do merge, sem self-merge.
