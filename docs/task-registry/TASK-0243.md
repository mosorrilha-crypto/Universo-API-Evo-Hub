## Objetivo

Canal Evolution: filtro de contatos dentro/fora da janela de 24h na lista de conversas + corrige aviso de janela pra não tratar Evolution como se tivesse a mesma restrição de template da Meta

## Atualizações

Achado durante a revisão final do PR #599 (auditoria da "Central de Operação por WhatsApp"): a faixa de status de janela de 24h e o bloqueio de "Reabrir a conversa" (implementados nesse PR) tratavam qualquer canal como se tivesse a restrição de template da Meta — mas essa é uma regra técnica exclusiva da API oficial (Cloud API); Evolution (Baileys/QR code) não tem esse tipo de restrição, e não existe conceito de "template" nesse canal (`server/services/evolutionSend.ts` só tem `sendEvolutionTextMessage`/`sendEvolutionVoiceMessage`/`sendEvolutionMediaMessage` — nenhuma função de template). O risco real no Evolution é outro: reengajar contato inativo há muito tempo por cliente não-oficial (Baileys) pode aumentar o risco de o número ser sinalizado/banido pelo próprio WhatsApp — risco de reputação, não de rejeição técnica.

**Migration 0076 (`conversation_list_summary_window`, aplicada via Supabase MCP, confirmada em `list_migrations`):** acrescenta `last_lead_message_at` (última mensagem especificamente do LEAD, não da conversa em geral — necessário porque `getCustomerServiceWindowStatus` conta a janela a partir dela, e ela quase sempre é seguida de uma resposta do agente/operador) e expõe `phone_number_id` (já existente na tabela `conversations`, não estava na view) na view `conversation_list_summaries` — usado tanto pro novo filtro da lista quanto pra saber se a conversa é do canal Meta sem N+1 chamadas.

**Backend (`server/services/conversationStore.ts`):** `ConversationSummaryRow`/`StoredConversation` ganham `lastLeadMessageAt`; `toStoredConversationSummary` popula o campo. 2 testes novos em `conversationStoreSummary.test.ts` (regressão validada via `git stash` do código-fonte: falharam contra a versão anterior como esperado, restaurado e suíte completa volta a passar 100%).

**Frontend (`src/components/WhatsAppLeadsSim.tsx`, `src/types.ts`):**
- Novo filtro na lista de conversas: aba "Fora das 24h" (`activeTabFilter: 'window_closed'`), contagem em tempo real via `lastLeadMessageAt`.
- Faixa de status da conversa aberta corrigida: quando `phoneNumberId` está ausente (canal não-Meta), mostra aviso de risco de reengajamento em vez do bloqueio "precisa de WABA" — sem impedir o envio (nunca impediu de verdade, só a informação estava errada).
- O `useEffect` que checa WABA configurado (`reopenAvailability`) agora só roda pra conversas do canal Meta (`phoneNumberId` presente) — evita chamada de API inútil pro Evolution.

**Validação:** `npm run lint` / `npx vitest run` (256 arquivos, 1412 testes) / `npm run build` — todos limpos.

**Botão "Sugerir mensagem de retomada" no canal Evolution:** o botão "Reabrir a conversa" tinha sido removido de vez pro canal Evolution na primeira passada — o usuário pediu pra manter uma ação equivalente, mas preenchendo o campo de mensagem com um texto de retomada sugerido em vez de abrir o modal de templates da Meta (que não se aplica nesse canal, já que Evolution não tem conceito de template). Implementado em `WhatsAppLeadsSim.tsx`: nova `buildReengagementDraft(leadName, tenantName)` (texto adaptado do template `retomada_atendimento` de `operatorFollowUpService.ts`, mas em pt-BR e já interpolado — sem placeholder `{{n}}`, já que Evolution manda texto puro) + novo handler `handleDraftReengagementMessage` (reaproveita `handleDraftSuggestedReply` já existente, sem alterar seu contrato pros outros 2 chamadores que já usam) + foco automático no campo via `composerTextareaRef`. Rótulo do botão deliberadamente diferente de "Reabrir a conversa" (nada está de fato bloqueado nesse canal — reusar o rótulo da Meta reintroduziria em texto o mesmo erro já corrigido na lógica). Mesmo estilo visual do botão Meta (ícone `Sparkles`, classes emerald). Sem teste automatizado novo (JSX + função pura de 1 linha, sem padrão de teste de interação estabelecido neste componente) — validado via `npm run lint`/`npx vitest run`/`npm run build`.

**Achado real de auditoria — CodeQL bloqueando o PR #625 (não relacionado ao objetivo desta task, mas resolvido pra destravar o merge, a pedido do usuário):** 2 alertas HIGH "Clear text storage of sensitive information" em `WhatsAppLeadsSim.tsx:2168`/`:2828` — pré-existentes, fora do diff real do PR, só ficaram "novos" na comparação por estarem no mesmo arquivo. As duas linhas gravavam o array `leads` inteiro (nome, telefone, histórico completo de mensagens de clientes reais, incluindo mídia base64 de comprovantes) em `localStorage` sem criptografia nenhuma. Investigação (agente Explore) confirmou que esse cache (`saas_whatsapp_leads_${tenantId}`) servia só pra pintura instantânea da lista — nenhum caminho de fallback funcional depende dele. Corrigido eliminando os sinks: removidos os 2 `localStorage.setItem`, os 2 `localStorage.getItem` correspondentes (lista agora começa vazia e é populada só pelo fetch real), e adicionada uma purga ativa (`useEffect` de montagem varrendo `Object.keys(localStorage)` por qualquer chave `saas_whatsapp_leads_*` de qualquer tenant) pra limpar PII já gravada em navegadores de sessões anteriores à correção — sem isso, parar de escrever não apagaria o que já estava lá. `clearCachedTenantScopedData` (App.tsx, roda no logout) mantido intacto como rede de segurança adicional. Rejeitadas as alternativas de só reduzir campos antes de serializar (o sink continuaria existindo) ou cifrar no cliente (a chave ficaria acessível no próprio JS, não protege de verdade). Validado: `npm run lint`/`npx vitest run` (257 arquivos, 1417 testes)/`npm run build`, todos limpos.

**Achado colateral registrado, fora de escopo desta correção:** o mesmo padrão (localStorage sem criptografia) é sistêmico no app — token de autenticação (`saas_auth_token`), access token da Meta CAPI (`meta_capi_config`), CRM/financeiro/base de conhecimento (`App.tsx`) usam o mesmo padrão, alguns com dado ainda mais sensível (tokens reais, não só PII). Sem helper de criptografia/ofuscação em `src/lib/` hoje. Registrado como TASK própria (ver #504) pro dono do produto decidir prioridade/abordagem.
