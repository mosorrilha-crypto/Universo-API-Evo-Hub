## Objetivo

Transcrição de áudio ENVIADO pelo painel (fecha a brecha de contexto do agente)

## Atualizações

**Achado real (reportado pelo dono do produto):** hoje o painel só transcreve áudio RECEBIDO do cliente (`webhooks.ts` + `transcriptionQueue.ts`, via Gemini). Áudio ENVIADO pelo operador pela rota `POST /api/conversations/:phone/send-media` nunca era transcrito — ficava salvo pra sempre como o placeholder literal `"🎤 Áudio enviado"`. Como `autoReply.ts` monta o histórico do agente a partir de `message.text` (`buildHistoryText`, que nem olha `type`), isso era uma brecha real: uma instrução dada por voz pelo operador nunca chegava ao contexto do agente.

Investigado via agente Explore (read-only) contra o código real antes de codar, confirmando linha a linha: `transcribeAudioWithGemini` (`server/services/geminiTranscription.ts`) e `updateMessageText` (`conversationStore.ts`, genérica, não amarrada a "entrada") já existiam e já eram usadas exatamente nesse padrão pela rota `POST /api/conversations/:phone/messages/:messageId/retry-transcription` (re-transcrição de áudio recebido) — bastava replicar o mesmo padrão no envio.

**Decisão confirmada com o dono do produto antes de codar:** se o Gemini falhar/estiver indisponível na hora de transcrever um áudio enviado, gravar o mesmo texto de fallback já usado do lado de entrada (`"[Não foi possível transcrever o áudio no momento]"`), em vez de manter o placeholder original — sinaliza claramente que houve uma tentativa falha.

**Fix (`server/routes/conversations.ts`, rota `send-media`):** depois do envio real (Meta/Evolution) e de `recordOutgoingMessage`/`saveMediaImage`, quando `msgType === 'audio'`, chama `transcribeAudioWithGemini` de forma AGUARDADA (não fire-and-forget — o handler já espera o envio real terminar antes de responder, então mais um `await` do Gemini é consistente com a latência que a rota já tem, e fica determinístico/testável) dentro de um `try/catch` que nunca derruba a resposta de sucesso — o áudio real já foi entregue ao cliente nesse ponto, uma falha de transcrição não pode virar erro 502 pro operador. Reusa `getAi`, `formatKnowledgeBaseForPrompt`, `getKnowledgeBase` já importados no arquivo (nenhum import novo).

**Testes novos:** `server/routes/__tests__/conversationsSendMediaAudioTranscription.test.ts` (4 testes) — sucesso grava a transcrição real; falha/fallback do Gemini grava o texto de fallback combinado; exceção na chamada de transcrição não derruba a resposta 200 nem o placeholder original quando a transcrição não resolve; imagem (não-áudio) nunca chama transcrição.

**Validação:** `npm run lint` limpo; `npx vitest run` — 217 arquivos / 1096 testes aprovados; `npm run build` limpo.

**Pendente ou risco:** o mesmo gap estrutural existe pra IMAGEM enviada (placeholder de legenda nunca vira "real"), fora de escopo aqui — o dono do produto só reportou áudio. Nenhuma migration nem mudança de schema.
