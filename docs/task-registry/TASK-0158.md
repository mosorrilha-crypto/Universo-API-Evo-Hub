# TASK-0158 — Refatora altura do frame de Atendimento pra flexbox real (elimina chute de dvh/porcentagem que causava sobra/falta de espaço no mobile)

- **Iniciado em:** 2026-08-29T16:59:05.639Z
- **Agente/plataforma:** Claude
- **Issue central:** [#290](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/290)
- **Status:** concluído

## Objetivo

Refatora altura do frame de Atendimento pra flexbox real (elimina chute de dvh/porcentagem que causava sobra/falta de espaço no mobile)

## Atualizações

Feedback real do dono do produto: duas telas (lista de conversas e
thread aberta), sem texto — só a observação de que "ainda tem um
espaço embaixo nas duas telas" depois da TASK-0157 (que ainda tinha
tentado acertar com um valor fixo `100dvh`/`82dvh`).

Essa é a **quarta tentativa** de acertar a altura do frame de
Atendimento no mobile (TASK-0150 escondeu cabeçalhos, TASK-0153/0155
mexeram no rodapé, TASK-0157 tentou `82dvh`→`100dvh`) — todas usando
valores de `dvh`/`%` chutados a partir de estimativa de quanto
"chrome" (cabeçalho global + cabeçalho do Atendimento + barra inferior)
está visível em cada estado. Sempre sobrava ou faltava um pouco,
porque o chute nunca batia exatamente com a altura real desses
elementos no dispositivo real.

Desta vez, em vez de tentar um quinto chute, troquei a abordagem:
**flexbox de verdade**, sem nenhum valor de altura adivinhado.
- `App.tsx`: o wrapper da aba Atendimento (antes só um `<div
  style={{display}}>`) virou `flex flex-col h-[calc(100dvh-1.5rem)]
  sm:h-[calc(100dvh-3rem)] lg:block lg:h-auto` — a única conta manual
  que sobra é cancelar o padding vertical do `<main>` (`.app-main`,
  `p-3`/`sm:p-6`), que é um valor fixo e conhecido, não uma estimativa
  de UI.
- `index.css`: `.atendimento-workspace` ganhou `height:100%;
  min-height:0` e `.atendimento-workspace__content` ganhou `flex:1 1
  auto; min-height:0` — a coluna de conteúdo agora ocupa
  automaticamente o que sobrar depois do cabeçalho (quando ele
  aparece), em vez de uma fração fixa da tela.
- `WhatsAppLeadsSim.tsx`: `.atendimento-chat-shell` trocou
  `h-[82dvh]`/`h-[100dvh]` (condicional a `mobileThreadOpen`) por só
  `h-full` — ocupa 100% do que `.atendimento-workspace__content` já
  calculou como espaço disponível, sem precisar saber nada sobre
  cabeçalho/barra inferior.

**Verificação real desta vez** (não só leitura de código): montei um
HTML estático fora do app usando o CSS de produção gerado pelo
`npm run build` (`dist/assets/index-*.css`), reproduzindo a árvore de
elementos e classes reais (wrapper → `.atendimento-workspace` →
`.atendimento-workspace__content` → `.atendimento-chat-shell` →
colunas), e rodei no Chromium (via Playwright, headless) num viewport
mobile (412×915) nos dois estados — lista de conversas (cabeçalho
visível) e thread aberta (cabeçalho escondido). Em ambos,
`document.documentElement.scrollHeight` bateu exatamente com
`window.innerHeight` (915px, sem sobra nem falta), e a captura de tela
confirma visualmente a barra inferior/rodapé de composição encostados
no fim da tela nos dois casos. Isso não substitui testar no app real
autenticado (ainda não é possível no sandbox), mas testa a mesma
lógica de CSS/layout que causava o bug, com o CSS que realmente vai
pro ar.

Entregue: `App.tsx`, `WhatsAppLeadsSim.tsx`, `index.css`.

## Encerramento

**Status: concluído.** Não toca autenticação/pagamento/isolamento de
tenant — é ajuste de CSS/layout. Self-merge autorizado. Validação:
`npm run lint`, `npx vitest run` (225 arquivos, 1166 testes) e
`npm run build`, todos limpos, mais a verificação visual descrita acima
(Playwright headless contra o CSS real de build, ambos os estados sem
gap/overflow).

**Pendente ou risco:** a verificação foi contra uma reprodução estática
da árvore de elementos/CSS real, não o app autenticado rodando de
verdade (sandbox sem credenciais Supabase). Ainda recomendo conferência
visual pós-deploy, mas com confiança bem maior que nas três tentativas
anteriores — desta vez não há nenhum valor de altura chutado que possa
estar errado para um device específico; a única conta manual (padding
do `.app-main`) é um valor de CSS fixo, não uma estimativa de UI.
