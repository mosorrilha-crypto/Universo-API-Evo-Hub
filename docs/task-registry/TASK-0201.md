## Objetivo

Corrige log injection e use of externally-controlled format string (CodeQL) em massa: ~25 pontos de codigo em 12 arquivos

## Contexto

5º e último PR da varredura dos 52 alertas de CodeQL Code scanning (ver
TASK-0197/0198/0199/0200). Cobre as duas categorias que, juntas, eram a
maioria dos alertas: "Use of externally-controlled format string" (High,
13 alertas) e "Log injection" (Medium, ~27 alertas) — as duas apontam pra
praticamente os mesmos ~25 pontos de código (mesma linha, duas regras
diferentes), então um fix por linha fecha os dois alertas ali.

## Causa raiz e padrão de correção

Mesma causa em todo lugar: dado potencialmente controlado externamente
(parâmetro de rota, corpo de webhook, resposta de API externa, mensagem de
erro) interpolado direto dentro do 1º argumento (o "formato") de
`console.log`/`console.warn`/`console.error`, seja via template literal
(`` `texto ${valor}` ``) ou via placeholders `%s` — em ambos os casos, um
caractere de controle (quebra de linha) no valor permitiria forjar uma
linha de log falsa.

Padrão de fix já confirmado como eficaz em uma PR anterior
(`googleSheetsSync.ts`, TASK anterior): 1º argumento vira uma string
**totalmente estática** (sem nenhuma interpolação), e todo dado variável
vai num **objeto** como 2º argumento — `console.warn('texto fixo:', {
campo1, campo2 })`. Isso também é estruturalmente mais forte que a
alternativa já usada antes neste repo (`encodeURIComponent` + `%s`, ver
comentário removido de `sanitizeForLog` em `conversations.ts` — TASK-0152):
mesmo que uma dessas duas abordagens já tivesse funcionado numa rodada
anterior, `conversations.ts:479` (que já usava `%s` + `sanitizeForLog`)
ainda aparecia como alerta aberto no levantamento atual, então padronizei
tudo pro padrão de objeto.

## Teste ajustado

`server/routes/__tests__/webhooksStatusLogging.test.ts` verificava o
conteúdo do log fazendo `warnSpy.mock.calls.map(c => c.join(' '))` — como
os argumentos agora incluem um objeto (não mais só strings), `.join()`
virava `[object Object]` e o teste passou a falhar. Corrigido pra
serializar argumentos não-string com `JSON.stringify` antes de juntar —
ajuste de infraestrutura do teste, não um enfraquecimento da asserção (o
teste continua verificando que `wamid.TESTE123` e `failed` aparecem no log
efetivamente emitido).
