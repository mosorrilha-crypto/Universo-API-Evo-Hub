## Objetivo

Auto-retry no painel para imagem de lead que ainda não terminou de salvar (RealClientImage)

## Atualizações

Continuação direta do "fotos ainda não carregam" (TASK-0392, TASK-0398) — o dono do produto desconectou o próprio número (TASK-0397) e mandou duas fotos de teste reais pro número da Monique; ambas continuaram "Imagem indisponível (HTTP 404)" no celular mesmo depois de clicar "Tentar novamente".

Investigação (Render logs + Supabase, produção): nenhum download de imagem gerou erro no servidor (nem no primeiro download, nem em nenhuma tentativa do retry da TASK-0398); áudios do mesmo tenant/período foram baixados e transcritos com sucesso (mesmo pipeline R2); a checagem de tenant do endpoint `/api/media` não é o problema (a mensagem já aparecia certinho na conversa). O dono do produto então confirmou, com um print do desktop, que **a mesma imagem abre normalmente lá** — ou seja, o arquivo está salvo corretamente no R2; o problema nunca foi perda de dado.

**Causa raiz real:** `RealClientImage` (`WhatsAppLeadsSim.tsx`) busca a mídia via `GET /api/media/:messageId` **uma única vez**, no instante em que a mensagem aparece na conversa (quase imediato, via SSE) — enquanto o download real (Evolution/Meta → R2, TASK-0398) roda em paralelo e pode levar mais alguns segundos. O botão manual "Tentar novamente" (TASK-0392) cobria isso, mas dependia do operador esperar o tempo certo antes de clicar — no celular, testando ativamente, esse tempo normalmente não é suficiente.

**Mudança:** `RealClientImage` agora tenta de novo **sozinho** antes de mostrar qualquer estado de falha — até 4 tentativas automáticas espaçadas (2s, 4s, 8s, 15s — ~29s no total, cobrindo folgadamente o tempo real de download+upload observado), reaproveitando o mesmo `retryToken` que já disparava o botão manual. Durante essas tentativas automáticas o operador só vê "Carregando imagem..." (nunca "Imagem indisponível"); o botão manual só aparece — como já acontecia — se mesmo depois de esgotar as tentativas automáticas ainda falhar (atraso maior que ~29s, ou falha real).

**Arquivos:** `src/components/WhatsAppLeadsSim.tsx` (`RealClientImage`), `src/components/__tests__/WhatsAppLeadsSim.mediaLoadFailure.test.tsx` (reescrito: cobre recuperação automática sem clique nenhum, e confirma que uma falha persistente continua tentando em silêncio em vez de mostrar o erro já na 1ª tentativa).

**Validação:** `npm run lint` (tsc --noEmit) limpo; `npx vitest run` — 303 arquivos / 1735 testes passando; `npm run build` sem erros. Nenhuma alteração de backend nesta tarefa (a causa raiz era 100% de timing no frontend).

**Pendente ou risco:** nenhum risco técnico novo — o componente já tinha exatamente esse mecanismo de retry manual; isto só automatiza as primeiras tentativas antes de expor qualquer estado de falha ao operador. Se uma imagem específica demorar mais que ~29s pra ficar disponível (ex.: Evolution API muito lenta), o botão manual continua existindo como antes. Fechamento do arco "fotos não carregam" desta sessão (TASK-0392 → TASK-0397 → TASK-0398 → TASK-0401).
