## Objetivo

Ficha IA: usa modelo Groq mais forte (llama-3.3-70b-versatile) nos 4 endpoints de análise/resposta, reduzindo falha de validação de JSON durante o incidente de créditos Gemini

## Atualizações

**Contexto:** durante o mesmo incidente ativo (créditos Gemini esgotados)
das TASK-0346/0348, o dono do produto mandou um print real mostrando a
Ficha IA de um operador travada: botão "Criar resposta para revisão"
retornando "Não foi possível gerar a resposta agora (Gemini
indisponível)". Investigando, confirmei que `server/routes/ai.ts` já tem
Groq→Gemini como fallback nos 4 endpoints (`analyze-conversation`,
`reply-from-hint`, `ai/ask`, `analytics/ai-report`) desde 19/08/2026 —
mais antigo que esta sessão. Mas os logs de produção mostraram o Groq
FALHANDO também nesse exato horário: `"Groq falhou
(analyze-conversation), caindo pro Gemini: Groq respondeu 400: Failed to
validate JSON..."`. Ou seja: os dois provedores falharam na mesma
mensagem — Gemini por falta de crédito (causa raiz do incidente maior),
Groq por uma falha de validação de JSON no próprio Groq.

**Causa provável do Groq falhar:** os 4 endpoints usavam o modelo default
de `callGroqJsonCompletion` (`openai/gpt-oss-20b`), dimensionado
originalmente só pro roteador do `autoReply.ts` (classificação curta,
enum de poucas palavras). `analyze-conversation` em particular pede um
schema JSON bem mais complexo (objeto aninhado `extractedCRMData`, vários
campos de texto livre) — mais chance do modelo mais fraco falhar a
validação de JSON que o próprio Groq faz sobre a saída do modelo.

**Implementado:** os 4 endpoints de `server/routes/ai.ts` agora passam
`GROQ_SPECIALIST_MODEL` (`llama-3.3-70b-versatile`) e
`GROQ_SPECIALIST_TIMEOUT_MS` (12s) — as mesmas constantes já criadas na
TASK-0346 pra resposta do especialista do agente principal — em vez do
modelo/timeout default de `callGroqJsonCompletion`. Reduz a chance da 1ª
tentativa (Groq) falhar, sem mudar a rede de segurança já existente
(cai pro Gemini, e se este também falhar, cai pro fallback anti-fabricação
que já existia em cada endpoint — nunca inventa análise/resposta/relatório).

**Testes novos:** `server/routes/__tests__/aiGroqModelUpgrade.test.ts` (4
casos) — confirma que os 4 endpoints realmente pedem
`GROQ_SPECIALIST_MODEL` ao Groq (mock de `global.fetch` distinguindo pela
URL, já que o próprio teste também fala HTTP com o servidor Express local).

**Validação:** `npm run lint` (`tsc --noEmit`), `npx vitest run` (279
arquivos / 1531 testes, suíte completa) e `npm run build` — todos limpos.
Os testes pré-existentes desses 4 endpoints não passam `groqApiKey` na
config, então nunca exercitam o branch Groq — confirmado que continuam
passando sem alteração (mudança é aditiva/paramétrica, não estrutural).

**Pendente ou risco:**
- Não elimina 100% a chance de falha do Groq (nenhum modelo garante JSON
  válido sempre) — só reduz a taxa, trocando por um modelo mais capaz.
  Vale monitorar os logs (`⚠️  [Ficha IA] Groq falhou`) nos próximos dias
  pra confirmar se a frequência caiu de verdade.
- Mesmo pré-requisito das tarefas anteriores: precisa de `GROQ_API_KEY`
  configurada em produção — já confirmado ativo (ver relato na #504 das
  TASK-0346/0348).
- Transcrição de áudio (`/api/transcribe`, `geminiTranscription.ts`) NÃO
  tem Groq nenhum ainda — só Gemini, com fallback que nunca inventa texto
  mas também não transcreve nada quando Gemini está fora. Discutido com o
  dono do produto como próxima extensão possível (Groq tem Whisper), mas
  não iniciado nesta tarefa.
