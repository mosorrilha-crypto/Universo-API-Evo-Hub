## Objetivo

Adiciona pairing code (conectar por numero) como alternativa ao QR Code na conexao Evolution API

## Atualizações

**Contexto:** durante o onboarding do tenant "Dr. Daniel" (fisioterapeuta,
Bonito/MS), o dono do produto perguntou se dava pra conectar o WhatsApp
Business sem escanear QR Code. A Evolution API (Baileys por trás) já suporta
isso nativamente: passando um `number` na criação/reconexão da instância, ela
devolve um `pairingCode` (código curto) em vez de/junto com o QR — o usuário
digita esse código em WhatsApp > Aparelhos conectados > Conectar com número
de telefone. O código já existente (`server/routes/admin.ts`) nunca
repassava esse parâmetro.

**Implementado (opção alternativa ao QR, mantendo o fluxo de QR intacto —
decisão confirmada via AskUserQuestion):**
- `server/routes/admin.ts`:
  - Novo helper `normalizePairingPhoneNumber(value)` — remove tudo que não é
    dígito, exige 8–15 dígitos (faixa E.164); ausente/vazio devolve
    `undefined` (fluxo de QR normal); qualquer outra coisa lança erro
    explícito (mapeado pras rotas como 400) em vez de mandar lixo pra
    Evolution API.
  - `createFreshInstance`/`reconnectExistingInstance` ganham um parâmetro
    opcional `phoneNumber` — quando presente, vai no corpo do
    `POST /instance/create` (campo `number`) ou na query string do
    `GET /instance/connect/:instance?number=...`; a resposta passa a também
    extrair `pairingCode` (`data.pairingCode || data.qrcode.pairingCode`),
    devolvido junto do `qrCodeBase64` (um dos dois vem preenchido,
    dependendo se `number` foi passado).
  - As três rotas (`POST .../evolution-instance`, `GET .../qrcode`,
    `POST .../recreate`) leem `number` do body (POST) ou da query (GET),
    validam com o helper (400 se inválido) e repassam pras funções acima.
  - Removida a duplicação que existia no branch de "criar instância nova"
    de `POST .../evolution-instance` (reimplementava a mesma lógica de
    `createFreshInstance` em vez de chamá-la) — sem isso, o suporte a
    `number` teria que ser escrito duas vezes.
- `src/components/ReconectarWhatsAppQrCode.tsx` — novo estado
  `pairingCode`/`phoneInput`/`useCode`; um link "Sem câmera à mão? Conectar
  digitando o número" alterna pra um campo de telefone + botão "Gerar
  código", mostrando o pairing code em destaque com a instrução de onde
  digitá-lo no celular. QR Code continua sendo o padrão (opção não
  substitui, só complementa — decisão confirmada com o dono do produto).
- **Rebase**: TASK-0371 (concorrente, também neste arquivo — adiciona prop
  `alreadyConnected`) mergeou em `main` durante esta tarefa; rebaseado sem
  conflitos, ambas as mudanças convivem no componente.

**Testes novos** (`adminEvolutionInstance.test.ts`, describe "pairing code"):
número normalizado e repassado no `POST /instance/create`; `number` na
query do `GET .../qrcode` repassado pro `/instance/connect`; comportamento
de QR normal inalterado quando `number` não é passado; 400 em ambas as
rotas (POST/GET) para número inválido, sem chegar a chamar a Evolution API
no caso do GET.

**Validação:** `npm run lint` (limpo), `npx vitest run` (290 arquivos /
1618 testes, todos passando — 34/34 no arquivo de Evolution, incluindo os
6 casos novos), `npm run build` (limpo).

**Pendente ou risco:**
- Não testado contra uma instância Evolution real — depende de como a
  versão específica do servidor self-hosted formata a resposta do pairing
  code; o parsing (`data.pairingCode || data.qrcode.pairingCode`) segue o
  mesmo padrão de "melhor esforço" já usado pro QR (`data.base64 ||
  data.qrcode.base64`), mas vale confirmar no primeiro uso real.
- Sem dispositivo/navegador real nesta sessão pra validar visualmente o
  toggle novo no modal — pedir confirmação visual do dono do produto antes
  de considerar a UI 100% ajustada.
