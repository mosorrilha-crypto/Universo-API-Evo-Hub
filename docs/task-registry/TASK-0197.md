# TASK-0197 — Corrige SSRF (Critical) no fluxo Evolution API: valida api_url lido do banco contra o valor configurado antes de qualquer fetch

## Objetivo

Corrige SSRF (Critical) no fluxo Evolution API: valida api_url lido do banco contra o valor configurado antes de qualquer fetch

## Contexto

Primeiro de uma sequência de PRs pra zerar os 52 alertas abertos de CodeQL
Code scanning (`Security → Code scanning`, `is:open branch:main`) — pedido
direto do usuário depois de revisar prints da aba Security. Este cobre o
único alerta **Critical**: "Server-side request forgery" em
`server/services/evolutionSend.ts:221` (dentro de `setEvolutionWebhook`).

## Investigação

`apiUrl` nas funções de `evolutionSend.ts` normalmente chega vindo de
`tenant_evolution_credentials.api_url` (lido do banco em `admin.ts`) — o
CodeQL trata isso como potencialmente externally-controlled por análise
estática, já que nada garante em tempo de compilação que só um caminho
grava ali. Investigação real (`git grep` em `admin.ts`) confirma: hoje só
`evolutionApiUrl` (env `EVOLUTION_API_URL`) é gravado nessa coluna — nunca
vem de body de request. E o `instanceName` que ALGUMAS vezes vem de
`req.body.instanceName` já é sanitizado antes de qualquer fetch
(`.replace(/[^a-z0-9-]/g, '-')`, `server/routes/admin.ts` ~linha 644) — não
dá pra usá-lo pra escapar do path e trocar host/protocolo.

**Tentativa descartada:** cheguei a implementar `assertTrustedEvolutionApiUrl`
comparando `cred.api_url` contra o `evolutionApiUrl` (env) atual antes de
qualquer fetch — quebrou um teste real
(`adminEvolutionInstance.test.ts`, "sem EVOLUTION_API_URL/KEY globais
configurados, 404 no connect não tenta se autocurar"): reconectar/consultar
status de uma instância já provisionada é uma operação legítima mesmo com
`EVOLUTION_API_URL`/`KEY` ausentes neste servidor (essas envs só importam
pra *provisionar instância nova*). Revertido pra uma checagem estrutural
(URL bem-formada + protocolo `http`/`https`), que não depende do valor
atual do env.

## Correção

- `server/services/evolutionSend.ts`: extrai `assertValidApiUrl(apiUrl)`
  (URL bem-formada via `new URL()`, protocolo restrito a `http:`/`https:`)
  e chama em `requireCredentials` (usado por todas as funções exportadas
  exceto `showEvolutionTyping`) e diretamente em `showEvolutionTyping`
  (que tem sua própria checagem de presença, sem passar por
  `requireCredentials`).
- `server/routes/admin.ts`: mesma checagem estrutural (`assertValidHttpUrl`)
  aplicada logo após cada leitura de `cred`/`existingCred` do banco (4
  pontos: `evolution-instance` POST, `.../qrcode` GET, `.../status` GET,
  `.../recreate` POST), antes de qualquer fetch que use `cred.api_url`.

Isso bloqueia um SSRF de verdade (`javascript:`, `file:`, string malformada,
etc.) sem quebrar o caso legítimo de reconectar/consultar uma credencial já
salva mesmo com o env global ausente/diferente.
