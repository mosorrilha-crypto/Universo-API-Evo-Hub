## Objetivo

Adiciona restricao preventiva de horario no prompt do especialista (agendamento)

## Atualizações

Pedido direto do dono do produto: aplicar o item #1 de maior prioridade de uma pesquisa comparativa
feita nesta sessão contra dois projetos open source do mesmo domínio (recepcionista de WhatsApp com
agendamento real no Google Calendar) — o achado era que o anti-alucinação de horário do Universo é
**reativo** (gera resposta livre, corrige depois se citar horário errado), enquanto o padrão mais
maduro observado (`martin-minghetti/whatsapp-ai-receptionist`) é **preventivo** (nunca deixa o
modelo calcular data, injeta os horários já prontos como contexto fechado).

- `server/services/autoReply.ts` (`generateAutoReplyForText`, dentro do bloco que chama
  `runAgendamentoTools`): quando uma ferramenta de agenda confirma horário(s) de verdade nesta
  mensagem (`result.actionsSummary.length && confirmedTimes.length`), empurra uma nova entrada em
  `contextParts` — uma restrição imperativa e inequívoca ("RESTRIÇÃO OBRIGATÓRIA DE HORÁRIO: os
  únicos horários que você pode citar... são exatamente estes...") com a lista deduplicada e
  ordenada de `confirmedTimes`, separada da narrativa solta que já existia em `actionsSummary`.
- **O gate reativo (Epic 4.5.7, `extractCitedTimes`/`confirmedTimes` comparados DEPOIS da geração)
  não foi alterado nem removido** — continua exatamente como estava, como rede de segurança pros
  casos em que o modelo ignore a restrição preventiva mesmo assim. Isso é uma camada adicional
  (defesa em profundidade), não uma substituição.
- **Escopo intencionalmente restrito**: só entra quando uma ferramenta rodou de verdade nesta
  mensagem (`result.actionsSummary.length > 0`), nunca só por existir um agendamento antigo
  (`confirmedTimesFromExisting`, ver `runAgendamentoTools`). Achado ao rodar a suíte completa:
  sem essa restrição de escopo, o teste `autoReplyPaymentVerification.test.ts` ("sem
  payment_status, não menciona nada sobre pagamento") quebrava — "quero remarcar" sem novo
  horário ainda recebia a restrição dizendo pra só citar o horário ANTIGO, o que atrapalharia o
  especialista de simplesmente perguntar a nova data/hora desejada num fluxo real de remarcação.
- Teste novo: `server/services/__tests__/autoReplyPreventiveTimeConstraint.test.ts` — 2 casos
  (a restrição aparece no prompt do especialista quando uma ferramenta confirma horário; não
  aparece quando nenhuma ferramenta roda por falta de dado).
- Validado com `npm run lint` (limpo), `npx vitest run` (896 testes, 174 arquivos, todos verdes —
  incluindo os 4 arquivos de teste de anti-alucinação/duração já existentes, intactos), `npm run
  build` (limpo).

**Pendente ou risco:** nenhum conhecido. Efeito real (se a restrição de fato reduz a taxa de
alucinação em produção) só é observável com tráfego real do tenant Monique — sem telemetria hoje
que meça "quantas vezes o gate reativo disparou por semana" pra comparar antes/depois (gap de
observabilidade já registrado na pesquisa comparativa desta sessão).
