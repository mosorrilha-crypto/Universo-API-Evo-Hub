# TASK-0338 — corrige menu inferior sobrepondo tela ao abrir Agenda/Ferramentas no mobile

## Objetivo

corrige menu inferior sobrepondo tela ao abrir Agenda/Ferramentas no mobile

## Atualizações

Pedido direto do dono do produto, com 2 prints reais do celular (a barra inferior "Conversas/Pendências/Agenda/Ferramentas" flutuando/sobrepondo a tela ao abrir "Agenda", e a gaveta "Ferramentas" com a barra reaparecendo por baixo do próprio conteúdo dela).

**Contexto:** este mesmo sintoma já tinha sido atacado duas vezes na sessão anterior — TASK-0336 (trocou o valor chutado `4.75rem` reservado pro nav nos overlays por uma medida real via `ResizeObserver`) e TASK-0337 (trocou `100vh`/`100dvh` por medição real via `window.visualViewport`) — mas os dois ficaram registrados como "concluído, aguardando confirmação visual real", e o print desta sessão confirma que o problema persistia.

**Causa raiz real (achado desta sessão, via agente de investigação dedicado):** nenhuma das duas tentativas anteriores tocava no problema de verdade. `.atendimento-conversations` (`WhatsAppLeadsSim.tsx`, div raiz que envolve as 3 colunas do Atendimento E os overlays fixos de Agenda/Ferramentas, já que eles são renderizados como filhos dela antes do fechamento do componente) tinha a classe `animate-page-enter` (`index.css`), que roda a animação `page-enter` com `animation: ... 260ms ... both`. O fill-mode `both` faz o navegador manter pra sempre o `transform: translateY(0)` do frame final da animação — e pela spec do CSS, QUALQUER `transform` diferente de `none` (mesmo um "idêntico", 0px) transforma aquele elemento no *containing block* dos seus descendentes `position: fixed`, em vez do viewport real da página.

A gaveta "Ferramentas" (`fixed inset-x-0 top-0 bottom-[...]`) e o `UpcomingEventsPanel` da Agenda (`calendar/UpcomingEventsPanel.tsx`, mesmo padrão `fixed inset-x-0 top-0 bottom-[...] sm:inset-0`) são os dois descendentes afetados: em vez de se posicionarem contra a tela real do celular, eles passavam a se posicionar contra a caixa do `.atendimento-conversations` — cuja altura/posição não bate com o viewport verdadeiro. Por isso NENHUM ajuste de `dvh`/`visualViewport`/altura medida do nav (TASK-0336/0337) resolvia: o cálculo de altura estava certo, mas o "viewport" contra o qual os overlays se posicionavam nunca foi o viewport de verdade.

**Correção:** removida a classe `animate-page-enter` de `.atendimento-conversations` (`WhatsAppLeadsSim.tsx`) — não havia nenhum outro ancestral entre ela e o `<body>` com transform/animação equivalente (conferido em `App.tsx`). A entrada suave (fade+slide de 260ms) da lista de conversas ao montar deixa de existir, troca aceitável pelo bug real que causava.

**Sobre o "toque profissional de organização" pedido junto:** a reorganização visual da gaveta "Ferramentas" (ícones únicos expansíveis em vez de fileiras de texto, grade de ícones pra Configurações) já foi feita a fundo na TASK-0336 (concluída ontem, 07/09/2026) a pedido do mesmo dono do produto — não repetida aqui pra não arriscar reverter/duplicar aquele trabalho ainda não confirmado visualmente. Recomendo validar a reorganização da TASK-0336 no mesmo teste visual desta correção.

**Arquivos:** `src/components/WhatsAppLeadsSim.tsx`.

**Validação:** `npm run lint` limpo; `npx vitest run` — 276 arquivos / 1511 testes, todos passando; `npm run build` limpo. Sem teste unitário dedicado (é remoção de uma classe CSS de animação, sem lógica nova) — os testes existentes de `WhatsAppLeadsSim` (incluindo os que já cobrem a gaveta Ferramentas/Agenda) continuam passando.
