## Objetivo

dispara o Meta Pixel do catalogo publico antes do fetch pesado do catalogo, pra reduzir gap entre clique e visualizacao de pagina

## Atualizações

**Contexto:** achado real (28/08/2026, checagem de anúncios): a campanha "Catálogo — Tráfego Site (Luque)" tinha custo de R$3,04 por "Visualização da página de destino" (evento `PageView` do Meta Pixel) no mesmo dia em que teve 20 cliques reais no link — só 5 desses cliques viraram `PageView` confirmado. Investigando o código: `PublicCatalogPage.tsx` só carregava o Pixel dentro de um `useEffect` disparado por `catalog?.pixelId`, e esse campo só existe depois que `GET /api/public/catalog/:slug` responde por completo — e essa rota, em `publicCatalogStore.ts::getPublicCatalogBySlug`, comprime uma miniatura de imagem por produto/variante antes de responder (`buildCatalogThumbnail`), o que pode levar segundos numa conexão ruim. Quem clicava no anúncio e saía da página antes desse payload inteiro voltar nunca disparava `PageView`, mesmo tendo chegado na página de verdade.

**Implementado:**
- `server/services/publicCatalogStore.ts`: nova função `getPublicCatalogPixelId(slug)` — consulta mínima (só `tenants.public_catalog_enabled` + `tenant_meta_credentials.capi_dataset_id`), sem tocar em produtos/imagens.
- `server/routes/publicCatalog.ts`: nova rota `GET /api/public/catalog/:slug/pixel-id`, mesmo rate limiter das outras rotas públicas do catálogo, 404 se o tenant não existe/não tem catálogo habilitado/não tem Pixel configurado.
- `src/components/PublicCatalogPage.tsx`: novo `useEffect` que dispara esse fetch leve assim que a página monta, em paralelo com (não bloqueado por) o fetch pesado do catálogo completo, e chama `loadMetaPixel` assim que o `pixelId` chega — normalmente bem mais rápido que esperar o catálogo inteiro. `loadMetaPixel` ganhou uma trava (`pixelPageViewTrackedFor`) contra disparar o evento `PageView` duas vezes, já que agora dois caminhos podem chamar a função (o fetch rápido novo e o fetch completo antigo, mantido como fallback caso o rápido falhe por algum motivo).

**Arquivos:** `server/services/publicCatalogStore.ts`, `server/routes/publicCatalog.ts`, `src/components/PublicCatalogPage.tsx`, `server/routes/__tests__/publicCatalog.test.ts` (3 testes novos: retorna só `pixelId`, 404 sem Pixel configurado, 404 pra slug sem catálogo/inexistente).

**Validação:** `npm run lint` limpo. `npx vitest run` — 223 arquivos / 1157 testes, todos verdes (incluindo os 3 novos). `npm run build` limpo (vite + esbuild). Não depende de migration — usa tabelas já existentes.

**Pendente ou risco:** o efeito real (quantas visualizações de página passam a ser contadas) só é observável depois do deploy, com dados novos da campanha nos próximos dias — não dá pra validar localmente. Continuo acompanhando `cost_per_action_type_landing_page_view` na próxima checagem de anúncios pra confirmar se a lacuna diminuiu.
