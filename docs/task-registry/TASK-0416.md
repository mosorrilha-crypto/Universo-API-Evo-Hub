## Objetivo

Corrige a interação entre firstContactBlocks e o modo somente leads: rede de segurança de 1ª mensagem passa a se basear em specialistInvokedBefore, não em history vazio

## Atualizações

**Achado** (durante auditoria pedida pelo usuário no prompt real do tenant Dr. Daniel Oliveira, mesma sessão da TASK-0415): a rede de segurança "1ª mensagem sempre responde" do modo `leads_only` (TASK-0411/0412) usava `isFirstMessage = !history || history.length === 0`. Isso nunca é verdade na 1ª vez que `generateSpecialistReply` roda de verdade quando o tenant tem uma Mensagem de Primeiro Contato fixa configurada (`firstContactBlocks`, nunca gerada pela IA — `webhooks.ts` intercepta a 1ª mensagem do lead com `history?.length === 0 && hasFirstContactMessage(kb)` e responde com o bloco fixo SEM chamar o especialista) — Daniel tem esse recurso configurado. Na 2ª mensagem real do cliente (a 1ª vez que o especialista roda de fato), `history` já tem 2+ entradas (a msg do cliente + a saudação fixa), então `isFirstMessage` já vinha `false` — a trava de código nunca protegia ninguém nesse tenant, restando só a instrução de prompt (mais fraca, exatamente o que a trava de código foi criada pra substituir). O mesmo vale pra qualquer conversa em que um operador escreveu antes de qualquer lead.

**Correção**: nova coluna `conversations.specialist_invoked_at` (migration 0091, aplicada via `mcp__Supabase__apply_migration`) + `conversationStore.markSpecialistInvoked`/`StoredConversation.specialistInvokedAt` (mesmo padrão idempotente de `markAdGreetingMatched`). `generateSpecialistReply`/`generateAutoReplyForText` ganham o parâmetro `specialistInvokedBefore` — quando informado (`true`/`false`), substitui inteiramente o cálculo antigo por `history.length`; `undefined` (chamador não migrado) cai no comportamento antigo, mais conservador. `webhooks.ts` e `transcriptionQueue.ts` (os 2 pontos reais de invocação — texto e áudio transcrito) calculam `specialistInvokedBefore = !!conversation?.specialistInvokedAt` antes de chamar e marcam `markSpecialistInvoked` logo depois, independente do resultado.

**Escopo**: correção de plataforma, não específica do Daniel — qualquer tenant que combine `firstContactBlocks` + `leads_only` (ou tenha um operador escrevendo antes do 1º lead) se beneficia. Nenhuma mudança de comportamento pra tenants sem essas combinações (o fallback pra `undefined` preserva o cálculo antigo, e mesmo com o novo cálculo o resultado coincide pro caso comum de conversa nova sem nada configurado).

**Testes novos**: `conversationStoreSpecialistInvoked.test.ts` (idempotência, isolamento por tenant) + 2 casos em `autoReply.test.ts` reproduzindo o cenário exato (histórico não vazio simulando só a saudação fixa já enviada, `specialistInvokedBefore=false` → rede de segurança ainda protege; `specialistInvokedBefore=true` → outOfScope aceito normalmente).

**Verificação**: `npm run lint` / `npx vitest run` (309 arquivos, 1780 testes) / `npm run build` — todos limpos.
