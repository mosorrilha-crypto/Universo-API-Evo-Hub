# TASK-0037 — corrigir dados antigos após troca de tenant

## Objetivo

Quando um `saas_admin` troca de empresa, a faixa ativa muda para o tenant escolhido, mas a fila e o histórico podem continuar exibindo conversas da empresa anterior. A correção deve descartar respostas assíncronas antigas, limpar o estado imediatamente, recarregar somente os dados do tenant novo e manter o override usado pelo backend.

## Causa identificada

Foram encontrados dois problemas distintos. No frontend, `WhatsAppLeadsSim` permanecia montado entre mudanças e uma resposta assíncrona da fila ou do histórico iniciada no tenant anterior podia executar `setLeads` depois da troca. No backend, o ID real do Clic (`11111111-1111-1111-1111-111111111111`) tem formato UUID aceito pelo Postgres, mas não segue a variante RFC 4122 tradicional. O padrão excessivamente restritivo rejeitava o header `X-Tenant-Id` e fazia o servidor cair silenciosamente no tenant do JWT, Monique. Por isso a faixa mostrava Clic enquanto a API entregava 190 conversas da Monique.

A distribuição do banco foi conferida somente para diagnóstico: Clic possui 58 conversas e Monique possui 190. O endpoint com um UUID inexistente retorna zero, comprovando que o filtro existe; o erro específico era a rejeição do UUID legado do Clic.

## Implementação

- A Central remonta `WhatsAppLeadsSim` com `key={activeTenant.id}`, zerando seleção, histórico e estados transitórios quando o tenant muda.
- Cada request de fila e histórico captura o tenant em que começou e verifica o tenant atual antes de aplicar qualquer resposta, erro ou atualização de mensagens.
- O fetch da fila valida cancelamento novamente depois de `response.json()`, impedindo que uma resposta atrasada do tenant anterior repovoe a lista.
- O padrão de validação no cliente e no servidor passou a aceitar o formato UUID canônico completo sem restringir versão/variante RFC 4122; IDs fictícios como `tenant_004` continuam rejeitados.
- O callback de troca, o `X-Tenant-Id`, a persistência do override e as regras de `saas_admin` foram mantidos; nenhum endpoint, token, `tenant_id` ou regra de isolamento foi alterado.

## Validação

`git diff --check`, `npm run lint`, `npm test` — **168 arquivos / 867 testes aprovados** — e `npm run build` foram concluídos. Foram adicionados testes para o UUID legado do Clic, para a rejeição de IDs fictícios e para a restrição do override a `saas_admin`.

Após a publicação, será conferido no bundle e na API pública que a consulta com `X-Tenant-Id` do Clic retorna o conjunto tenant-scoped, diferente das 190 conversas da Monique.
