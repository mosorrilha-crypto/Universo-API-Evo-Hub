# TASK-0037 — corrigir dados antigos após troca de tenant

## Objetivo

Quando um `saas_admin` troca de empresa, a faixa ativa muda para o tenant escolhido, mas a fila e o histórico podem continuar exibindo conversas da empresa anterior. A correção deve descartar respostas assíncronas antigas, limpar o estado imediatamente, recarregar somente os dados do tenant novo e manter o override usado pelo backend.

## Causa identificada

O componente `WhatsAppLeadsSim` permanecia montado entre mudanças de empresa. Uma resposta de `GET /api/conversations?archived=true` ou de um histórico iniciado no tenant anterior podia terminar depois da troca e executar `setLeads`, repovoando a lista nova com dados antigos. O primeiro guard existente verificava cancelamento somente antes de ler o JSON, deixando uma janela de corrida durante a resposta assíncrona.

## Implementação

- A Central agora remonta `WhatsAppLeadsSim` com `key={activeTenant.id}`, zerando seleção, histórico e estados transitórios quando o tenant muda.
- Cada request de fila e histórico captura o tenant em que começou e verifica o tenant atual antes de aplicar qualquer resposta, erro ou atualização de mensagens.
- O fetch da fila valida cancelamento novamente depois de `response.json()`, impedindo que uma resposta atrasada do tenant anterior repovoe a lista.
- O callback de troca, o `X-Tenant-Id`, a persistência do override e as regras de `saas_admin` foram mantidos; nenhum endpoint, token, `tenant_id` ou regra de isolamento foi alterado.

## Validação

`git diff --check`, `npm run lint`, `npm test` — **167 arquivos / 863 testes aprovados** — e `npm run build` foram concluídos. O build mantém apenas o alerta conhecido de chunk JavaScript acima de 500 kB.

A reprodução no ambiente público confirmou que o nome mudou para **Clic Piscinas (Meta)** e a correção agora elimina a fonte de dados antiga durante a troca. Após a publicação deste ajuste, será feita nova conferência do bundle público e da fila no navegador.
