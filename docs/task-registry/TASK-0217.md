# TASK-0217 — criptografia em repouso das credenciais Evolution/Meta/Instagram/broadcast (fase 2 de 2)

- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504) (painel v2 — #290 rotacionada em 26/08/2026, ver CLAUDE.md)
- **Status:** concluído

## Objetivo

Fase 2 do item 2 da auditoria de segurança (TASK-0210/TASK-0211, comparação
com o DeskcommCRM): estender a criptografia AES-256-GCM em repouso
(`server/services/tokenCrypto.ts`, já usada pro Google Calendar na fase 1)
pra todas as credenciais de terceiros restantes — Evolution API, Meta
Cloud API/Ads/CAPI, Instagram e números de broadcast — que ainda estavam
em colunas `text` puras, protegidas só pelo RLS.

## Atualizações

Essa é a fase de maior risco: diferente do Calendar (isolado, 2 funções,
falha só quebra reconexão), aqui os pontos de leitura estão espalhados por
21+ call sites em 5 tabelas, vários no caminho quente de envio de mensagem
WhatsApp/Instagram em produção pra tenant paga real. Cada site foi
verificado individualmente e envolvido com `decryptSecret`/`encryptSecret`
preservando exatamente o fluxo de controle e a ordem de fallback já
existente (`|| shared.X`, `|| sharedMeta.X`, etc.) — nenhuma lógica de
negócio mudou, só a camada de leitura/escrita do segredo.

**Leitura (`decryptSecret`), por arquivo:**
- `server/services/tenantResolver.ts` — 8 pontos (`resolveTenantByPhoneNumberId`
  ×2, `resolveTenantByEvolutionInstance`, `resolveTenantByInstagramAccountId`,
  `resolveMetaCredentialsForTenant`, `resolveCredentialsForTenant` ×2,
  `resolveCredentialsForConversation`) via um helper local `maybeDecrypt()`.
- `server/services/metaAdsInsightsService.ts` — `getTenantMetaAdsCredentials`.
- `server/services/metaAdsManagementService.ts` — `getManagementCredentials`.
- `server/services/metaCapiService.ts` — `getTenantCapiCredentials`.
- `server/services/evolutionConnectionAlertJob.ts` — `checkOneTenant`
  (job periódico de 5min que consulta o estado da conexão Evolution).
- `server/services/broadcastStore.ts` — `mapNumberRow` (tabela
  `broadcast_numbers.access_token`, achada durante o rastreamento de
  código a partir do `tenantResolver.ts` — não estava no levantamento
  original de `information_schema` da TASK-0211 porque esse levantamento
  cobriu só as 4 tabelas de credencial "por tenant", e `broadcast_numbers`
  é uma tabela auxiliar separada).
- `server/routes/admin.ts` — todo ponto que lê `tenant_evolution_credentials.api_key`
  antes de usar num header HTTP pra Evolution API (rotas
  `POST .../evolution-instance`, `GET .../evolution-instance/qrcode`,
  `GET .../evolution-instance/status`, `POST .../evolution-instance/recreate`).
  As rotas `GET .../capi-credentials` e `GET .../instagram-credentials` só
  devolvem um booleano (`!!data?.capi_access_token`/`!!data?.access_token`)
  pro painel — não precisam decifrar, um valor cifrado ainda é truthy.

**Escrita (`encryptSecret`), por arquivo:**
- `server/services/metaAdsInsightsService.ts` — `saveMetaAdsConnection`
  (`meta_ads_access_token` e `meta_ads_management_access_token`).
- `server/services/broadcastStore.ts` — `createBroadcastNumber` e
  `updateBroadcastNumber`.
- `server/routes/admin.ts` — inserção de credencial Meta na criação de
  tenant (`access_token`); `createFreshInstance` (Evolution `api_key`,
  insert e update); a inserção de `tenant_evolution_credentials` feita
  direto na rota `POST .../evolution-instance` (achado que não seguia o
  helper `createFreshInstance`, tinha o próprio insert com `api_key` em
  texto puro); `PUT .../capi-credentials` (`capi_access_token`); `PUT
  .../instagram-credentials` — aqui com cuidado extra pra não cifrar duas
  vezes: o valor final só é cifrado quando um token NOVO foi digitado no
  formulário (`trimmedAccessToken`); quando o campo vem em branco e o
  código reaproveita o valor já salvo (`existing.access_token`), esse
  valor já está cifrado e é gravado de volta como está.

**`scripts/encrypt-phase2-credentials.ts` (novo, `npm run
encrypt:phase2-credentials`)** — backfill idempotente (mesmo padrão da
fase 1: pula qualquer valor já prefixado `v1:`) cobrindo as 4 tabelas/7
colunas de segredo desta fase (`tenant_evolution_credentials.api_key`;
`tenant_meta_credentials.access_token/capi_access_token/meta_ads_access_token/meta_ads_management_access_token`;
`tenant_instagram_credentials.access_token`; `broadcast_numbers.access_token`).
Não é obrigatório rodar pro código funcionar — `decryptSecret` já
reconhece texto puro legado e devolve como está.

## Encerramento

**Pendente ou risco:** com esta fase, as 5 tabelas identificadas na
auditoria original (TASK-0210/0211) — `tenant_calendar_tokens`,
`tenant_evolution_credentials`, `tenant_meta_credentials`,
`tenant_instagram_credentials` — mais `broadcast_numbers` (achada durante
a implementação) estão todas cobertas. `TOKEN_ENCRYPTION_KEY` (mesma
chave da fase 1, `openssl rand -base64 32`) ainda precisa estar
configurada em produção (Render) pra a criptografia entrar em vigor de
verdade nas escritas novas; sem ela, o código roda normalmente mas
continua gravando em texto puro (rollout intencionalmente não-quebrante,
mesmo padrão da fase 1). Depois da chave configurada, rodar `npm run
encrypt:calendar-tokens` (fase 1) e `npm run encrypt:phase2-credentials`
(esta fase) uma vez cada pra cifrar o que já está em produção — nenhum
dos dois é obrigatório pro sistema continuar funcionando, só aceleram a
proteção pros tenants já conectados. Fora do escopo desta fase: o item 1
da auditoria (sweep de completude de RLS) segue pendente, tarefa separada.
