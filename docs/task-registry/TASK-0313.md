# TASK-0313 — Backfill de criptografia em repouso rodado em produção (Evolution/Meta/Instagram)

- **Iniciado em:** 2026-09-05T22:33:13.512Z
- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluído

## Objetivo

Backfill de criptografia em repouso rodado em produção (Evolution/Meta/Instagram)

## Atualizações

Achado durante uma auditoria geral de prontidão comercial (pedido direto do
dono do produto, "começa pelos backfills de criptografia"): o código de
criptografia em repouso AES-256-GCM pras credenciais de terceiros já existia
havia dias (TASK-0211, fase 1, Google Calendar, 02/09; TASK-0217, fase 2,
Evolution/Meta/Instagram/broadcast, 02/09), mas nenhuma das duas tasks
confirmou que o **backfill** (`npm run encrypt:calendar-tokens` /
`npm run encrypt:phase2-credentials`) tinha de fato rodado contra produção —
ambos os registros terminam com "ainda precisa ser gerada/rodada", sem
fechamento posterior.

**Auditoria confirmou o gap real via query direta no Supabase de produção**
(não confiei no "código existe" como prova de "está protegido"):

| Tabela | Antes (texto puro) |
|---|---|
| `tenant_calendar_tokens` | 0 (já cifrado) |
| `tenant_evolution_credentials.api_key` | 2/2 |
| `tenant_meta_credentials` (access_token/capi/ads/ads_mgmt) | as 3 colunas com valor, das 4 |
| `tenant_instagram_credentials.access_token` | 1/1 |

Ou seja: só o Google Calendar (fase 1) estava protegido de verdade — a
credencial da conta WhatsApp Business real da tenant paga (Evolution +
Meta CAPI/Ads) seguia em texto puro no banco, meses depois do código já
existir.

**Ação:** como os scripts exigem a `TOKEN_ENCRYPTION_KEY` exata já
configurada em produção (usar uma diferente quebraria a decriptação em
runtime — risco real de derrubar o envio de WhatsApp da tenant paga) e não
existe nenhuma ferramenta neste ambiente que **leia** variáveis de ambiente
do Render (só escrita, por desenho de segurança do próprio conector),
recusei rodar com uma chave gerada por mim ou pedir pro dono do produto
colar a chave real no chat (exporia o segredo no histórico da conversa,
exatamente o tipo de risco que a TASK-0311 trabalhou pra eliminar). Em vez
disso, o dono do produto rodou os dois comandos diretamente no Shell do
Render do serviço `universo-api-evo-hub` (ambiente já carregado com a
chave real, nunca sai de lá):

```
npm run encrypt:calendar-tokens
npm run encrypt:phase2-credentials
```

Saída real do backfill: `tenant_evolution_credentials` cifrados 2;
`tenant_meta_credentials` cifrados 1; `tenant_instagram_credentials`
cifrados 1; `broadcast_numbers` cifrados 0 (tabela vazia); Calendar já
estava cifrado (0 novos, 1 pulado).

## Validação

Re-consultei o Supabase de produção depois do backfill: as 4 tabelas/7
colunas de segredo (Calendar, Evolution, as 3 colunas de Meta com valor,
Instagram) agora têm 100% dos valores com o prefixo `v1:` (cifrado),
zero em texto puro. `tenant_meta_credentials.access_token` segue `null`
pro único tenant real (nunca teve valor gravado, nada a cifrar).

Confirmação de que nada quebrou no caminho quente de mensagens: consultei
os logs do Render (`mcp__Render__list_logs`) da janela seguinte ao backfill
— zero linhas de erro/warning, e um webhook Evolution real chegou e foi
processado com sucesso (`📱 [Evolution Webhook] Evento recebido`,
22:22:57 UTC), confirmando que a decriptação da credencial cifrada
funciona normalmente em produção.

## Encerramento

**Concluído.** As 5 tabelas de credencial de terceiro identificadas na
auditoria original (TASK-0210/0211/0217) estão hoje efetivamente cifradas
em repouso em produção — não só com o código pronto, com o dado real
protegido. Atualizei `docs/task-registry/TASK-0211.md` e
`docs/task-registry/TASK-0217.md` pra refletir esse fechamento (as duas
terminavam com essa pendência em aberto).

**Pendente ou risco:** nenhum novo. Nenhuma mudança de código nesta task —
só ação de dado em produção + atualização de docs.
