# TASK-0190 — Etiquetas sugeridas fixas (BEAUTY_STUDIO_LABEL_SUGGESTIONS) reaparecem sempre após excluir no X

## Objetivo

Etiquetas sugeridas fixas (BEAUTY_STUDIO_LABEL_SUGGESTIONS) reaparecem sempre após excluir no X

## Contexto (relato real, 01/09/2026)

Usuário reportou, junto com o print de uma conversa com 8 chips de etiqueta
("Turno confirmado", "Interesada en pestañas/cejas/labios", "Precio
informado", "Duda sobre dolor", "Seña pendiente", "Comprobante recibido"):
"os horários não estão persistindo e as etiquetas não apagam no x".

## Investigação

- A conversa do print (tenant `8a786c2a-...`, telefone `595984390832`,
  identificada por texto de mensagem) tem **zero** linhas em
  `conversation_labels` no Supabase — e a tabela inteira só tem 2 linhas em
  toda a produção. Ou seja, os 8 chips do print não são etiquetas realmente
  aplicadas a essa conversa.
- Os 8 textos do print batem exatamente, palavra por palavra, com o array
  `BEAUTY_STUDIO_LABEL_SUGGESTIONS` (`src/components/WhatsAppLeadsSim.tsx`),
  um texto **fixo no código** (não vem do catálogo do tenant) adicionado na
  TASK-0189/PR #572 como sugestões de exemplo pro segmento beauty_studio —
  aparecem em TODA conversa como chips tracejados (`+ etiqueta`) na barra
  logo abaixo do cabeçalho.
- O X num chip tracejado chama `handleDeleteLabelCatalog` → `DELETE
  /api/conversation-labels/:label`, que apaga o texto do catálogo real do
  tenant (`conversation_labels`) — mas como esses 8 textos nunca existiram
  como linha real ali, o DELETE só faz um no-op (200 OK, zero linhas
  afetadas). No próximo render, a lista de sugestões é recalculada como
  `new Set([...tenantLabelSuggestions, ...BEAUTY_STUDIO_LABEL_SUGGESTIONS])`
  — como o array fixo nunca é filtrado por nada que reflita a exclusão, a
  sugestão reaparece imediatamente. Daí "as etiquetas não apagam no x".
- **"Horários de atendimento"**: verificado via consulta direta no Supabase
  que `tenants.business_hours` do tenant real já está persistido
  corretamente (Seg–Sáb 09:00–18:00) após o deploy da TASK-0187 (commit
  `e4e4aa0`, live desde 01/09 16:26 UTC, confirmado via
  `mcp__Render__list_deploys`). O fix já está em produção; se o usuário
  ainda via o modal vazio, era um problema de cache do navegador/PWA (bundle
  antigo), não um bug de backend novo — nenhuma alteração de código
  necessária nesta frente.

## Correção

`src/components/WhatsAppLeadsSim.tsx`: guarda um `Set` de sugestões-padrão
já dispensadas em `localStorage` por navegador+tenant
(`saas_dismissed_label_suggestions_<tenantId>`) — não é dado de negócio real
(por isso `localStorage`, não uma tabela nova), só preferência de UI. Ao
excluir uma sugestão do catálogo (`handleDeleteLabelCatalog`), o texto
normalizado é adicionado a esse Set; a lista de sugestões filtra por ele além
do filtro de "já aplicada" que já existia. Recarrega o Set ao trocar de
tenant (saas_admin usa o seletor no Header).
