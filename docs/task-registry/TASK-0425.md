## Objetivo

Corrige duração de áudio fixa (15s) exibida pro painel: mostra a duração real medida ao tocar, em vez de um valor sempre errado

## Atualizações

**Achado real** (reportado pelo usuário via print, conversa "Jaz Escobar"): todo áudio no painel — recebido ou enviado, qualquer tenant — mostrava exatamente "15s", mesmo áudios visivelmente mais longos/curtos no player.

**Causa raiz**: `WhatsAppLeadsSim.tsx` renderizava `{msg.audioDuration || 15}s`. `audioDuration` só é preenchido em dois casos: gravação feita na hora no navegador (estimativa client-side, `blob.size / 4000`) e leads de demonstração/mock — nunca pra mensagem real vinda do banco (nem `StoredMessage` no backend, nem `MessageRow`, têm esse campo — a API nunca guarda duração de áudio em lugar nenhum). Resultado: pra qualquer mensagem de áudio real, `msg.audioDuration` é sempre `undefined`, caindo sempre no fallback fixo `15`.

**Correção**: em vez de inventar um número (contraria o princípio já seguido em todo o resto do projeto de nunca fabricar dado que não existe), a duração real agora é medida no navegador quando o áudio é tocado pela 1ª vez — `handlePlayRealAudioMessage` escuta `onloadedmetadata` do elemento `<audio>` e cacheia `audioEl.duration` (arredondado) num novo estado `realAudioDurations` por `messageId`. O rótulo mostra essa duração real assim que conhecida; até lá, fica vazio (nunca mais um número fixo e quase sempre errado).

**Escopo**: só front-end, só a exibição — não mexe em transcrição, em como o áudio é enviado/salvo, nem introduz nenhuma chamada nova ao backend (usa o mesmo fetch lazy de `/api/media/:messageId` que já existia pra tocar o áudio). Não persiste a duração — cada sessão do navegador remede ao tocar de novo, aceitável pra um rótulo cosmético.

**Verificação**: `npm run lint` / `npx vitest run` (313 arquivos, 1797 testes — nenhum teste dependia do valor fixo "15s") / `npm run build` — todos limpos.
