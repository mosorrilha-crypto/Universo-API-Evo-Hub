# TASK-0119 — contador de pendencias do whatsapp ignorava escalonamentos arquivados nao resolvidos

- **Iniciado em:** 2026-08-27T21:59:26.025Z
- **Agente/plataforma:** Claude
- **Issue central:** [#290](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/290)
- **Status:** concluída

## Objetivo

contador de pendencias do whatsapp ignorava escalonamentos arquivados nao resolvidos

## Atualizações

Usuário reportou um screenshot real: o botão "Pendências" na tela de Atendimento (WhatsApp)
mostrava "1", mas não existia nenhum escalonamento pendente de verdade (confirmado consultando
`escalations` no Supabase: zero linhas com `resolved = false` pra esse tenant no momento do
report).

Ao investigar, a explicação mais provável pro caso específico é uma falha de rede transitória —
o sinal fraco visível no topo da tela e o fato de `fetchEscalations` (`src/App.tsx`, polling a
cada 8s) engolir silenciosamente qualquer erro de fetch (`.catch(() => {})`, mantendo o estado
anterior em vez de zerar) — comportamento correto de degradação graciosa, não um bug.

Só que, ao comparar os dois lugares que calculam essa mesma contagem, achei uma inconsistência
real e permanente: `AtendimentoWorkspaceFrame` recebe `pendingCount={escalations.filter((e) =>
!e.resolved && e.status !== 'archived').length}` (`src/App.tsx:1312`), mas o badge do botão
"Pendências" dentro de `WhatsAppLeadsSim` recebia `escalationsPendingCount={escalations.filter((e)
=> !e.resolved).length}` (`src/App.tsx:1330`) — **sem excluir `status === 'archived'`**. Um
escalonamento arquivado (via botão "Arquivar" em `EscalationsPanel.tsx`) atualiza só `status`
localmente (`{ ...e, status: 'archived' }`), sem necessariamente marcar `resolved: true` — então
um caso arquivado mas tecnicamente `resolved: false` contaria pro badge do WhatsApp e não pro
contador do cabeçalho, gerando exatamente o tipo de divergência relatada (mesmo não sendo,
confirmadamente, a causa desta ocorrência específica — o banco não tinha nenhum caso assim agora).

Correção: alinhado o filtro do `escalationsPendingCount` com o do `pendingCount`, excluindo
`status === 'archived'` também.

## Encerramento

**Validação:** `npm run lint`, `npx vitest run` (217 arquivos, 1104 testes) e `npm run build`,
todos limpos. Não existe arquivo de teste pra `App.tsx` (componente monolítico sem cobertura
própria) — não criado um teste de renderização só pra essa expressão de uma linha, desproporcional
pro tamanho do fix.

## Pendente ou risco

Nenhum risco de código conhecido. A ocorrência específica relatada pelo usuário provavelmente foi
rede, não este bug — mas o bug em si era real e ficaria latente até um caso arquivado-não-resolvido
aparecer; corrigido preventivamente.
