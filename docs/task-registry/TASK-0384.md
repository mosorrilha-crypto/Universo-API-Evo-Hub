# TASK-0384 — Error Boundary para as abas com React.lazy (TASK-0376) — tela em branco após deploy

- **Iniciado em:** 2026-09-11T14:54:01.565Z
- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluído

## Objetivo

Achado real, reportado pelo dono do produto: "no desktop não estou conseguindo acessar as configurações do sistema saas admin e selecionar empresas".

## Investigação

A TASK-0376 (10/09/2026, mesclada em `main`) converteu 11 abas — incluindo `SaaSAdminDashboard` (aba "Empresas") e todas as abas dentro de "Configurar" — de import estático pra `React.lazy`, reduzindo o bundle inicial em ~33%. O próprio registro da TASK-0376 já sinalizava o risco: "não foi possível abrir o app real neste sandbox... recomendo confirmação visual em produção pós-deploy" — essa confirmação nunca aconteceu antes do relato do dono do produto.

Auditei o app inteiro (`grep -rn "ErrorBoundary\|componentDidCatch" src/`) e **não existe nenhum Error Boundary em lugar nenhum do frontend**, nunca existiu. Antes da TASK-0376 isso não importava (tudo vinha no mesmo bundle, sem chamada de rede adicional ao trocar de aba). Com `React.lazy`, cada aba passou a depender de um `import()` dinâmico buscando um chunk com nome de arquivo hasheado (`SaaSAdminDashboard-<hash>.js`) que muda a cada build/deploy. Sem Error Boundary, se esse `import()` falhar — o caso mais comum sendo uma aba aberta no navegador ANTES de um novo deploy, cujo `index.html` em cache ainda referencia hashes de chunk que o deploy novo já substituiu (404) — o React derruba a árvore de componentes inteira a partir do ponto da falha, sem nenhuma boundary pra conter, deixando a tela em branco/travada. Isso bate exatamente com o relato: apps de página única mantidos abertos por horas (típico de um admin no desktop) são o cenário mais exposto a essa falha logo após qualquer deploy.

## O que mudou

- `src/components/LazyTabErrorBoundary.tsx` (novo): Error Boundary reutilizável. Se o erro capturado tem cara de chunk desatualizado (`ChunkLoadError` ou mensagem batendo com o padrão do Vite pra `import()` dinâmico falho), recarrega a página sozinho **uma única vez** (guardado por `sessionStorage`, evita loop) — o `index.html` atualizado após o reload aponta pros chunks certos. Pra qualquer outro erro, ou se o reload automático já foi tentado nesta aba, mostra um fallback com botão manual "Recarregar página" em vez de tela em branco.
- `src/App.tsx`: todo o conteúdo de `<main>` (todas as 11 abas lazy + a aba Atendimento, sempre montada) passou a ficar dentro do `<LazyTabErrorBoundary>` — uma falha em qualquer uma delas fica contida, sem derrubar o app inteiro.
- Teste novo `src/components/__tests__/LazyTabErrorBoundary.test.tsx`: renderização normal, fallback genérico com botão, reload automático único para erro de chunk, e que o reload não repete se já foi tentado na mesma aba do navegador.

## Validação

`npm run lint` (limpo), `npx vitest run` (294 arquivos / 1648 testes, 4 novos, todos verdes) e `npm run build` (limpo, chunks lazy confirmados no output com hashes novos) — todos rodados depois da correção.

## Pendente ou risco

Mitigação de UX/disponibilidade, não uma mudança de área crítica (auth/pagamento/tenant_id) — não deveria precisar de revisão bloqueante antes do merge. Recomendo ao dono do produto: (1) der um `Ctrl+Shift+R`/`Cmd+Shift+R` agora pra descartar o cache do deploy anterior e confirmar que "Empresas"/"Configurar" voltam a abrir; (2) confirmar, no próximo deploy, que deixar uma aba aberta de antes do deploy e navegar pra uma aba lazy dispara o reload automático (ou o fallback manual) em vez de tela em branco.
