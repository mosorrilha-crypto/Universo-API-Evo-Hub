## Objetivo

Corrige de vez a faixa em branco do Atendimento mobile: regra CSS de toque nunca testada e cabecalho global nao descontado

## Atualizações

Continuação direta da TASK-0159 (PR #543, mergeada mais cedo hoje). O dono do
produto mandou 2 prints novos (celular real, pós-deploy da TASK-0159):
"melhorou mas ainda não resolveu" — e apontou que a tela de LISTA de
conversas também "passa um pouco pra baixo".

**Auditoria em vez de chutar mais uma vez** — dado o histórico de 5
tentativas anteriores (TASK-0150/0153/0155/0157/0158/0159) todas alegando
"concluído" sem resolver de vez, refiz a reprodução do zero em vez de propor
outra correção às cegas.

**Achado raiz nº1 (o mais importante):** existe uma regra CSS `!important`
adicionada em 22/08 (`fix: preserva fila do atendimento em mobile`, commit
`4827c35`) — **antes** de toda a saga TASK-0150...0159 começar:

```css
@media (hover: none) and (pointer: coarse) {
  .atendimento-chat-shell {
    display: grid !important;
    grid-template-columns: minmax(0, 1fr) !important;
    height: 70dvh !important;
    min-height: 26rem !important;
    max-height: 38rem;
  }
}
```

Essa regra trava `.atendimento-chat-shell` numa altura fixa (`max-height:
38rem` = 608px) em QUALQUER dispositivo de toque, com `!important` — vencendo
qualquer `className` que as seis tentativas anteriores tentaram (`h-full`,
`flex-1`, `h-[82dvh]`, `h-[100dvh]` etc.), porque nenhuma delas mexeu ou
sequer olhou pra esse bloco. Pior: **nenhuma verificação estática anterior
(a minha própria incluída, na auditoria da TASK-0159 mais cedo hoje)
detectou isso**, porque `(hover: none) and (pointer: coarse)` só casa com
input de toque de verdade — um `chromium.newPage()` do Playwright sem
emulação de dispositivo reporta `hover: hover` / `pointer: fine` (igual
mouse), então esse bloco inteiro nunca era exercitado nos testes, mesmo
carregando o CSS real compilado. Confirmado com um teste dedicado
(`window.matchMedia('(pointer: coarse)').matches`): `false` num
`newPage()` puro, `true` com `devices['Pixel 5']` do Playwright.

Corrigido: removidas `height`/`min-height`/`max-height` fixas dessa regra
(`src/index.css`) — mantido só `display: grid !important` +
`grid-template-columns` (comportamento legítimo: colapsar fila/conversa numa
coluna só em telas de toque, mesmo quando o navegador reporta viewport
largo — é essa a razão original da regra existir). Sem a altura chutada, o
`flex-1 min-h-0` da TASK-0159 finalmente consegue agir também em
dispositivos de toque reais.

**Achado raiz nº2 (explica a tela de lista):** o wrapper em `App.tsx`
(`h-[calc(100dvh-1.5rem)]`) só cancela o padding do próprio `.app-main` —
nunca soube quanto o `<Header/>` global (marca "Universo", seletor de
idioma/tema) mede de verdade quando está visível (tela de lista, sem
conversa aberta). Sobrava exatamente essa altura embaixo da tela. Em vez de
chutar mais um valor fixo (mesmo erro repetido nas tentativas anteriores),
medida a altura real do `<Header/>` via `ResizeObserver` (novo `useEffect`
em `App.tsx`, perto de `isMobileWhatsAppThreadOpen`) — inclusive reportando
`0px` automaticamente quando o Header vira `display:none` (conversa aberta).
O valor alimenta `--atendimento-header-h` (custom property em
`document.documentElement`), usada no cálculo:
`h-[calc(100dvh-var(--atendimento-header-h,0px)-1.5rem)]`.

**Verificação corrigida** (agora com emulação de toque de verdade —
`devices['Pixel 5']` do Playwright, não só largura/altura de viewport):
- Tela de lista (Header visível): gap embaixo do chat-shell caiu de -51px
  (overflow real, sem o fix do Header) pra 5px.
- Tela de thread (Header escondido): gap caiu de 1041px (com a regra de
  toque ainda ativa, ANTES deste fix) pra 5px.
- Confirmado também que a regra de toque tem impacto real: sem removê-la,
  mesmo com a TASK-0159 e o fix do Header aplicados, o chat-shell ficava
  travado em 608px de altura (`max-height: 38rem`) — 1041px de gap num
  viewport de 1813px.

Arquivos: `src/App.tsx`, `src/index.css`.

- Validado com `npm run lint` (limpo), `npx vitest run` (227 arquivos, 1177
  testes, todos verdes — nenhum teste quebrou, mudança é CSS + uma
  medição via ResizeObserver que não altera nenhum comportamento de outra
  aba), `npm run build` (limpo).
- Confirmado via Render MCP que o deploy da TASK-0159 (`b45f1b7`) já estava
  `live` bem antes do horário dos prints do dono do produto — não é atraso
  de deploy, o residual reportado era real.

## Encerramento

**Pendente ou risco:** mudança só de CSS/layout + uma medição de altura via
`ResizeObserver` (sem tocar lógica de negócio/dados) — mas `App.tsx` é
compartilhado por TODAS as abas, então pedir uma conferência visual rápida
no dono do produto em outras abas além do Atendimento é prudente, mesmo o
efeito novo só afetando o cálculo quando `activeTab === 'whatsapp'`.
Recomendo fortemente confirmação no celular real pós-deploy — mesma
ressalva de sempre, mas desta vez com uma metodologia de verificação que
realmente reproduz o ambiente de toque real, não só largura/altura de tela.
