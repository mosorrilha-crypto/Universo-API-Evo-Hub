## Objetivo

Cancela pendência de reengajamento automático do funil quando um operador responde manualmente pelo painel

## Atualizações

**Achado real** (reportado pelo usuário via print, tenant Monique, conversa com Ruth Gonzalez, 16/09/2026): a IA ofereceu revisar horários às 17:10 (mensagem "¿Te gustaría que revise los horarios disponibles para esta semana, Ruth?"), criando uma pendência `customer_reply` no funil (vence em ~2h30, `pendingFollowUpJob.ts`). Às 19:35 a própria Monique respondeu manualmente pelo painel (rota `/send` em `conversations.ts`, `sentBy='operator'`) com uma mensagem de reengajamento similar. Sete minutos depois (19:42), o job automático de reengajamento disparou por conta própria e mandou OUTRA mensagem quase idêntica pra mesma cliente — porque nada cancelava a pendência do funil numa resposta manual do operador (`resolveOpenEscalationsAfterManualReply`, chamado na mesma rota, só resolve escalonamentos, nunca pendências de funil).

**Investigação**: reconstruí a timeline exata via SQL direto na tabela `messages` (sender/sent_by/operator_name/created_at) — confirmou que a mensagem das 19:35 tinha `sent_by='operator'`, `operator_name='Monique (Teste)'`, e um ID no formato de WAMID real (não o `wa-<timestamp>-...` interno), batendo exatamente com o padrão da rota `/send` manual (não um eco de app externo). A das 19:42 tinha `sent_by='ai'` — confirmado como o job `pendingFollowUpJob.ts`/`tryAutomaticFollowUp`, que não verifica se um humano já reengajou antes de disparar.

**Correção**: `conversationStore.recordOutgoingMessage` agora chama `clearPendingFollowUp(tenantId, phone, 'customer_reply')` (best-effort, `.catch(() => {})`, mesmo padrão de `registerPendingEcho` logo acima) sempre que `sentBy === 'operator'` — cobre TODOS os pontos reais de envio manual (resposta simples, resposta em bolhas, template oficial), já que é o único ponto central por onde toda mensagem enviada passa. Escopo deliberadamente restrito a `'operator'`: `'campaign'` (disparo em massa automático) não conta como alguém cuidando desta conversa específica, e `'ai'` já é o próprio reengajamento automático — não faz sentido ele cancelar a si mesmo.

**Testes novos**: `recordOutgoingMessageClearsFollowUp.test.ts` — cobre `operator` cancelando a pendência, `ai`/`campaign` NÃO cancelando, e nenhuma quebra quando não há pendência aberta.

**Verificação**: `npm run lint` / `npx vitest run` (313 arquivos, 1797 testes) / `npm run build` — todos limpos. Branch sincronizada com `main` (merge, não rebase — outras sessões já tinham avançado até TASK-0422 nesse meio-tempo; conflito em `server/routes/webhooks.ts` resolvido mantendo a versão de `origin/main`, que já incorporava corretamente o trabalho anterior desta sessão — TASK-0415/0416 — mais a absorção de buffer da TASK-0418).
