## Objetivo

contador interno de clique no whatsapp do catalogo, independente de pixel e gatilho de texto

## Atualizações

**Pedido direto no chat**, no mesmo dia do incidente do webhook e da correção dos Gatilhos de Anúncio: o dono do produto perguntou se dava pra saber quantas pessoas clicaram nos links de WhatsApp do catálogo. Resposta honesta na hora: ainda não — o Meta Pixel (PR #409, mergeado nesta mesma sessão) só manda o evento pro Facebook, nunca chega no nosso backend; e o reconhecimento por texto ("Gatilhos de Anúncio") é frágil, só funciona se o cliente mandar a mensagem pré-preenchida exatamente como veio.

**Solução implementada** (aprovada pelo dono do produto, inclusive escolhendo emojis fofos em vez de código alfanumérico):
1. Os 3 botões de WhatsApp do catálogo (`PublicCatalogPage.tsx`) não apontam mais direto pro `wa.me` — apontam pra uma rota nova do nosso backend.
2. `GET /api/public/catalog/:slug/whatsapp-click` (`publicCatalog.ts`): grava o clique numa tabela própria (`public_catalog_whatsapp_clicks`, migration 0048, aplicada via Supabase MCP e confirmada em `list_migrations`) — contagem real, acontece sempre, independente do cliente chegar a mandar a mensagem — e redireciona (302) pro WhatsApp de verdade com um code único (3 emojis de um conjunto "fofo", `publicCatalogClickStore.ts`) embutido no fim da mensagem pré-preenchida.
3. Quando a mensagem chega no agente, `attachCatalogClickIfMatched` (`conversationStore.ts`, chamado de `webhooks.ts` e `transcriptionQueue.ts`) procura o code em qualquer parte do texto recebido (substring, não só prefixo — sobrevive a edição do cliente) e liga a conversa ao clique específico (`matched_at`/`matched_phone`). Roda pra QUALQUER tenant, não só os com `ads_only` ligado — decisão deliberada: a métrica "clique virou conversa" não devia depender desse modo.
4. `shouldBlockForAdsOnlyMode` continua com sua responsabilidade original (decidir se a resposta automática fica em silêncio); a checagem de clique foi fatorada pra fora dela, pra não acoplar as duas coisas.

**Arquivos:** `supabase/migrations/0048_public_catalog_whatsapp_clicks.sql`, `server/services/publicCatalogClickStore.ts` (novo), `server/routes/publicCatalog.ts`, `server/services/conversationStore.ts`, `server/routes/webhooks.ts`, `server/services/transcriptionQueue.ts`, `src/components/PublicCatalogPage.tsx`.

**Testes novos:** `server/services/__tests__/publicCatalogClickStore.test.ts`, `server/services/__tests__/conversationStoreCatalogClick.test.ts`, casos novos em `server/routes/__tests__/publicCatalog.test.ts`.

**Validação:** `npm run lint`, `npx vitest run` (916 testes, todos passando), `npm run build` — todos OK. Migration aplicada em produção via `apply_migration` e confirmada em `list_migrations`.

**Pendente ou risco:** nenhum conhecido. `/api/public/catalog/:slug/whatsapp-click` usa o mesmo rate limiter da rota pública existente (`publicCatalogRateLimiter`), então não abre superfície de abuso nova sem proteção.
