# TASK-0296 — Overrides determinísticos no revisor: ordem de pedir o nome e pronome compartilhado 'te'

## Objetivo

Overrides determinísticos no revisor: ordem de pedir o nome e pronome compartilhado 'te'

## Contexto

Fase 2 de 3 de uma tarefa maior (ver TASK-0295). O dono do produto perguntou se valeria adicionar "revisor puro em código" depois de ver dois falsos-positivos do revisor por IA no mesmo dia (TASK-0293: revisor exige nome "antes" do preço, quando a regra só pede nome na mesma resposta; TASK-0294: revisor trata o pronome "te" como mistura de espanhol/português). Ambos já tinham sido corrigidos só por reforço de prompt — esta tarefa converte os dois em overrides determinísticos de verdade, mesmo princípio já usado em `overrideNameOnlyFalsePositive` (TASK-0277): quando o próprio julgamento do revisor erra de um jeito específico e repetível, um override é mais durável que confiar no LLM lembrar da clarificação toda vez.

## Mudança

- **`server/services/replySafetyGate.ts`**:
  - Nova `overrideNameOrderFalsePositive`: aprova quando o motivo reprovado cita nome + palavra de ordem ("ordem", "antes de", "primeiro") E o rascunho já contém um pedido de nome reconhecível (regex pt/es) E não afirma confirmação de agenda já feita (`CONFIRMED_BOOKING_LANGUAGE`) — qualquer outro problema citado junto (idioma, pagamento, nome inventado) continua bloqueado.
  - Nova `overrideSharedWordLanguageFalsePositive`: aprova quando o motivo cita mistura/idioma E, removendo os pronomes "te"/"tu" (compartilhados pelos dois idiomas) do rascunho normalizado, não sobra nenhuma palavra GRAMATICAL exclusiva de espanhol (`SPANISH_EXCLUSIVE_GRAMMAR_WORDS`: pero, entonces, así, vos...) — deliberadamente uma lista própria, sem vocabulário de conteúdo/catálogo (`hasSpanishSignal` inclui "labios"/"cejas"/"pestañas", que são nome de produto e apareceriam legitimamente numa resposta em português, o que faria o override nunca disparar pro caso real).
  - Nova `applyDeterministicOverrides`: encadeia os três overrides (o de TASK-0277 + os dois novos) — usada nos dois pontos que chamavam `overrideNameOnlyFalsePositive` diretamente (branches Groq e Gemini de `reviewAutoReplyBeforeSend`).
- **`server/services/replySafetyGate.test.ts`**: 6 testes novos (3 por override), no mesmo estilo dos 3 já existentes pra `overrideNameOnlyFalsePositive` — cobrindo o padrão puro aprovado, mistura com outro problema real (não aprova), e o caso em que a condição de fato não bate (não aprova). Um dos testes de "não aprova" precisou ser ajustado depois de rodar: um rascunho que não empurra pra agenda e é acusado só de "nome ausente" já é aprovado pelo override de TASK-0277 (correto, por regra de negócio — nome só é obrigatório ao avançar pra agenda) antes mesmo de chegar no novo override; o teste foi reescrito pra usar um rascunho que realmente empurra agenda sem pedir nome (violação de verdade, não falso-positivo de ordem).

## Encerramento

`npm run lint` limpo, `npx vitest run` — 264 arquivos / 1456 testes passando (6 novos), `npm run build` limpo.

**Arquivos:** `server/services/replySafetyGate.ts`, `server/services/replySafetyGate.test.ts`.

**Pendente ou risco:** os dois overrides são heurísticos (listas de padrões conhecidos) — não cobrem toda variação possível de "reclamação de ordem" ou "mistura de idioma", só os casos já observados; ajustar as listas se aparecerem casos reais novos, mesmo critério de risco documentado nos overrides anteriores (TASK-0277, TASK-0278). Fase 2 de 3 — falta a Fase 3 (correção automática da regra 14 em vez de bloquear/escalar).
