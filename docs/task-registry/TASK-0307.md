## Objetivo

Localização/Dados da conta enviando texto antigo pro cliente: Base de Conhecimento tem dois sistemas de dados em paralelo (blob legado x documentos publicados) fora de sincronia

## Atualizações

Print real do usuário, seguido de mensagem direta: já tinha editado e publicado o campo "Link de Localização (Google Maps)" removendo o texto de instrução interna que tinha vazado pro cliente (achado da TASK anterior, mesma conversa), mas o botão "Localização" do menu de anexos continuava mandando o texto antigo pro cliente real — inclusive 15 minutos depois da correção salva.

**Achado real, com consulta direta ao Supabase (não confiei no relato nem assumi "cache" sem checar):**

1. `messages` confirmou que as 3 mensagens com o texto poluído foram `sent_by: 'operator'` (botão manual "Localização", não a IA) — a mais recente 15min DEPOIS do usuário publicar a correção.
2. `knowledge_base_documents` (tenant `8a786c2a-...`, `document_type='business_profile'`, `status='published'`, versão 5) já tinha o valor CORRETO e limpo de `locationMapsUrl` — a edição do usuário funcionou e persistiu no sistema novo.
3. `knowledge_base` (tabela antiga, 1 linha jsonb por tenant, `updated_at` de 26/08) ainda tinha o texto poluído — **e é exatamente esse dado que alimenta o botão "Localização"/"Dados da conta"** no menu de anexos da conversa (`WhatsAppLeadsSim.tsx` → `App.tsx` → `GET /api/knowledge-base`).

**Causa raiz (achado de arquitetura, não é um bug pontual):** existem hoje DOIS sistemas paralelos de Base de Conhecimento:
- **Sistema novo** (`knowledge_base_documents`, documentos tipados com draft/publish, ISSUE-0096/PR2) — é o que `AgentKnowledgeBase.tsx` edita e o que `getRuntimeKnowledgeBase()` (usado por `autoReply.ts` pra gerar as respostas da IA) lê, com fallback pro sistema antigo só se a publicação estiver incompleta/indisponível.
- **Sistema antigo** (`knowledge_base`, 1 linha jsonb por tenant, "legacy blob") — é o que `GET/POST /api/knowledge-base` lê/grava DIRETO (a rota GET faz `select` cru na tabela pra um ETag baseado em `updated_at`, decisão documentada no próprio código como fix de um incidente real de egress do Supabase, TASK anterior não numerada — comentário em `conversations.ts:1706-1713`). Esse é o `knowledgeBase` que chega no frontend (`App.tsx`) e alimenta os botões manuais da conversa ("Localização", "Dados da conta") — e é TAMBÉM o que `getKnowledgeBase()` (sem "Runtime" no nome) devolve, usado ainda hoje em ~10 outros pontos do backend (`webhooks.ts:571`, `conversations.ts` várias linhas, `transcriptionQueue.ts`).

**O sistema novo NUNCA escreve de volta no sistema antigo** — publicar um documento tipado (`business_profile`, `POST /api/knowledge-base/documents/:type/publish`) não sincroniza a tabela `knowledge_base`. Resultado: qualquer edição feita pela tela de documentos tipados fica "invisível" pra tudo que ainda lê o blob antigo, indefinidamente, até alguém também salvar pelo formulário antigo (`onSaveKnowledgeBase` → `POST /api/knowledge-base`, que faz upsert do objeto inteiro).

**Achado colateral mais sério, no mesmo diff:** `agentGoal` (a instrução-mestra da IA) estava COMPLETAMENTE diferente entre os dois sistemas pro tenant Monique — o blob antigo ainda tinha a versão em ESPANHOL, enquanto o documento publicado já tinha a versão em PORTUGUÊS atualizada. `paymentDetailsText` no blob antigo estava `null` (o botão "Dados da conta" nem aparecia pro operador). `companyName`/`businessModel` já batiam.

**Ação imediata tomada (hotfix de dado, não de código):** sincronizei manualmente os 5 campos de `business_profile` (`companyName`, `agentGoal`, `businessModel`, `locationMapsUrl`, `paymentDetailsText`) do documento publicado pro blob antigo, via `UPDATE` direto no Supabase (produção), só pro tenant Monique - Evolution (`8a786c2a-...`) — desbloqueia o operador agora. Não é uma correção geral: qualquer OUTRO tenant com a mesma divergência continua afetado, e uma nova publicação futura volta a divergir até o fix de código abaixo ser feito.

**Fix de código recomendado (NÃO implementado ainda, nesta sessão — risco/escopo maiores do que o tempo restante comportava):** trocar a leitura crua de `GET /api/knowledge-base` (e, com mais cautela, os ~10 call sites de `getKnowledgeBase()` legado) por `getRuntimeKnowledgeBase()` (já testado, já usado por `autoReply.ts`). Complicador direto: o ETag desta rota hoje é `updated_at` da tabela crua (`knowledgeBaseEtag.test.ts`, criado pra resolver um incidente real de egress ~12MB) — trocar a fonte exige recalcular o ETag a partir do conteúdo composto (ex.: hash do corpo), e ajustar esse teste, que hoje assume ETag == `updated_at` do blob. Também é preciso decidir se a migração completa dos ~10 call sites legados (webhooks/transcrição/etc.) é uma tarefa própria maior (parece ser o que o comentário do código já chama de "corte de runtime aprovado em PR4", ainda não executado).

**Validação:** nenhuma automatizada (é um hotfix de dado em produção, não uma mudança de código). Consulta de confirmação rodada após o `UPDATE` (ver acima) confirma os 5 campos sincronizados pro tenant Monique - Evolution.
