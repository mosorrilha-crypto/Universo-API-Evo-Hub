# TASK-0036 — torna a numeração de TASK-XXXX segura entre sessões concorrentes (reserva atômica no remote)

- **Iniciado em:** 2026-08-24T02:50:00.000Z
- **Agente/plataforma:** Claude
- **Issue central:** [#290](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/290)
- **Status:** concluída

## Objetivo

Pedido direto do dono do produto depois de eu reportar a colisão recorrente de numeração `TASK-XXXX` entre sessões: "pode implementar isso unifica qualquer desenvolvedor que for me ver no repositório". Eliminar a classe de bug (não só mitigar reativamente renumerando depois).

## Causa raiz confirmada

`npm run task:start` (`scripts/start-task.ts`) calculava o próximo número lendo só o maior `TASK-XXXX.md` **commitado localmente** no checkout de quem roda o comando, protegido por um lock **de arquivo local** (`.sequence.lock`). Isso trava duas chamadas concorrentes *no mesmo checkout*, mas não trava nada entre checkouts diferentes — duas sessões (ex: Claude e Manus.Ai, cada uma com seu clone) que rodem o comando sem ter acabado de sincronizar a `main` uma da outra veem o mesmo "último número" e geram o mesmo próximo. Aconteceu de verdade três vezes na janela de 23-24/08/2026 (TASK-0026, TASK-0028, TASK-0030 colidiram; cada sessão resolveu renumerando antes de publicar, sem sobrescrever nada, mas de forma reativa).

## Correção

Reserva atômica no remote antes de escrever o arquivo local, em vez de só calcular localmente:

1. Além do maior número local, `getRemoteMaxSequence()` consulta `git ls-remote --heads origin 'refs/heads/task-claim/*'` pra saber o maior número já reservado por qualquer sessão, mesmo que ainda não tenha sido commitado/mergeado.
2. `claimSequence()` tenta reservar o próximo número criando um commit vazio local (mensagem com nonce aleatório, garante SHA único mesmo se duas sessões estiverem exatamente no mesmo `HEAD`) e empurrando **esse SHA específico** pra uma ref nova `refs/heads/task-claim/XXXX` — o checkout volta pro `HEAD` original logo em seguida (`finally`), então nenhum commit vazio sobra no branch de quem roda o comando.
3. `git push` de uma ref nova é atômico no servidor: a primeira sessão a empurrar cria a ref; qualquer outra tentativa pro mesmo nome com um SHA diferente é rejeitada de verdade (`non-fast-forward`) — o loop então tenta o próximo número.
4. **Achado real durante a implementação:** a primeira tentativa usou `refs/tags/task-seq/XXXX` (mais idiomático pra esse tipo de trava), mas `git push` de uma tag nova devolveu **HTTP 403** pras credenciais desta sessão — confirmado por teste real (push de branch normal funciona, push/delete de tag e delete de branch não). Trocado pra `refs/heads/task-claim/XXXX`, que funciona.
5. **Achado real (2):** empurrar o mesmo SHA duas vezes pro mesmo nome de branch novo não colide — git devolve "Everything up-to-date" com sucesso, porque pra um branch (diferente de tag) só rejeita quando os SHAs divergem. Como duas sessões limpas sincronizadas com a mesma `main` costumam estar exatamente no mesmo commit, isso quebraria a garantia de exclusividade — por isso o commit vazio com nonce é necessário, não é só estética.

Testado de ponta a ponta contra o remote real antes de fechar a tarefa: push de duas SHAs diferentes pro mesmo nome de ref nova (primeira aceita, segunda rejeitada de verdade), e uma execução real completa de `npm run task:start` (gerou este próprio registro, TASK-0036, sem deixar nenhum commit vazio sobrando no branch).

## Pendente ou risco

- Os branches de reserva (`refs/heads/task-claim/XXXX` e os dois de teste, `refs/heads/task-seq-test/0001` e `.../9001`) ficam pra sempre no remote — apagar ref remota também está bloqueado pras credenciais desta sessão (mesmo 403 do teste de tag). São branches vazios/inofensivos (só uma trava, sem PR aberto), mas se o dono do produto quiser limpar visualmente, só um admin com acesso de delete de branch consegue (pelo GitHub, não por esta sessão).
- Não elimina 100% a chance de colisão (duas sessões podem ainda gerar o mesmo candidato inicial), mas agora a segunda tentativa detecta o conflito de verdade e avança pro próximo número sozinha, sem precisar de renumeração manual depois.
