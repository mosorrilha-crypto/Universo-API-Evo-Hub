## Objetivo

Elimina o sistema legado knowledge_base (blob jsonb): migra Documentos Anexados pro Storage tipado, remove rotas/código morto e o fallback legado

## Contexto

Pedido direto: "vamos eliminar este sistema antigo ele está causando
confusão verifica se não vamos perder nada e já elimina ele" — motivado por
um achado real na mesma sessão: um dado bancário desatualizado (conta antiga
da Sara, já trocada pela conta da Monique) sobreviveu isolado no blob legado
`knowledge_base` (campo `pricingAndPolicies`), divergindo do que o editor
tipado já mostrava havia dias — corrigido pontualmente antes desta task, mas
a causa raiz (dois sistemas de Base de Conhecimento coexistindo, um deles
com escrita "invisível") só se resolve eliminando o legado por completo.

## Verificação (antes de eliminar)

1. **Publicação completa nos 3 tenants reais** — `select` direto em
   `knowledge_base_documents` confirmou os 8 tipos publicados pra Monique
   (Meta), Monique - Evolution e Clic Piscinas - Evolution. A leitura runtime
   (`getRuntimeKnowledgeBase`) já preferia a fonte tipada pros três — o
   fallback legado estava dormente, não removendo funcionalidade nenhuma.
2. **`firstContactBlocks`** (não vazio pra 2 dos 3 tenants no blob legado) —
   comparado campo a campo com `media_assets.firstContactBlocks` do
   documento tipado: idêntico pra Monique (Meta), e um SUPERSET (a versão
   tipada tinha um bloco de vídeo a mais, mais recente) pra Clic Piscinas —
   nada seria perdido.
3. **Caminhos de escrita restantes** — grep completo por
   `getKnowledgeBase\(|setKnowledgeBase\(|from('knowledge_base')` encontrou
   3 rotas ainda gravando no blob: `POST /api/knowledge-base` (save
   completo, PROVADO inalcançável em produção — único ponto de renderização
   real do editor, `App.tsx`, sempre passa `usesPublishedKnowledgeBase=true`,
   que já pula pro fluxo tipado antes de chamar esse callback) e
   `POST/DELETE /api/knowledge-base/documents` (upload/remoção de
   "Documentos Anexados" — esse SIM ativo e alcançável, com 0 documentos
   anexados em qualquer tenant no momento da checagem).
4. **Scripts fora do server** — `scripts/seed-monique-knowledge-base.ts`
   (documentado em CLAUDE.md como comando suportado) e
   `scripts/migrate-knowledge-base-images.ts` (utilitário avulso, nunca
   documentado como comando) dependiam de `setKnowledgeBase`/`getKnowledgeBase`
   diretamente. O primeiro também continha o MESMO dado bancário desatualizado
   hardcoded — achado extra durante a auditoria.

## Mudanças

**Migração da funcionalidade viva:** upload de "Documentos Anexados" trocado
pra `/api/knowledge-base/document-storage` (já existia, nunca era chamado
pelo frontend — só sobe o binário, sem tocar tabela nenhuma; a associação
final acontece no rascunho/publicação do documento tipado `media_assets`,
mesmo padrão já usado por vídeo/foto de exemplo). `DELETE
/api/knowledge-base/documents/:docId` simplificado pra só apagar o Storage
(a remoção da referência já é responsabilidade do editor tipado).

**Código removido:** rota `POST /api/knowledge-base` (legado, inalcançável);
`onSaveKnowledgeBase` (prop + callback em `AgentKnowledgeBase.tsx`/`App.tsx`,
`handleSave` unificado pro fluxo tipado sempre); `getKnowledgeBase`/
`setKnowledgeBase`/`collectReferencedVideoIds`/`collectReferencedImageIds`
(`knowledgeBaseStore.ts`); fallback `legacy_blob` de
`getRuntimeKnowledgeBaseFromDb` (agora só `published_documents` ou
`unavailable`, sem servir dado potencialmente desatualizado
silenciosamente); ramo `isLegacyFallback` de
`getSystemIncidentFromStructuredLog` (`structuredLog.ts`, ficaria
permanentemente morto); scripts `seed-monique-knowledge-base.ts` e
`migrate-knowledge-base-images.ts` (+ seu teste).

**Correção extra encontrada durante a auditoria:** a mesma conta bancária
desatualizada da Sara (achado original desta sessão) também existia hardcoded
no preset "Monique Sorrilha Beauty Studio" usado pelo saas_admin pra
onboarding de tenant novo (`AgentKnowledgeBase.tsx`,
`moniqueStudioKnowledgeBase.pricingAndPolicies`) — corrigida pra conta real
da Monique na mesma varredura.

**Migration:** `supabase/migrations/0079_drop_legacy_knowledge_base_table.sql`
(`DROP TABLE IF EXISTS knowledge_base`), aplicada via `apply_migration` do
Supabase MCP — confirmada com `to_regclass('public.knowledge_base')` → null.
Sem FK apontando pra ela, sem trigger, RLS/FK própria removida junto.

**Testes:** 2 arquivos inteiros removidos (testavam só o orphan-cleanup da
rota legada removida); ~20 arquivos de teste tiveram fixtures migradas de
`knowledge_base` (blob) pra `knowledge_base_documents` (8 tipos publicados) ou
tiveram o mock `getRuntimeKnowledgeBase` adicionado/corrigido (sem mais
`source: 'legacy_blob'`, que deixou de existir no tipo).

## Validação

`npm run lint` (limpo), `npx vitest run` (269 arquivos, 1483 testes, 100%
passando), `npm run build` (frontend Vite + backend esbuild), todos limpos.
Verificação manual no navegador não foi feita nesta sessão (ambiente sem
acesso ao painel real) — recomendo validar o fluxo de "Documentos Anexados"
(upload → salvar rascunho → publicar → aparece no prompt do agente) assim
que este PR for mesclado e deployado.

## Risco de sequenciamento (janela até o deploy)

A migration (DROP TABLE) já foi aplicada na produção real durante esta
sessão, antes do merge/deploy deste código — decisão deliberada: o código
JÁ RODANDO em produção (versão anterior a este PR) só usa o fallback legado
quando a publicação tipada está incompleta, o que não é o caso de nenhum dos
3 tenants reais hoje, e o próprio fallback já degrada com segurança (try/catch)
se a tabela sumir no meio de uma leitura. **Único ponto de risco real:** entre
agora e o deploy deste PR, se um operador tentar usar a aba "Documentos
Anexados" (upload/exclusão) no painel em produção, a chamada vai falhar com
500 (a rota antiga ainda ativa no deploy corrente aponta pra uma tabela que já
não existe) — recurso de baixo tráfego, 0 documentos anexados em qualquer
tenant no momento da checagem, mas registrado aqui pra dar prioridade ao
deploy deste PR.
