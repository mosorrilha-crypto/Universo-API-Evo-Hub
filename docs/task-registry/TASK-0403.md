# TASK-0403 — GET /api/media/:messageId nunca cacheia 404 (Cache-Control: no-store) — proxy de operadora retendo 404 velho

- **Status:** concluído

## Objetivo

GET /api/media/:messageId nunca cacheia 404 (Cache-Control: no-store) — proxy de operadora retendo 404 velho

## Atualizações

Fechamento (por ora) do arco "fotos não carregam" desta sessão (TASK-0392 → TASK-0397 → TASK-0398 → TASK-0401 → esta). Depois da TASK-0401 (auto-retry no painel), o dono do produto mandou novos prints reais: o celular mostrava "Carregando imagem..." (confirmando que o auto-retry estava rodando) por um tempo, mas voltava a "Imagem indisponível (HTTP 404)" — enquanto o MESMO print, tirado do desktop na mesma hora, mostrava as 3 fotos abrindo normalmente.

Isso descartou de vez as hipóteses anteriores (perda de dado no R2 — já descartada na TASK-0401; timing/corrida — já não fazia sentido depois de ~29s de auto-retry + minutos de espera real) e apontou pra uma causa nova: como `GET /api/media/:messageId` nunca dizia explicitamente que uma resposta 404 não deve ser guardada em cache, um proxy transparente de operadora de celular (comum em redes móveis da região — mais agressivo que qualquer proxy de wi-fi/desktop) pode reter o primeiro 404 e devolvê-lo de novo pras tentativas seguintes com a MESMA URL, mesmo depois da mídia já estar disponível de verdade no servidor — nenhuma tentativa nova do cliente (nem o auto-retry, nem o botão manual) chega a bater no servidor de fato, porque o proxy intercepta e responde do próprio cache. Isso explica por que o desktop (outra rede, sem esse proxy específico) sempre funcionou.

**Mudança:** `server/routes/conversations.ts`, rota `GET /api/media/:messageId` — os dois caminhos de 404 (mensagem não encontrada nesse tenant; mídia não encontrada no armazenamento) agora respondem com `Cache-Control: no-store` explícito, garantindo que nenhum proxy intermediário guarde essa resposta de erro. O caminho de sucesso (200) continua com o `Cache-Control: private, max-age=3600` + `Vary: Authorization` de sempre — sem mudança ali.

**Arquivos:** `server/routes/conversations.ts`, `server/routes/__tests__/conversationsMediaCacheControl.test.ts` (novo — 3 casos: 404 por mídia ausente com `no-store`, 404 por mensagem fora do tenant com `no-store` sem sequer consultar o armazenamento, 200 mantendo o cache privado de sempre).

**Validação:** `npm run lint` (tsc --noEmit) limpo; `npx vitest run` — 304 arquivos / 1738 testes passando (+3 novos); `npm run build` sem erros. Não depende de migration.

**Pendente ou risco:** nenhum risco técnico novo — só adiciona um cabeçalho de cache mais estrito num caminho de erro, sem mudar nenhum comportamento funcional. Não é possível confirmar 100% que o proxy de operadora é a causa exata (não há acesso a devtools/rede do celular real), mas é a explicação mais plausível dado o padrão observado (funciona sempre em wi-fi/desktop, falha persistentemente em rede móvel, mesmo com mais de meio minuto de retry automático) e a correção é de baixo risco e sem efeito colateral caso a causa real seja outra. Se o problema persistir mesmo depois desta correção, o próximo passo seria pedir pro dono do produto testar a mesma foto trocando de wi-fi pra dados móveis (e vice-versa) de propósito, pra isolar se é mesmo rede/operadora.
