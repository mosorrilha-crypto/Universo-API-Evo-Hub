# TASK-0281 — Corrige separador de data das mensagens mostrando sempre 'Hoje' pra conversas reais

- **Iniciado em:** 2026-09-04T21:38:05.140Z

- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluída

## Objetivo

Corrige separador de data das mensagens mostrando sempre 'Hoje' pra conversas reais

## Contexto

Achado colateral durante TASK-0280 (paginação de mensagens), já observado antes pelo dono do produto, que confirmou e pediu a correção: o separador de data acima de cada bloco de mensagens (`shouldShowDateSeparator`/`dateLabel` em `WhatsAppLeadsSim.tsx`) sempre mostrava "Hoje", mesmo pra mensagens de dias/semanas atrás.

Causa raiz: `msg.timestamp` de uma conversa real já chega formatado só como `"HH:MM"` (pra exibir no balão) — a lógica de agrupamento (`getChatDateParts` em `src/lib/chatDate.ts`) trata qualquer valor no formato `HH:MM` como mensagem de demonstração legada e assume "hoje" de propósito (comentário original: "Mensagens antigas de demonstração guardam apenas HH:MM"). Como as mensagens reais passaram a ser formatadas do mesmo jeito antes de chegar no separador de data, caíam no mesmo fallback por engano.

## Mudança

- **`src/types.ts`**: novo campo opcional `ChatMessage.rawTimestamp` — ISO completo (data + hora), só presente em mensagem real; mensagem mock continua sem ele.
- **`src/components/WhatsAppLeadsSim.tsx`**: `formatMessagesForDisplay` (usado por `loadRealConversationHistory`/`loadOlderMessages`, TASK-0280) agora preenche `rawTimestamp` com o ISO original antes de sobrescrever `timestamp` com o "HH:MM" de exibição. No render da lista de mensagens, `shouldShowDateSeparator`/`dateLabel` passaram a usar `msg.rawTimestamp || msg.timestamp` em vez de só `msg.timestamp` — mensagem real usa a data completa de verdade, mock cai no mesmo fallback "hoje" de sempre (comportamentoide destinado, sem mudança).
- `src/lib/chatDate.ts` não precisou de nenhuma mudança — a lógica de agrupar por data já estava correta pra ISO completo (coberta pelos testes existentes em `chatDate.test.ts`); o bug era só o chamador passando a string errada.

## Encerramento

`npm run lint` limpo, `npx vitest run` — 264 arquivos / 1450 testes passando (nenhum teste novo — a lógica de data em si já tinha cobertura em `chatDate.test.ts`, a correção foi só no valor passado pra ela), `npm run build` limpo.

**Arquivos:** `src/types.ts`, `src/components/WhatsAppLeadsSim.tsx`.

**Pendente ou risco:** validado só por typecheck/build, sem teste automatizado dedicado pro componente (não há suíte de teste pra `WhatsAppLeadsSim.tsx` — componente grande, fora do padrão de teste do repo, que foca em `server/services/*`); vale conferir visualmente numa conversa real de mais de um dia depois do deploy.
