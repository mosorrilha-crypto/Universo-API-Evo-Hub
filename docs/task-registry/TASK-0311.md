## Objetivo

TASK-0249 item 1: token de sessão sai do localStorage e vira cookie httpOnly

## Atualizações

Achado de segurança documentado na TASK-0249 (03/09/2026, nunca corrigido até
aqui): o JWT de sessão do operador (`saas_auth_token`) vivia em `localStorage`
em texto puro — diferente de PII exposta, isso era a SESSÃO INTEIRA, roubável
por qualquer XSS ou extensão maliciosa, com o mesmo nível de acesso do
operador logado (incluindo `saas_admin`). Este é o item de maior prioridade
da lista da TASK-0249; os outros 4 itens (CRM/financeiro/KB cacheados, config
da Meta CAPI) continuam deferidos para tasks separadas.

Migração feita como corte atômico (backend + frontend no mesmo deploy) — não
existe "modo duplo" seguro: se o token continuasse disponível em qualquer
lugar legível por JS (corpo da resposta, `localStorage`), a vulnerabilidade
persistiria. Isso é seguro aqui porque frontend e backend sempre são
construídos e implantados como uma única unidade (mesmo `dist/`, mesmo
processo Express servindo API e SPA, sem risco de descompasso de versão).

**Backend:**
- Nova dependência `cookie-parser` (+ `@types/cookie-parser`); `server.ts`
  monta `app.use(cookieParser())` antes dos routers.
- `server/routes/auth.ts`: login por senha e por Google passam a setar
  `res.cookie('universo_session', token, { httpOnly: true, secure:
  isProduction, sameSite: 'strict', path: '/', maxAge: 24h })` em vez de
  devolver `token` no corpo JSON. `GET /api/auth/session` passou a ler o
  cookie em vez do header `Authorization`. Nova rota `POST
  /api/auth/logout` (não existia nenhuma antes — só o servidor consegue
  apagar um cookie `httpOnly`, via `res.clearCookie` com as mesmas opções).
- `server/middleware/auth.ts` (`authenticateToken`): passou a ler
  `req.cookies.universo_session` em vez de `Authorization: Bearer`. Resto
  da verificação (jwt.verify, checagem de `tenantId`, header
  `X-Auth-Session-Invalid` no 403) não mudou.
- CSRF: não existia proteção alguma antes (não precisava — header
  `Authorization` só existe se o JS mandar). Um cookie é anexado
  automaticamente pelo navegador mesmo em requisições cross-site, o que
  abriria uma superfície nova nas ~141 rotas que mutam estado. Mitigado com
  `sameSite: 'strict'`, suficiente porque o app é 100% same-origin (sem
  nenhum fluxo cross-site legítimo que precise do cookie — nem o login
  Google, que só troca o ID token do Firebase por uma sessão via `fetch`
  same-origin depois do popup resolver).
- `server/routes/conversations.ts`: achado fora do escopo original do
  plano — a rota `GET /api/conversations/stream` (SSE) tinha sua PRÓPRIA
  verificação de JWT via querystring (`?token=`), porque `EventSource`
  nativo não manda header `Authorization`. Como `EventSource` manda
  cookies automaticamente em conexões same-origem (mesma regra do
  `fetch`), essa rota foi simplificada para usar o `authenticateToken`
  padrão — removido o `jwt.verify` manual e o `import jwt` (agora morto no
  arquivo).

**Frontend:**
- `src/lib/apiClient.ts`: removidos `TOKEN_STORAGE_KEY`, `readStoredToken`,
  `currentToken`, `setAuthToken`, `getAuthToken` e o header `Authorization`
  manual em `apiFetch` — o cookie já é enviado automaticamente
  (`credentials: 'same-origin'` é o padrão do Fetch API).
- `src/App.tsx`: o efeito de restauração de sessão perdeu o guard `if
  (!getAuthToken())` (o token agora é invisível pro JS por desenho) —
  sempre chama `GET /api/auth/session` e deixa o backend decidir. `onLogout`
  agora chama `POST /api/auth/logout` (só o servidor apaga um cookie
  `httpOnly`). Callback de login e `setUnauthorizedHandler` pararam de
  manipular token como string.
- `src/components/LoginModal.tsx`: `onLogin` perdeu o segundo parâmetro
  (token) — a sessão já chega via `Set-Cookie` da própria resposta de
  login.
- `src/components/WhatsAppLeadsSim.tsx`: a conexão SSE deixou de depender
  de `getAuthToken()` (removida a gate `if (token)`) — sempre abre a
  conexão, já que o cookie garante a autenticação.

**Testes:** `server/routes/__tests__/auth.test.ts` (+ `authGoogleLogin`,
`authOperatorBlocked`, `authLoginLockout`, `authChangePassword`,
`authTenantBlocked`) adaptados para `createAuthRouter({..., isProduction:
false})` e para extrair/repassar o `Set-Cookie` da resposta de login em vez
de ler `data.token`. `authChangePassword.test.ts` passou a mandar o JWT via
header `Cookie` em vez de `Authorization`. `conversationsStream.test.ts`
reescrito para usar o `authenticateToken` real (cookie) em vez do
`fakeAuthenticateToken`/`?token=` antigos — essa suíte era a cobertura real
de "sem sessão → 401" / "sessão inválida → 403" desta rota, então precisava
continuar testando o caminho de autenticação de verdade, não um mock que
sempre autentica. Dois testes de componente
(`WhatsAppLeadsSim.windowFilter.test.tsx`,
`WhatsAppLeadsSim.resyncAppointment.test.tsx`) ganharam um stub de
`EventSource` (jsdom 30 implementa um `EventSource` real que tentaria
conectar de verdade, já que a conexão deixou de ser condicional a "havia
token").

## Validação

`npm run lint` (tsc --noEmit), `npx vitest run` (270 arquivos / 1494 testes,
todos verdes) e `npm run build` rodaram limpos.

Verificação manual em produção (login por senha, login Google, F5 mantendo
sessão sem token em `localStorage`, logout de verdade, sessão inválida caindo
pro login) fica pendente — não automatizável neste ambiente, precisa ser
confirmada após o deploy.

## Riscos conhecidos

- **Aba já aberta antes do deploy**: uma aba com o bundle antigo (que ainda
  manda `Authorization: Bearer <token>`) vai começar a receber 403 sem
  `X-Auth-Session-Invalid` (o middleware novo não lê mais header) — não
  dispara o `onUnauthorized` automático, fica "travada" até um F5 manual.
  Janela pequena e única, só no deploy desta mudança.
- Os outros 4 itens da TASK-0249 (CRM/financeiro/KB cacheados em
  `localStorage`, config da Meta CAPI) continuam pendentes, tratados em
  tasks futuras separadas.
