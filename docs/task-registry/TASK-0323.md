# TASK-0323 — Corrige cache do index.html no servidor (causa provavel de nao ver mudancas apos deploy)

- **Iniciado em:** 2026-09-06T12:31:10.363Z
- **Agente/plataforma:** Claude
- **Issue central:** [#504](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/504)
- **Status:** concluído

## Objetivo

Depois do deploy confirmado ao vivo no Render (commit `3128cb2`, TASK-0321/
0322), o dono do produto reportou "não vejo nenhuma mudança ainda". O
service worker (`public/sw.js`) foi descartado como causa — é passthrough
puro, sem `event.respondWith`, comentário explícito no próprio arquivo
confirma que nunca fez cache. A causa raiz real estava em `server.ts`.

## Causa raiz

`server.ts` servia os arquivos estáticos (`express.static(distPath)`) e o
`index.html` (fallback SPA via `res.sendFile`) sem nenhum `Cache-Control`
explícito. Sem esse header, o navegador pode manter uma cópia antiga do
`index.html` em cache (o comportamento padrão varia entre navegadores/
condições de rede) — e como o `index.html` é o único lugar que referencia
os nomes de arquivo JS/CSS com hash da build atual, uma cópia antiga dele
continua carregando os arquivos da build ANTERIOR mesmo com o deploy novo
já no ar no servidor. Confirmado que não era só suspeita: reproduzi local
(build real + servidor Express isolado) e as respostas não tinham
`Cache-Control` nenhum antes da correção.

## Correção

`server.ts`: `express.static(distPath, { index: false, maxAge: '1y',
immutable: true })` — arquivos com hash no nome (imutáveis por definição,
Vite gera hash novo sempre que o conteúdo muda) podem ficar em cache por 1
ano; `index: false` impede que esse `maxAge` longo vaze pro `index.html`
quando ele seria servido por essa mesma camada. A rota de fallback da SPA
agora seta explicitamente `res.set('Cache-Control', 'no-cache, no-store,
must-revalidate')` antes do `res.sendFile(index.html)` — o navegador nunca
usa uma cópia em cache sem revalidar com o servidor primeiro.

Testado isoladamente (script descartável reproduzindo exatamente as duas
linhas de middleware, rodando contra o `dist/` real gerado pelo build desta
sessão): `index.html` → `Cache-Control: no-cache, no-store, must-revalidate`;
`assets/index-*.css` → `Cache-Control: public, max-age=31536000, immutable`.
Confirmado com `curl` local, não só lido no código.

## Validação

`npm run lint` limpo. `npx vitest run`: 272 arquivos, 1508 testes, todos
passando (nenhum teste cobria os headers HTTP do servidor antes; não
adicionei teste dedicado dado o escopo pequeno — validação feita via script
isolado real contra o build, não apenas leitura de código). `npm run build`
limpo.

## Pendente/risco

Isso corrige o problema PRA FRENTE (deploys futuros vão sempre servir a
build certa) — não resolve retroativamente uma cópia já em cache no
dispositivo do usuário agora. Recomendação imediata pro dono do produto:
fechar completamente a aba/app (não só trocar de aba) e reabrir, ou fazer
um refresh forçado/limpar cache do site, pra garantir que está vendo a
versão mais recente.
