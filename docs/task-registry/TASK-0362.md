# TASK-0362 — Corrige estouro do limite de tokens do Groq: pula o Groq (sem cache, sempre envia o prompt inteiro) quando o payload estimado excede o limite de 8000 TPM da conta, caindo direto pro Gemini

## Objetivo

Corrige estouro do limite de tokens do Groq: pula o Groq (sem cache, sempre envia o prompt inteiro) quando o payload estimado excede o limite de 8000 TPM da conta, caindo direto pro Gemini

## Contexto

Incidente ativo em produção, reportado direto ("identifique o pq o agente não está respondendo os novos leads"): zero respostas automáticas pra novos leads há 14h+ no tenant Monique. Investigação via logs reais do Render e schema do Supabase encontrou DUAS falhas simultâneas e independentes:
1. **Groq** (`especialista:${agent}:groq`, path Groq-primeiro introduzido pela TASK-0346 numa sessão concorrente): HTTP 413 "Request too large" em TODA chamada, todo tipo de agente — `Limit 8000, Requested [10.081-11.840]` tokens. O Groq não tem NENHUM mecanismo de cache (confirmado lendo `groqClient.ts` inteiro) — `callGroqJsonCompletion` manda o `systemInstruction` (Camada 1 + Base de Conhecimento) inteiro, achatado com o contexto dinâmico, em toda mensagem. O limite de 8.000 TPM desta conta pro modelo `openai/gpt-oss-120b` é avaliado sobre o tamanho cru do request na entrada — não existe cache que ajudaria mesmo que o Groq oferecesse um.
2. **Gemini** (fallback): HTTP 429 `RESOURCE_EXHAUSTED` "Your prepayment credits are depleted" — incidente já documentado no CLAUDE.md como recorrente, requer um humano recarregar em ai.studio/projects, fora do alcance de uma correção de código.

Pedido explícito do usuário depois do relatório das duas causas: **"só o problema do cachê"** — focar exclusivamente na correção estrutural do lado Groq, não na recarga de crédito do Gemini (ação humana, fora de escopo aqui).

## Mudança

`server/services/autoReply.ts`:
- Medido o tamanho real do `systemInstruction` combinado (Camada 1 + Base de Conhecimento) pro tenant Monique: **29.420-32.462 caracteres (~8.900-9.840 tokens estimados) SÓ na systemInstruction, antes mesmo de somar o contexto dinâmico (histórico, mensagem atual)** — ou seja, todo tipo de agente pra este tenant estrutural e permanentemente excede o limite de 8.000 TPM, não é um pico ocasional.
- Adicionada constante `GROQ_SPECIALIST_MAX_PROMPT_CHARS = 21_500` (heurística conservadora de ~3,3 caracteres/token, textos em português/espanhol acentuados tokenizam pior que inglês puro, aplicada a um alvo de ~6.500 tokens — abaixo dos 8.000 reais, com margem pro contexto dinâmico que só é conhecido depois de montar o prompt completo).
- Antes de chamar `callGroqJsonCompletion` no path do especialista, o tamanho do prompt combinado (`systemInstruction + flattenedUserContent`) é comparado contra esse teto. Quando excede, o Groq é pulado (com log explicando o motivo) e o fluxo cai direto pro Gemini de sempre — sem gastar o timeout/latência de uma chamada fadada a devolver 413, sem nenhuma mudança de conteúdo/qualidade da resposta final (que continua vindo do Gemini, exatamente como já acontecia no fallback de erro).
- Nenhuma mudança no path do roteador (`classifyAgent`) nem no de mídia (`decideMidiaActionViaGroq`) — ambos usam prompts muito menores (só uma classificação curta) e não fazem parte do incidente relatado (confirmado nos logs: só `especialista:*:groq` estava retornando 413).

**Efeito esperado pro tenant Monique especificamente:** com a Base de Conhecimento e REGRAS DE ESTILO atuais, o Groq será pulado em toda mensagem (o `systemInstruction` sozinho já excede o teto) — o agente passa a depender só do Gemini até (a) o crédito do Gemini ser recarregado (fora de escopo aqui) e/ou (b) uma futura redução adicional do prompt trazer o tamanho pra dentro do limite do Groq de novo. Isso é estritamente melhor que o comportamento atual (chamar o Groq, esperar o timeout de 12s, falhar com 413, só então cair pro Gemini) — mesma resposta final, sem o custo de latência e log de uma chamada garantidamente fadada ao erro. Pra tenants com Base de Conhecimento menor (a maioria, catálogos menores), o Groq continua sendo tentado normalmente.

**Pendente ou risco:**
- O problema do Gemini (crédito esgotado, 429) continua ativo e é responsabilidade de um humano recarregar em ai.studio/projects — enquanto isso não acontecer, o tenant Monique continua sem receber respostas automáticas mesmo com esta correção (ela só evita o desperdício da chamada Groq fadada ao erro, não substitui o Gemini).
- `GROQ_SPECIALIST_MAX_PROMPT_CHARS` é uma estimativa por caracteres, não uma contagem real de tokens — pode ser conservadora demais ou otimista demais dependendo do texto real; recomendo observar os logs de produção (`⚠️  [Especialista] Prompt do Groq (...) excede o teto...` vs. `413` residuais) por alguns dias e ajustar o valor se necessário.
