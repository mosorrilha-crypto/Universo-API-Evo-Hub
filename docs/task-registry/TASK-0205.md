## Objetivo

Debounce no refetch da lista de conversas disparado por cada evento SSE, reduzindo egress do Supabase

## Contexto

Usuário relatou ser deslogado do painel com "senha incorreta" — investigação
via `mcp__Render__list_logs` achou o erro real do Supabase: `Service for
this project is restricted due to the following violations:
exceed_egress_quota`. Confirmado no dashboard do Supabase
(`Organization → Usage`): 31,29 GB de egress usados no ciclo atual (limite
5 GB do Free Plan), com só 161 MB armazenados no Storage e 83 MB de banco —
ou seja, a mesma mídia/dado pequeno sendo transferido repetidas vezes, não
um volume de dados real grande. O gráfico "Egress per day" mostra subida
gradual desde ~09/08, sustentada (~1,5-3GB/dia) até hoje — descarta a
hipótese inicial do usuário de que PRs/deploys de hoje seriam a causa (CI
usa banco falso em memória, nunca toca o Supabase real; e o padrão não bate
com picos isolados em dias de deploy).

## Achado

`WhatsAppLeadsSim.tsx` — o `useEffect` que abre o `EventSource` de
`/api/conversations/stream` chamava `fetchRealConversations()` (um `GET
/api/conversations?archived=true` completo) incondicionalmente em **todo**
`source.onmessage`, mesmo pra eventos irrelevantes pra lista (ex: só um
`aiReplyStatus` "entregue"/"lida"). Cada mensagem real do WhatsApp gera
pelo menos 3 desses eventos (enviada/entregue/lida) — com o painel aberto
o dia todo, isso soma um número alto de refetches completos da lista de
conversas por hora, mesmo com poucas mensagens novas de verdade.

## Correção

Debounce de 400ms no `source.onmessage`: em vez de chamar
`fetchRealConversations()` direto, agenda a chamada com `setTimeout` e
cancela/reagenda (`clearTimeout`) a cada novo evento que chegar antes do
timer disparar — uma rajada de eventos próximos (comum quando várias
mensagens/status chegam quase juntos) vira uma única busca. Comportamento
percebido não muda: a conversa aberta já atualiza via
`loadRealConversationHistory` (chamado à parte, sem debounce, no mesmo
handler), e 400ms de atraso na lista de fora da conversa aberta não é
perceptível.

`fetchConversationsDebounceRef` (novo `useRef`) guarda o timer; limpo tanto
antes de reagendar quanto no cleanup do `useEffect` (troca de tenant/
desmonte), evitando o timer disparar depois que o efeito já foi
desmontado.

## Validação

- `npm run lint` (tsc --noEmit) — limpo.
- `npx vitest run` — 237 arquivos / 1275 testes, todos passando.
- `npm run build` — limpo.
- Não escrevi teste automatizado novo (não há suíte de testes de
  componente/E2E pro `WhatsAppLeadsSim.tsx` neste repositório — os testes
  existentes são todos de backend). Verificação é por leitura do código:
  o debounce não altera nenhuma outra branch de `onmessage` (o parsing de
  `aiReplyStatus`/`loadRealConversationHistory` continua rodando sem
  atraso, só o `fetchRealConversations()` foi adiado/agrupado).

## Pendente/risco

- Este fix reduz uma fonte real e concreta de egress, mas eu não tenho
  visibilidade granular (Database vs Storage vs Realtime) do dashboard do
  Supabase pra confirmar que essa é a ÚNICA ou a MAIOR fonte — pode haver
  outras (jobs de fundo, outras rotas). Recomendo ao usuário acompanhar o
  gráfico de "Egress per day" nos próximos dias (o ciclo atual reseta em
  03/09) pra ver se o consumo diário cai visivelmente depois deste deploy.
- Não fiz self-merge por prudência (é uma mudança de comportamento em
  tempo real do painel principal, mesmo sendo pequena) — abrindo PR normal.
