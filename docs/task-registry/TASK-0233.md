# TASK-0233 — Corrige falso positivo sistemico de lista numerada no juiz da avaliacao automatica

## Objetivo

Corrige falso positivo sistemico de lista numerada no juiz da avaliacao automatica

## Atualizações

Dono do produto rodou 15 perguntas sintéticas — **as 15 reprovaram** — e
suspeitou de bloqueio excessivo, mostrando um caso onde "Resposta real que
a IA deu" e "Como deveria ter respondido" eram praticamente idênticas.

Consultei os 15 achados direto no banco (`quality_reviews`,
`context->>'source'='synthetic_eval'`, rodada `agent_eval_runs` id
`704bf0ec`, started_at 05:10:21). Achado crítico: praticamente todo achado
citava "Qualidade: uso de lista numerada" / "formato de lista numerada"
como problema — mas nenhum `original_value` real continha "1."/"2."
nenhum, sempre só duas frases separadas por `\n`, o formato correto de
bolhas de WhatsApp.

**Causa raiz encontrada em `buildJudgePrompt` (`agentEvalService.ts`):** a
seção "RESPOSTA DO ATENDENTE A AVALIAR" mostrava as bolhas pro juiz
formatadas como `${i + 1}. ${b}` — ou seja, "1. bolha1\n2. bolha2". Essa é
uma marcação de REFERÊNCIA que só existe pra o juiz saber onde uma bolha
termina e a outra começa (nunca visível pro cliente real — cada bolha é
mandada como uma mensagem separada do WhatsApp, sem número nenhum). O juiz
(gemini-3.5-flash-lite) estava confundindo essa numeração nossa com um
defeito real de formatação da resposta, reprovando quase toda resposta de
2 bolhas por um "problema" que só existia na forma como avaliamos, nunca
na mensagem que o cliente realmente recebe. Isso explica a taxa de
reprovação artificialmente alta em TODAS as rodadas desde que a avaliação
automática existe (TASK-0203/0208) — não só nesta.

Corrigido: bolhas agora marcadas como `[BOLHA N]` no prompt do juiz (sem o
padrão "N." que visualmente é uma lista numerada de verdade), com uma
instrução explícita dizendo que essa marcação é só de referência desta
avaliação e nunca deve, por si só, ser motivo de reprovação.

**Segundo achado, menor:** 2 dos 15 casos ainda quebraram com "Erro: Falha
ao avaliar: Expected double-quoted property name in JSON" — mesmo erro da
TASK-0228, mesmo depois daquele fix estar em produção (confirmado: a
rodada começou às 05:10:21, bem depois do deploy do TASK-0228/PR#607 às
~05:03). A causa exata dessa malformação específica continua desconhecida
— o texto bruto que falha nunca fica registrado em lugar nenhum, só a
mensagem de erro genérica. Corrigido (`geminiJson.ts`): quando nenhuma
camada de recuperação funciona, o erro relançado agora inclui um trecho
(300 chars) do texto bruto recebido, pra dar evidência de diagnóstico na
próxima ocorrência em vez de continuar chutando.

`npm run lint`, `npx vitest run` (253 arquivos / 1392 testes, incluindo
novo teste em `geminiJson.test.ts` confirmando que o texto bruto aparece
na mensagem de erro) e `npm run build` passando limpo antes do commit.

**Arquivos/commits:** `f091021`, branch `claude/gestor-refinamento-atendimento-mwu1a7`
— `server/services/agentEvalService.ts`, `server/services/geminiJson.ts`,
`server/services/__tests__/geminiJson.test.ts`.

**Pendente ou risco:** este é provavelmente o achado de maior impacto de
toda a sessão de avaliação automática — recomendo fortemente que o dono
do produto rode outra rodada depois deste deploy pra confirmar que a taxa
de aprovação sobe de forma real (não só que "lista numerada" some, mas
que o número de `pass_count` aumente de verdade). Os 2 casos de JSON
malformado continuam sem causa raiz identificada — só diagnosticável na
próxima ocorrência, com o texto bruto agora anexado ao erro.
