## Objetivo

Botão Desconectar WhatsApp (Evolution API) — logout sem apagar a instância

## Atualizações

Pedido direto do dono do produto ("mas tem que ter esse botão se um tenant quiser desconectar"), depois de uma investigação de "fotos ainda não carregam" que revelou um achado real e distinto: o mesmo número de celular pessoal do dono do produto estava conectado simultaneamente como número da própria instância WhatsApp de dois tenants diferentes (Monique - Evolution e um tenant de teste próprio, "Lucas Vinicius") — WhatsApp/Baileys entrega toda a atividade do dispositivo pra TODA instância vinculada a ele (multi-device mirroring), o que gerava webhooks duplicados (mesmo `message_id`) chegando em ambos os tenants. A tela "Reconectar WhatsApp (Evolution API)" só tinha "Reconectar/Gerar QR Code" e "Recriar instância do zero" (apaga + recria, sempre exige novo QR) — nenhuma opção pra só encerrar a sessão atual sem perder o cadastro da instância, o que o operador precisaria pra tirar um número específico de um tenant sem destruir a instância.

**Mudança:**
1. **Backend** (`server/routes/admin.ts`): novo `POST /api/admin/tenants/:id/evolution-instance/disconnect`, ao lado de `/recreate`. Reaproveita `resolveEvolutionTenantId` (mesmo isolamento por tenant — `saas_admin` usa o `:id` da URL, qualquer outro papel sempre resolve pelo `tenantId` do JWT) e `assertValidHttpUrl` (guarda SSRF já usada nas rotas vizinhas). Chama `DELETE /instance/logout/:name` na Evolution API — o MESMO endpoint que `/recreate` já chama como primeiro passo best-effort, mas aqui é o passo final: uma falha real (não-404) devolve 502 em vez de seguir silenciosamente, já que o operador pediu essa ação deliberadamente. HTTP 404 do lado da Evolution API (instância já deslogada/inexistente) é tratado como sucesso, mesmo critério já usado em `/recreate`. Não mexe em `last_connection_state`/`disconnected_since` — o job periódico `evolutionConnectionAlertJob.ts` já reconsulta e atualiza essas colunas sozinho a cada 5min, mesmo padrão que `/recreate` também já segue.
2. **Frontend** (`src/components/ReconectarWhatsAppQrCode.tsx`): novo botão "Desconectar este número" (ícone `Unlink`, cor âmbar — distinto do vermelho de "Recriar instância do zero"), visível só quando `connectionState === 'connected'`, com confirmação (`window.confirm`) explicando que mensagens de clientes param de chegar até reconectar. Em caso de sucesso, reseta o estado local pra `'idle'` (o botão de reconectar/QR Code volta a aparecer).

**Arquivos:** `server/routes/admin.ts`, `src/components/ReconectarWhatsAppQrCode.tsx`, `server/routes/__tests__/adminEvolutionInstance.test.ts` (5 casos novos: sucesso, logout 404 tratado como sucesso, falha real → 502, tenant sem instância → 404, 403 pra role `operator`; mais 1 caso no describe de escopo por tenant confirmando que `:id` de outro tenant na URL não desvia o logout do tenant do próprio JWT).

**Validação:** `npm run lint` (tsc --noEmit) limpo; `npx vitest run` — 300 arquivos / 1701 testes passando (inclui os 6 novos casos, +40 no arquivo `adminEvolutionInstance.test.ts` no total); `npm run build` — build completo sem erros (chunk `unlink-*.js` confirma o novo ícone compilado). Revisão manual do diff: rota nova segue exatamente a mesma estrutura/guardas de segurança de `/recreate` (mesma linha acima no arquivo), sem duplicar lógica.

**Pendente ou risco:** nenhum risco técnico novo — reaproveita primitivas (`/instance/logout`, `resolveEvolutionTenantId`, `assertValidHttpUrl`) já testadas e em produção via `/recreate`. Toca mensageria/credenciais Evolution de tenant (área crítica) — revisão explícita solicitada, sem self-merge. A causa raiz real do "fotos ainda não carregam" (falha silenciosa no download fire-and-forget de mídia recebida, `webhooks.ts`) continua em aberto — esta tarefa resolve o achado colateral (número duplicado entre tenants), não o 404 de imagem em si; retry + log durável (`system_incidents`) foi oferecido ao dono do produto e ainda não confirmado.
