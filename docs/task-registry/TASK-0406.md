## Objetivo

Implementar o fix 2a do plano aprovado em `docs/CHECKLIST-VIABILIDADE-COMERCIAL.md` (TASK-0405): remover os 2 prompts hardcoded de "estética/micropigmentação" em `server/services/autoReply.ts`, que violavam a decisão de 14/08/2026 de zero regra/vertical hardcoded em código (`docs/AGENTE-VERTICAL-ARQUITETURA.md`).

## Atualizações

**Fix 2a (implementado):**
- `server/services/autoReply.ts:1241` — prompt de classificação de consulta via Groq: `"Classifique a mensagem de um cliente de um negócio de estética/micropigmentação..."` → `"Classifique a mensagem de um cliente deste negócio..."`.
- `server/services/autoReply.ts:1686` — prompt da ferramenta de agendamento: `"Você controla a agenda real de um negócio de estética/micropigmentação através de ferramentas..."` → `"Você controla a agenda real deste negócio através de ferramentas..."`.
- Mudança puramente textual — sem alteração de lógica, schema, tools ou labels de categoria. Os testes existentes de `autoReply.ts` cobrem o formato/comportamento das ferramentas, não o texto literal do prompt, então nenhum teste precisou mudar.
- Com isso, o item "zero edição de código para um segundo segmento" (achado 2 do checklist) pode ser marcado como resolvido.

**Fix 2b (NÃO implementado — achado durante a execução, corrige uma premissa errada do plano aprovado):**

O plano (TASK-0405) presumia que `human_handoff_rules` era um campo de conteúdo como qualquer outro dos 8 documentos tipados, só que vazio especificamente na KB do Dr. Daniel, e propunha um finding de completude em `src/lib/knowledgeBaseAudit.ts` no mesmo padrão do finding `operation-hours`. Investigando antes de implementar, isso não é verdade:

- `human_handoff_rules` **não faz parte de `AgentKnowledgeBase`** (o tipo visual do frontend) nem de `VISUAL_KNOWLEDGE_BASE_DOCUMENT_TYPES` (`src/lib/knowledgeBaseVisualDocuments.ts:9-16`) — não existe nenhum campo do formulário que serialize para esse documento.
- No backend, `server/services/knowledgeBaseStore.ts:572-574` trata esse tipo com um `case` vazio (`break;`) — zero validação, zero schema de conteúdo.
- `src/components/KnowledgeBaseDocumentation.tsx:108-111` já documenta isso explicitamente: "Nesta versão, não possui campos editáveis no documento; os gates humanos existentes continuam obrigatórios."
- Em todo o repositório (fixtures de teste incluídas), `human_handoff_rules` é sempre `data: {}` — **para todos os tenants, não só o Dr. Daniel.** Um comentário já registrado em `src/components/AgentKnowledgeBase.tsx:2568-2579` (auditoria de UX de 12/09/2026) confirma o mesmo achado por outro ângulo: o card "Encaminhamento humano" na navegação nem aponta para um campo real.

Ou seja: é um documento propositalmente reservado/placeholder nesta versão do produto (decisão de produto, não bug), e não uma lacuna de completude específica de um tenant. Adicionar um finding de "vazio" nesse campo dispararia incondicionalmente para 100% dos tenants, sempre, sem nada que o operador possa preencher para resolvê-lo — o oposto de um finding acionável. Implementar o fix como especificado geraria ruído permanente, não sinal. Por isso não foi implementado.

**Ação pendente:** corrigir o achado 3 de `docs/CHECKLIST-VIABILIDADE-COMERCIAL.md` (ainda na PR #775, TASK-0405, não mesclada) — a caracterização de "gap de auditoria pequeno e independente" para `human_handoff_rules` está incorreta; deve virar um item de **decisão de produto em aberto** (criar campos estruturados de escalonamento humano, quando fizer sentido) em vez de um "fix de 3 linhas". Reportado ao dono do produto nesta sessão; será corrigido como fast-follow na própria PR #775 ou logo após ela mesclar.
