## Objetivo

Roteador distingue dor como motivo de consulta nova de reclamação sobre atendimento que o próprio negócio realizou

## Atualizações

**Achado real** (pedido direto do usuário: "Analiza as últimas conversas do agente do dr Daniel e verifica se ele está atendiendo bem os clientes dele" — auditoria de conversas reais desde o deploy do `leads_only`, 14-17/09/2026): a classificação `"reclamacao"` do roteador (Camada 1, `classifyAgent`/`buildRouterPrompt`) tinha como exemplos "resultado, dor, alergia, reação" — escrito pensando num negócio de estética (Monique), onde dor pós-procedimento normalmente significa que algo deu errado. Numa clínica de fisioterapia, porém, "dor" é o motivo NORMAL de um paciente novo procurar atendimento — não uma reclamação.

Por política deliberada (Epic 4.5.8, `webhooks.ts`), `reclamacao` NUNCA envia resposta automática — só escala em silêncio pro operador ("a IA nunca resolve reclamação sozinha"). Confirmado em produção: a primeira mensagem do paciente Aldo Silva ("Estou com uma perna minha, posterior de coxa") foi classificada como `reclamacao` e ficou sem nenhuma resposta automática — só a mensagem seguinte dele recebeu resposta normal. Sem dano real nesse caso (ele continuou escrevendo), mas é um risco estrutural: como "dor" é o motivo mais comum de contato numa fisioterapia, esse padrão tende a se repetir.

**Correção**: `buildRouterPrompt` (`server/services/autoReply.ts`) agora deixa explícito que `reclamacao` exige que a dor/problema tenha sido CAUSADO pelo próprio negócio num atendimento anterior — descrever um sintoma como motivo de buscar consulta agora (mesmo mencionando "dor") cai em triagem/faq/agendamento normalmente, nunca em reclamacao, a menos que o cliente diga explicitamente que foi o negócio quem causou/piorou o sintoma. Mudança na Camada 1 (roteador, global) — vale pra todos os tenants (Monique continua coberta pro caso real dela: reação/dor pós-procedimento).

**Também verificado nesta auditoria (sem necessidade de correção)**: modo `leads_only` filtrando corretamente 208 mensagens pessoais sem nenhum falso positivo na amostra revisada; revisor de segurança (`replySafetyGate.ts`) bloqueando 10 rascunhos arriscados reais antes do envio (resposta repetida, dado de pagamento sem confirmação humana, contradição de disponibilidade) — 1 falso positivo observado (bloqueio por "idioma não preservado" numa conversa 100% em português), sem impacto real no paciente (operador assumiu em minutos); dois fluxos reais de agendamento (Silmara Gonçalves, Aldo Silva) terminaram em consulta marcada, com o padrão consultivo (TASK v7 do `brand_voice`) funcionando — preço só informado quando perguntado, nunca horário inventado.

**Testes novos**: `autoReplyAgentClassificationPrompt.test.ts` — novo caso confirmando que o prompt do roteador contém a distinção explícita, usando a mesma frase real do achado ("Estou com uma dor na perna, posterior de coxa").

**Verificação**: `npm run lint` / `npx vitest run` (314 arquivos, 1800 testes) / `npm run build` — todos limpos.
