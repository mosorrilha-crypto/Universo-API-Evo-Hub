## Objetivo

corrige falso positivo: foto comum vira 'possível comprovante de pagamento' quando há agendamento aguardando pagamento

## Atualizações

Surgiu de uma auditoria pedida direto ("faz uma auditoria no sistema... busque pontos de melhorias que ainda não identificamos"), que levantou um backlog real de 133 escalonamentos abertos (88 com mais de 7 dias), 52 deles rotulados como comprovante de pagamento nunca verificado — concentrados majoritariamente no tenant Dr. Daniel Oliveira (102 dos 133). Logo depois, o dono do produto confirmou direto: "Fotos comuns estão sendo classificadas como comprovante".

**Causa raiz confirmada no código:** `server/routes/webhooks.ts` (ramo `msg.type === 'image'`) já chamava `analyzePaymentReceiptWithGemini` (`paymentReceiptAnalysis.ts`) pra analisar o CONTEÚDO de qualquer imagem recebida enquanto o contato tem um agendamento com `payment_status` ausente ou `'awaiting_payment'` — mas o campo `looksLikeReceipt` devolvido pela análise NUNCA era usado pra decidir nada. Só o texto da dica (`hint`) entrava, de forma cosmética, no texto do escalonamento. Resultado: QUALQUER foto (selfie, print qualquer, foto de um pet) chegando nessa janela de tempo virava "possível comprovante de pagamento" — marcava `payment_status='pending_verification'` no agendamento de verdade e abria um escalonamento `payment_proof`, mesmo quando a própria análise da Gemini já tinha identificado corretamente que não era um comprovante (ex: hint "foto de rosto/selfie").

**Fix:** adiciona o gate que faltava — `if (analysis && analysis.looksLikeReceipt === false) return;` logo depois da análise, antes de `markPaymentPendingVerification`/`logEscalation`/`createQualityReview`. Mantém o fallback seguro de sempre quando a análise não roda ou falha (`analysis === null`, ex: Gemini indisponível) — nesse caso continua tratando como possível comprovante, igual a antes, pra nunca arriscar perder um comprovante de verdade por indisponibilidade do provedor. Só pula o fluxo de comprovante quando a análise RODOU e disse explicitamente que não parece um.

**Arquivos/commits:** `server/routes/webhooks.ts`, `server/routes/__tests__/webhooksPaymentProofFalsePositive.test.ts` (novo, 3 casos: nega corretamente quando `looksLikeReceipt:false`, continua escalando quando `true`, continua escalando quando a análise falha/`null`).

**Validação:** `npm run lint`, `npx vitest run` (329 arquivos / 1871 testes, incluindo os 3 novos) e `npm run build` — todos limpos. O teste do caso corrigido foi confirmado falhando sem o fix (via `git stash` temporário) — a escalação `payment_proof` era criada mesmo com `looksLikeReceipt:false` — e passando com ele.

**Pendente ou risco:** este fix impede a produção de NOVOS falsos positivos a partir de agora, mas não limpa o backlog já existente — os 133 escalonamentos abertos levantados na auditoria (muitos provavelmente fotos comuns classificadas erroneamente antes deste fix) continuam na fila como estavam, precisam de triagem manual por um operador. Recomendo revisar esse backlog (em especial o do tenant Dr. Daniel Oliveira) separadamente, já que parte dele deve ter sido causada exatamente por este bug.
