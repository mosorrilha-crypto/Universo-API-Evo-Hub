# TASK-0168 — Corrige foto de exemplo enviada pela IA aparecendo Imagem indisponível no painel (binario nunca era salvo, so o texto)

- **Iniciado em:** 2026-08-30T02:19:32.109Z
- **Agente/plataforma:** Claude
- **Issue central:** [#290](https://github.com/mosorrilha-crypto/Universo-API-Evo-Hub/issues/290)
- **Status:** concluído

## Objetivo

Corrige foto de exemplo enviada pela IA aparecendo Imagem indisponível no painel (binario nunca era salvo, so o texto)

## Atualizações

Print real do dono do produto: duas mensagens marcadas "IA" (verde) no
painel, ambas mostrando "Imagem indisponível" em vez do preview real da
foto de exemplo enviada — "as fotos não estão abrindo não sei qual foi
enviada". A foto chegava normal no WhatsApp real do lead (confirmado
pelo texto "📷 Foto de exemplo: ..." e pelo horário/check azul de
entregue), só o painel não conseguia mostrar de volta.

Causa raiz: `runMidiaTool` em `autoReply.ts` tem dois ramos praticamente
idênticos — `enviar_video_exemplo` e `enviar_foto_exemplo`. O ramo de
vídeo já tinha sido corrigido antes (achado real, 15/08/2026, Clic
Piscinas): gera um `messageId` antes de gravar, salva o binário em
`mediaImageStore` sob esse id, e passa o id como `customId` pro
`recordOutgoingMessage`. O ramo de **foto** nunca recebeu o mesmo fix —
só chamava `recordOutgoingMessage` com o texto
`"📷 Foto de exemplo: X"`, sem nunca salvar o binário. `GET
/api/media/:messageId` (usado pelo componente `RealClientImage` no
painel) nunca encontrava nada pra essas mensagens, caindo no fallback
"Imagem indisponível" pra sempre. O envio **manual** (operador clicando
no seletor de foto, `POST /send-example-photo` em `conversations.ts`)
já fazia isso certo — só o envio **automático da própria IA** ficou pra
trás.

Corrigido espelhando exatamente o padrão já usado no ramo de vídeo e no
`/send-example-photo` manual: gera `photoMessageId` antes de gravar,
chama `saveMediaImage(mediaConfig.supabaseUrl, mediaConfig.supabaseKey,
photoMessageId, photoMedia.exampleImageBase64, mimeType)`, e passa
`photoMessageId` como `customId` (7º argumento) pro
`recordOutgoingMessage`.

Teste atualizado (`autoReply.test.ts`, describe "ferramenta de envio de
foto"): a asserção existente ganhou `saveMediaImage` no mock e verifica
que foi chamado 1x com o mimeType certo, e que o `customId` passado pro
`recordOutgoingMessage` bate com o `messageId` usado em
`saveMediaImage` — mesmo padrão já usado no teste equivalente de vídeo.

Entregue: `server/services/autoReply.ts`,
`server/services/__tests__/autoReply.test.ts`.

## Encerramento

**Status: concluído.** Não toca autenticação/isolamento de tenant;
toca o caminho de mensageria real (envio automático da IA), mas de
forma aditiva (só adiciona a persistência do binário, não muda o envio
real pro WhatsApp) — mesmo padrão já em produção pro vídeo e pro envio
manual de foto. Self-merge autorizado dado o precedente idêntico já
mesclado sem incidentes. Validação: `npm run lint`, `npx vitest run`
(228 arquivos, 1184 testes, incluindo o teste atualizado) e
`npm run build`, todos limpos.

**Pendente ou risco:** não foi possível reproduzir end-to-end com o
Storage real do Supabase (sandbox sem credenciais) — a validação foi
via teste unitário com `saveMediaImage` mockado, mas o mesmo mock/
padrão já valida o caminho de vídeo em produção há duas semanas sem
problema. Recomendo conferência do dono do produto pedindo pra IA
mandar uma foto de exemplo e conferindo se abre no painel desta vez.
