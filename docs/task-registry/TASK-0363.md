## Objetivo

Impersonação: saas_admin acessa como um operador específico (audit trail, banner de aviso)

## Atualizações

**Contexto:** pedido real do dono do produto, logado como saas_admin: "eu
consigo trocar de empresa, mas se ela tem operadores eu não consigo
selecionar eles" — o seletor de tenant (`Header.tsx`) só troca de empresa,
nunca de identidade; a tela de gestão de operadores
(`SaaSAdminDashboard.tsx`) já permitia editar dados de um operador (role,
credenciais, bloqueio), mas não havia jeito de ver/usar o painel
EXATAMENTE como aquele operador — útil pra depurar um problema de
permissão real ou reproduzir um bug que só acontece pra determinado role.

Decisões confirmadas com o dono do produto: qualquer role pode ser
impersonado exceto `saas_admin` (nunca um saas_admin se escondendo atrás
de outro); motivo da impersonação fica opcional no formulário.

**Investigação (1 agente Explore) confirmou a arquitetura de auth atual:**
sessão é um único cookie httpOnly (`universo_session`, JWT `{id, tenantId,
role}`, sem tabela de sessão no banco); `GET /api/auth/session` sempre
revalida contra a linha real do operador; RLS do Postgres só verifica
`tenant_id` (nenhuma policy usa `sub`/`app_role`), então impersonar é
inteiramente uma troca de identidade na camada de aplicação, sem impacto
na granularidade de isolamento de dados.

**Implementado — mecanismo: troca stateless do MESMO cookie de sessão,
sem tabela de sessão nova:**
- `supabase/migrations/0081_operator_impersonation_events.sql` — tabela
  append-only de auditoria (`tenant_id, target_operator_id, actor_id,
  event_type: started|ended, reason, created_at`), mesmo padrão de
  `escalation_audit_events`. **Já aplicada em produção via Supabase MCP.**
- `server/services/operatorImpersonationStore.ts` (novo) —
  `recordOperatorImpersonationEvent`: diferente da jornada do contato
  (best-effort), uma falha AQUI bloqueia a troca de sessão — nunca
  acontece sem deixar rastro auditável.
- `POST /api/admin/operators/:id/impersonate` (`server/routes/admin.ts`,
  `requireRole('saas_admin')` — mais restrito que as outras rotas de
  operador, que usam `requireRole('admin')`): valida alvo (existe, não é
  saas_admin, não está bloqueado, não é o próprio chamador), grava o
  evento `started` (ANTES de trocar o cookie), assina um JWT novo com a
  identidade do ALVO + `impersonatedBy: <id do saas_admin>`, expiração
  menor que login normal (2h vs 24h, reduz janela de risco de sessão
  esquecida aberta), regrava o MESMO cookie `universo_session`.
- `POST /api/auth/end-impersonation` (`server/routes/auth.ts`, só
  `authenticateToken` — quem chama já É o operador impersonado, pode ter
  qualquer role): lê `req.user.impersonatedBy`, revalida o saas_admin
  original contra o Postgres (ainda existe, ainda é saas_admin, ainda
  ativo), grava o evento `ended`, assina um JWT fresh de 24h pra ele,
  restaura o cookie.
- `GET /api/auth/session` ganhou o campo `impersonation: { active,
  byOperatorId, byOperatorName }` (lido do claim `impersonatedBy` do JWT
  atual) — é o sinal que o frontend usa pra mostrar a faixa de aviso.
- `SESSION_COOKIE_NAME`/`sessionCookieOptions` exportados de `auth.ts` e
  reaproveitados em `admin.ts` (mesmas opções de cookie em toda troca de
  sessão, um único lugar de verdade).

**Frontend:**
- `SaaSAdminDashboard.tsx` — botão "Acessar como" (ícone `LogIn`) na linha
  de cada operador, oculto pra linhas `saas_admin` e pra si mesmo,
  desabilitado se o operador estiver bloqueado. Confirmação +
  `window.prompt` opcional pro motivo → `POST
  /api/admin/operators/:id/impersonate` → reload completo
  (`window.location.href = '/'`) pra todo o app reinicializar já como o
  operador alvo, sem cirurgia de estado parcial.
- `App.tsx` — novo estado `impersonation`, populado por `GET
  /api/auth/session`. Faixa de aviso persistente (âmbar, `sticky top-0`,
  fora do wrapper que se esconde com conversa aberta no mobile — sempre
  visível, em qualquer aba/tela) com "Voltar para admin", que chama `POST
  /api/auth/end-impersonation` e recarrega a página.

**Testes novos:** `adminOperatorImpersonate.test.ts` (6 casos: sucesso com
motivo + evento gravado, bloqueia outro saas_admin, bloqueia operador
inativo, bloqueia impersonar a si mesmo, 404 pra alvo inexistente, bloqueia
admin comum); `authEndImpersonation.test.ts` (5 casos: restauração
bem-sucedida + evento ended, recusa sem `impersonatedBy`, recusa se o
saas_admin original foi bloqueado, `GET /api/auth/session` expõe
`impersonation` corretamente nos dois estados).

**Validação:** `npm run lint` (limpo), `npx vitest run` (284 arquivos /
1572 testes, suíte completa) e `npm run build` (limpo). Migração aplicada
em produção via Supabase MCP `apply_migration`; `get_advisors` (security)
só aponta o INFO esperado "RLS enabled, no policy" — mesmo padrão de
referência.

**Pendente ou risco:**
- Sem dispositivo/browser real nesta sessão pra validar visualmente o
  botão "Acessar como" e a faixa de aviso — pedir confirmação visual do
  dono do produto antes/depois do merge.
- Trocar o cookie afeta TODAS as abas do mesmo navegador (mesmo cookie
  httpOnly compartilhado) — abrir uma impersonação numa aba troca a
  sessão em qualquer outra aba aberta do painel. Mesma limitação que já
  existe hoje pra logout, não é uma regressão nova; vale documentar no PR.
- Sessão impersonada expira em 2h (mais curto que o login normal de 24h)
  — se isso incomodar na prática (esquecer aberta durante uma investigação
  longa), é fácil ajustar o valor depois.
- Não há UI de auditoria (listar/consultar `operator_impersonation_events`
  no painel) — os eventos ficam gravados no banco, mas só consultáveis via
  SQL/Supabase direto por enquanto; pode virar uma tarefa futura se o dono
  do produto quiser revisar o histórico pelo painel.
