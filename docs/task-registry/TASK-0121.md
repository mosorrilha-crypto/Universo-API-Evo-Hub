## Objetivo

Auditoria e correção do CodeQL na PR #496 (guards de entitlement Qualidade/Agenda)

## Atualizações

**Contexto:** dono do produto pediu pra auditar e mesclar a PR #496 (aberta pelo Manus.Ai, branch `manus/quality-agenda-entitlement`), que adiciona guards fail-closed de entitlement pra Qualidade (`quality.agent_review`) e Agenda (`booking.calendar`) nas rotas de `conversations.ts`, `googleCalendar.ts` e `qualityAudit.ts`.

**Auditoria da lógica (aprovada sem ressalvas):** `agendaModuleAccess.ts`/`qualityModuleAccess.ts` seguem o mesmo padrão fail-closed já em produção em `financialModuleAccess.ts` (`try { resolve } catch { return false }`). Os middlewares `requireAgendaModule()`/`requireQualityModule()` fazem bypass explícito só pra `role === 'saas_admin'` (que administra a liberação por tenant) e retornam 403 com `code` estável nos demais casos. Confirmado via Supabase que o fluxo de booking automático do agente (Gemini function-calling em `autoReply.ts`) não passa por essas rotas HTTP — só ações manuais do painel são protegidas. Testes novos da PR cobrem os casos habilitado/desabilitado/bypass saas_admin.

**Achado real durante a auditoria (não bloqueante, confirmado com o dono do produto):** o tenant "Clic Piscinas - Evolution" (`0fa19ec1-...`) tem overrides desabilitando `booking.calendar`/`quality.agent_review` (e outras features) criados no mesmo dia, em sequência rápida, com motivo genérico "P" — parecia teste manual de admin, mas o dono do produto confirmou que esse tenant genuinamente não usa Agenda, então não é regressão.

**CodeQL bloqueando o merge — 3 tentativas erradas antes de achar a causa real:** o check CodeQL falhava com "1 new alert including 1 high severity" sem expor arquivo/linha/regra via nenhuma ferramenta disponível nesta sessão (API de check-runs não expõe `annotations`, sem acesso à UI de Security do GitHub). Assumi (errado) que seria `js/log-injection`/`js/clear-text-logging` nos `console.warn` novos de `agendaModuleAccess.ts`/`qualityModuleAccess.ts` (idêntico a um padrão já existente, não sinalizado, em `financialModuleAccess.ts`) e tentei 3 correções sucessivas nessas linhas (coagir erro pra string; sanitizar `\r\n`; remover todo dado dinâmico do log) — o alerta persistiu **idêntico** nas 3, inclusive com zero dado dinâmico logado, o que provou que a causa era outra. O dono do produto abriu a UI do GitHub (Security → Code scanning) e confirmou a regra real: **`js/missing-rate-limiting`**, em `server/routes/googleCalendar.ts:97` — a rota `GET /api/google-calendar/connect` (gera a URL de consentimento OAuth do Google Calendar) faz autorização (checagem de entitlement da Agenda + role admin) sem nenhum limite de requisições.

**Fix real:** novo `googleCalendarConnectRateLimiter` (10/min por IP) em `server/middleware/rateLimit.ts`, seguindo o mesmo padrão dos limiters já existentes no arquivo (`aiRateLimiter`, `authSessionRateLimiter` etc.), aplicado na rota `/connect` logo após `authenticateToken` (mesma ordem usada em `ai.ts`). Revertidos `agendaModuleAccess.ts`/`qualityModuleAccess.ts` ao padrão original idêntico a `financialModuleAccess.ts` — nunca foram a causa do alerta, então não fazia sentido divergir da convenção do projeto sem necessidade real.

**Validação:** `npm run lint` / `npx vitest run` (218 arquivos, 1113 testes) / `npm run build` — limpos em cada uma das 4 iterações de commit. CodeQL, lint-test-build, Dependency review e Analyze todos `success` no commit final (`7beb43d`).
